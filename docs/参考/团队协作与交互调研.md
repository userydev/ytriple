# ytriple 团队协作与交互调研

公开资料核查：2026-09-11。

本文是[产品调研](../产品调研.md)的专项参考，研究常驻团队、子 Agent 和用户交互如何相互支撑。官方能力、研究判断和体验示例分别标明；不是开发规格，不规定技术栈、接口、组件、数据库或开发排期。没有进行框架安装、付费模型调用、实机界面测试或性能对比。研究从零建设的新产品，不参考 ytriple 旧实现。

## 1. 研究服务于什么产品

本专题依据本轮用户讨论：ytriple 是吸收与产出的工作台，Y 与团队共同从外部和实践中吸收，形成本地 Lib 资产；产出面向人的说明书，以及面向 Agent、工具和专业执行者的说明书，再通过真实使用、用户成长和项目反馈改进资产。说明书包括直接文档成果、判断依据、方法、工作流和执行说明，不只是聊天答复。

多 Agent 交互是贯穿这条主线的底层核心，不是单独的角色聊天模块。常驻的统筹、CTO、Deep Research 等成员，应能交流、委派、追问、使用彼此成果，并按需调用子 Agent。用户面对团队或一个成员，不承担转述和协调全部助手的负担。

从 0x 继承的个人状态、信息理解、能力、连续性与学习不因此被替换。项目开发仍遵守初始化、监控、指定反馈文档的边界；具体工程设计与修改交给 Codex。完整方向见[讨论总结](../讨论总结.md)。

## 2. 首要结论：团队协作和子任务委派不是一回事

**研究判断：稳定团队 + 按需子 Agent + 共同的工作对象，是比固定三次调用更适合 ytriple 的产品结构。**这里的结构是责任关系，不是强制的运行时拓扑。

| 层面 | 用户或成员的需要 | 不能混淆的地方 |
| --- | --- | --- |
| 常驻成员 | 身份和职责稳定，可以持续交流；共享当前目标与必要证据 | 常驻不等于进程永不退出、模型一直运行，也不等于每次全员参加 |
| 成员之间 | 研究员交付依据，CTO提出缺口并要求补查，统筹组织收敛 | 相互利用和修正结果，不是给同一问题加几个人设后各自回答 |
| 成员与子 Agent | 将限定的调查、提取、比较或验证工作交给专项助手 | 子 Agent 对具体任务负责；调用它的成员仍负责核查、整合和向用户交付 |
| 人与团队 | 直接与一个成员交流，或让团队处理目标 | 换成员不能等于丢失工作背景，也不必把所有子任务变成用户的新聊天窗口 |

执行责任可以呈层级，成员间沟通不必只有一棵树。是否用消息、共享成果、工具调用或其他方式连接，由具体实现决定；关键是能追溯“谁委派、谁补充、哪些证据改变了结果”。

Claude Code 的官方团队文档区分了团队成员直接通信与子 Agent 返回专项结果，并提供直接联系成员的交互。它是可参考的产品行为，不是 ytriple 必须依赖的底座。[R1]

## 3. 已有方案能提供什么

| 参考方案 | 官方资料支持的能力事实 | 适配 ytriple 的判断与限制 |
| --- | --- | --- |
| OpenAI Agents SDK | 区分 agents-as-tools（调用者保留对话责任）与 handoff（把当前对话交给另一成员）；支持嵌套调用中的审批和包含工具活动的事件流 [R2][R3][R4] | 可以参考“找助手”和“找另一个成员”两种关系；单纯 handoff 或 asTool 不等于完整的团队消息、共享资产与持续协作产品 |
| Google ADK | 官方仓库说明 AgentTool、父子 Agent、会话状态和工作流机制；当前资料也提示新工作流选项替代部分旧式自定义方案 [R5] | 可研究层级委派、共享结果和 Google 能力，但不能只照旧示例固定框架形态；具体 SDK 语言、版本与功能需对应验证 |
| LangChain / LangGraph | 支持用子 Agent 隔离专项上下文；子图可选择每次调用隔离或跨线程调用累积状态，并支持检查点与中断 [R6][R7][R8] | 对长任务、恢复和跨轮工作有参考价值；不是必须把用户工作做成可视化图，也不说明选它就自动得到可靠记忆 |
| Claude Code Agent Teams | 成员有各自上下文，可直接通信、查看成员工作；官方仍标实验性，并列出会话恢复、状态滞后、嵌套团队等限制 [R1] | 研究交互与责任分配，不照搬其终端界面，不以它满足任意层级和长期团队持久性为前提 |
| AG-UI | 用运行、文本、工具、活动和状态事件连接 Agent 与前端，区分状态快照与增量 [R9] | 是界面与运行过程互通的参考，不是 Agent 编排器或用户权限系统；可借其思路，不强制采用协议 |

**选型判断：复用一个合适的主要运行方案，再补产品需要的协作与交互；不是把上述框架全部叠在一起。**研究应同时检查真实委派、必要上下文传递、用户参与、子任务可见性和恢复，而不是只验证几个模型都能返回文本。最终选型留给 Codex。

### 模型与外部研究服务不应限定团队形态

OpenAI 兼容格式与 Google 原生能力继续保留。OpenAI SDK 文档明确区分 Chat Completions 和 Responses，部分能力只适用于后者；因此兼容入口不代表全部工具、事件和状态功能等价。[R10]

Google Deep Research 是通过 Interactions API 使用的外部研究服务，支持其文档列出的研究工具与远程 MCP。它可以为常驻研究员工作，但不等于本地子 Agent 可以任意修改它的内部流程、读取所有中间状态或接管本机工具。[R11]

对外部服务，只展示实际提供的状态、引用和结果。供应商不暴露子任务时，不能在 UI 中编造它的“子 Agent 树”。接入 Google 也不意味着整个团队必须改用 Google ADK。

## 4. 三种协作关系需要同时研究

### 委派：请助手把一个问题查清楚

例如研究员将一批收藏按主题分配给提取助手，再请核查助手查证争议点。每个助手获得限定问题、必要材料和被允许的工具，返回结果与依据；研究员决定是否采纳、继续补查或合并。

这是适合分解任务的方式。OpenAI agents-as-tools 和 LangChain 子 Agent 都提供相关机制。[R2][R6] 但“并行出结果，再拼接”只是基础形态，不应成为整个协作能力的上限。

### 协商：成员利用和纠正彼此的工作

例如 CTO 发现研究员推荐的工具无法满足当前本地条件，直接提出一个具体补查问题；研究员调查后修正能力说明，统筹再更新面向 Y 的判断。这个过程不要求所有成员广播全部发言，也不靠无限辩论证明质量。

这是本产品的研究判断：协作应围绕证据、问题和正在形成的说明书发生。保留未解决的分歧，限制无收益往返；多个成员重复同一来源，不构成多份独立证据。

### 转交：用户现在直接和另一位成员工作

用户正在和统筹交流，但希望 CTO 专门解释一处工具限制。可以切到 CTO，同时保留当前工作对象和有效目标；局部问答不一定自动改动全团队计划。

OpenAI handoff 是这种责任转移的参考之一，但“界面选择一位成员”“实际转交对话责任”和“把全局目标改掉”是不同事情。[R2] 产品需要让用户理解影响范围，而不要求用户理解运行图。

## 5. 连续性与扩展能力的关键取舍

以下是基于研究提出的边界，不是接口设计。

**身份、工作状态、Lib 资产分开。**身份可以长期存在；专项任务可以结束；知识和可复用方法不应只留在某个助手的临时会话。成员共享当前有效目标和必要事实，而非复制整个 Lib。LangGraph 对每次调用隔离与跨调用状态的区分可提供参考，但不能替代产品对项目归属和资料权限的判断。[R7]

**子任务可增加，但责任不能丢失。**每个助手应有明确的委派来源与任务范围；可以扩展层级，但需要合理的并发、深度、时间、费用和往返上限。停止某项工作时，需要知道哪些子任务或远端请求仍在运行，不能只停止界面动画。上限的具体数值不在此规定。

**用户修正需要传到受影响的工作。**补充条件、改变整体目标、要求暂停是不同操作。旧目标下迟到的结果应保留为可识别的旧结果，不悄悄进入新版说明书。外部任务不能实时改向时，应明确说明继续、取消或另起研究的实际效果，而不是假装已修正。

**任务返回不等于资产已经有效。**子 Agent 的材料先交给负责成员核查；正式说明书与 Lib 资产的更新需保留依据和修订关系，不能让所有助手各自覆盖同一个权威文件。说明书已生成、已保存、已交给工具和已验证有用不是同一个完成状态。

**安全与费用不能因委派扩大。**子 Agent 不应凭身份或层级自动获得整个项目、所有 MCP 或安装权限。已有授权范围内的低风险工作不应反复弹窗，但越界动作必须有清晰的用户决定入口。OpenAI SDK 的嵌套审批上浮机制是一种现成参考，不等于父任务一次批准以后所有子任务都得到授权。[R3]

**恢复不等于任意步骤无损重放。**LangGraph 文档提醒，中断恢复可能重新执行节点，中断前有副作用的操作须避免重复产生影响；其子图状态检查也取决于调用方式，工具内部包裹的子图不一定能被直接检查。[R7][R8] 对 ytriple 的启发是：保存了聊天并不代表保存了完整工作；重新打开后应区分正在运行、已中断、等待恢复和未知状态。

可扩展性的目标是增添成员、工具、Skill、MCP、专项助手或托管能力时，沿用同一套工作和成果表达；不是一开始建设无限递归团队、插件市场或庞大配置中心。

## 6. UI 是协作的一部分，不是运行完成后的装饰

### 两类已有交互参考

Claude Code 团队文档提供集中查看成员与分屏查看两种形式，并允许直接联系成员。可借鉴的是“知道谁负责、能直接找人、能查看工作”；不能将“更多终端同时滚动”照搬成消费者工作台。[R1]

Microsoft HAX 将易于调用、忽略、纠正，解释系统行为，说明用户操作后果和谨慎适应列为人机交互原则。[R12] 对 ytriple 的研究判断是：用户既要感受到团队正在替自己工作，也要能轻松纠正，而不是只能等待或阅读大量日志。

### 建议探索的交互细节

下表是体验方向与考察点，不是固定页面或组件清单。

| 用户的动作或处境 | 应体现的体验 | 要避免的问题 |
| --- | --- | --- |
| 打开一项工作 | 看见当前目标、负责成员、相关材料，以及正在形成的说明书 | 先面对空白输入框，重新交代背景 |
| 与团队或一位成员交流 | 接收对象明确；切换成员保留同一工作和有效背景，可返回团队视图 | 每个身份成为另一座聊天孤岛，或局部问题被当成全局指令 |
| 成员调用子 Agent | 默认看成员负责的事项和关键变化；按需展开专项助手、来源、发现与失败原因 | 为每个子 Agent 新开主窗口，或只显示“思考中” |
| 阅读成果时出现新结果 | 阅读位置、选中段落与输入草稿保持稳定，新发现有克制的提示 | 自动滚动抢焦点、反复重排、每个 token 都打断用户 |
| 对一条证据或说明书段落有疑问 | 就地提问、质疑或补充材料，团队知道针对哪一对象和版本 | 复制到聊天再解释；只改回复，不影响对应成果 |
| 改变目标或否定一个判断 | 说明影响的是解释、草稿还是正在进行的任务；呈现受影响部分 | 显示“收到”却继续旧方向，或无差别重做全部内容 |
| 面对两类说明书 | 能看懂面向 Y 的结果，也能检查面向工具的目标、条件和执行说明；同一目标下相互对应 | 强制每次生成两套重复文件，或把机器参数当成用户摘要 |
| 有权限请求、分歧或失败 | 说明具体事项、影响和当前可保留的结果；只把真正需要判断的部分交给 Y | 弹窗轰炸，或把等待审批、外部服务失败表示成正常完成 |
| 关闭后回来或换设备环境 | 根据实际保存和运行条件恢复工作；不能恢复的部分明确标出 | 把旧截图或历史最后一句话当作实时状态 |

常驻团队应有稳定的可达入口，专项助手可逐层展开。主工作对象是被消化的知识与正在形成的说明书，成员和助手用于说明它如何形成、怎样继续改进。研究不限定三栏，也不要求完全隐藏团队过程。

### 前端需要的不只是文字流

OpenAI SDK 的文字流只输出助手文本，完整事件流才包含工具调用、成员切换和审批等信息。[R4] AG-UI 则提供运行、工具、活动和状态事件及快照/增量机制。[R9]

特别注意：工具参数发送结束不等于工具实际执行成功，AG-UI 将工具调用结束与工具结果分开；同理，流停止不等于说明书保存成功。UI 的状态要依据真实运行结果，而不是从模型的一句“已完成”推断。

研究判断：底层协作与 UI 同时围绕真实工作状态设计。可以参考 AG-UI 的表达，也可以采用更简单的本地机制；不必为了界面上显示父子任务就额外引入分布式协议。调试 Trace 可以保留给深入检查，但不是默认用户工作界面，更不能拿内部推理全文替代证据与结果。

## 7. 一个贯穿吸收与产出的体验例子

以下是候选体验，用来说明价值，不是固定执行流程：

用户交给团队一批积压收藏，希望留下真正有用的知识和工具方法。统筹理解用户目的与已有 Lib；研究员调用专项助手提取、去重、归纳，并返回保留或过滤的理由及来源。读取不完整的材料单独说明，不把标题分析冒充全文理解。

CTO 看到其中一个工具方案，发现与本机条件不符，要求研究员补查；必要时调用获准的验证能力。用户只看主题总结和关键分歧，需要深入时展开材料，不必逐个读取助手对话。

团队形成面向 Y 的理解与指导，以及面向工具的使用说明或工作流草案。Lib 中已有资产优先修订关联，不盲目新增重复文件。未经运行验证的方法仍标草案；被过滤的收藏不等于已经从原平台删除。

这些说明书经过人或专业工具实际使用，项目结果和用户修正再回到工作台。专项助手可以结束，有效知识、使用条件与经验则留下。来源订阅、项目反馈和账号观察可以逐步接入，不要求本轮同时建设所有入口。

## 8. 哪些还没有被这次研究证明

没有实测的包括：候选 SDK 对实际 OpenAI 兼容服务的稳定性；Google 托管研究的真实响应和控制范围；嵌套任务在桌面关闭后的恢复；真实团队是否比单成员减少返工；界面是否让用户更容易判断和修正。官方功能存在，不等于它们组合后已经满足 ytriple。

考察方向应围绕完整工作：用户只说一次背景能否换成员继续；能否观察到成员基于另一成员的证据改变结论；子任务失败或用户修正后是否保留有效成果；是否真正留下有用说明书与 Lib 资产。少量小任务与复杂任务都值得比较，不能只用 Agent 数量和生成字数说明“倍增”。具体试验与工程验证由 Codex 设计。

**本轮结论：协作内核、扩展能力、用户交互应作为同一个问题研究。需要的不是几个独立 Prompt，也不是不受控的 Agent 网络，而是一支 Y 能理解、能纠正、能利用其成果的团队。**

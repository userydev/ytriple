# ytriple 信息源与知识工作台方案调研

**资料核查：2026-09-12｜性质：产品与能力专项研究，不是工程规格。**

研究基于 `userydev/ytriple` 的 `dev` 提交 `7a95e3bec8dd36f40e0a03d0560478a77499a797`。承接 [讨论总结](../讨论总结.md)、[产品调研](../产品调研.md)、[团队协作与交互调研](团队协作与交互调研.md)，并参考当前 [抖音收藏接入验证](抖音收藏接入验证.md)。不修改 Codex 的开发计划，不替换已完成的工作台与团队底座。

本轮覆盖 **32 项产品、开源方案、采集基础设施和解析组件**，以及信息源目录、浏览器接口、能力格式等资料。全文分别标记：**官方能力事实、项目已有证据、研究判断、待实测条件**。官方文档存在不代表已经在 ytriple 接通；本轮没有安装这些系统，没有调用付费 API，没有使用用户登录态采集，也没有做性能、版式或完整用户旅程实测。

## 0. 核心结论

**研究判断：ytriple 不宜选择一个“万能爬虫”后继续堆来源，也不宜改造成某个完整开源产品的换皮。** 更合适的方向是：复用成熟的来源发现、订阅、正文提取与受控采集能力；保留自己的团队、说明书和 Lib；重点吸收成熟产品在“如何消化、如何复用、如何让用户纠正”上的完整做法。

| 判断 | 本轮证据与含义 |
| --- | --- |
| 信息源不等于抓取器 | RSSHub 解决路由转换，RSSHub Radar 解决发现，FreshRSS/Miniflux 解决订阅和条目管理，正文提取器解决内容转换；它们不能互相冒充。[S28–S31][S39–S45] |
| 竞品已经不止摘要 | Readwise 有全库研究、可复用 Skill、Inbox/Feed 分诊和受控写操作；Inoreader 有定时多文章报告。不能再把“AI 摘要＋订阅”当作明显差异。[S01][S03] |
| 完整产品值得拆解 | Karakeep 的订阅—收藏—AI 整理、Open Notebook 的来源—转换—笔记—产出、BettaFish 的多类证据与报告，分别提供可借鉴的完整路径。[S09–S12][S21][S27] |
| 自托管不等于没有外部依赖 | TrendRadar 部分热榜依赖 NewsNow；WeWe-RSS README 声明使用外部转发服务且仓库已归档；Firecrawl 自托管不具备全部 Cloud 能力。[S32][S33][S36][S43] |
| ytriple 的重点是个体化积累 | 把新内容与 Y 的目标、既有判断、工具条件和 Lib 比较，形成知识更新或能力线索，再用于说明书；这是本产品的方向，不是本轮证明的独占优势。 |
| 开源复用必须按实际版本判断 | RSSHub 当前上游为 AGPL-3.0；Folo 有图标例外；Dify 有附加许可条件。“GitHub 上可下载”不是统一的商用授权。[S07][S26][S28] |

**首要参考组合，不是选型命令：**

- 阅读与主动吸收：Folo、Inoreader、Readwise Reader。
- 收藏消化与本地资产：Karakeep、Linkwarden、Obsidian Web Clipper。
- 从资料到知识与产出：NotebookLM、Open Notebook；BettaFish 提供团队证据协作参考。
- 可复用的基础能力：RSSHub/Radar、Miniflux 或 FreshRSS、Defuddle；复杂网页与文档再研究 Crawl4AI、Firecrawl、Docling 等。

这组参考不要求全部安装。产品做法可以吸收，组件可以按需复用，已有第三方服务可以通过授权接口连接；三种方式应分开。

## 1. 研究问题与证据口径

### 1.1 本轮真正要解决的问题

用户的困境是收藏分散且积压，缺少阅读时间；希望主要看团队处理后的理解，而不是再维护一套收藏夹。新信息也需要持续进入，但不能重复制造阅读负担。吸收既服务 Y 的知识、思路与判断，也服务 Agent 的工具、Skills、MCP 和工作流能力。

因此研究覆盖整条价值链：

**发现来源与导入收藏 → 取得真实内容 → 筛选与归并 → 主题理解与核查 → 更新本地知识/能力资产 → 用于两类说明书 → 实际使用与反馈。**

这是一种分析框架，不是要求每条内容都走完整流程。普通浏览、单条保存、一次性研究可以独立发生。

### 1.2 三类来源不能混淆

**用户与项目资料：** 当前产品正文、开发记录和抖音验证记录解释我们要做什么、已有证据到哪里。工程记录中的“已实测”是 Codex 的记录，本次没有独立复现。用户提供的视频参考强调有用知识、本地组织和结果复盘；其比例、数量门槛和自动变现表述不是本研究验证的事实，不作为产品保证。

**外部一手资料：** 产品官方帮助、维护者仓库、许可文件和官方接口文档，用于说明候选能力。功能宣传中的覆盖率、准确率、“自动变现”“预测趋势”等不能直接当作可交付证据。

**研究判断：** 适合吸收什么、怎样组合更贴近 ytriple、哪些风险应注意。它们供产品讨论与 Codex 选择，不自动成为用户已确认需求。

### 1.3 判断一个方案的八个维度

| 维度 | 研究关心什么 |
| --- | --- |
| 接入范围 | 公共订阅、私有收藏、文件、音视频、更新监控分别支持什么 |
| 内容深度 | 列表/摘要、完整文字、字幕、音频、画面/图表是否区分 |
| AI 作用 | 单篇摘要，还是跨资料综合、分诊、差异识别、工具调用与可修正产出 |
| 资产可携带性 | 能否保留来源、导出正文/批注/结构，是否只能留在供应商数据库 |
| 工作连续性 | 能否从来源进入研究，从成果返回来源，从新材料修订既有知识 |
| 集成形式 | 学习产品行为、消费 API、独立部署服务、嵌入组件的代价分别如何 |
| 运维与依赖 | 数据库、浏览器、模型服务、公共实例、版本更新和登录条件 |
| 证据与许可 | 能力事实与实测分开，当前许可证、归档状态和例外是否可核查 |

本轮不以 Star 数、宣传的支持站点数、模型数量或新闻量给总分。这些不能证明对真实收藏的覆盖和消化质量。

### 2.1 完整或较完整的产品：16 项

下表“借鉴与定位”均为研究判断；最后一列不表示竞品一定没有某能力，只说明本轮不能据此作出该承诺。

| 产品 | 已核查的能力事实 | 对 ytriple 的借鉴与定位 | 不能直接推定 |
| --- | --- | --- | --- |
| Readwise Reader | Global Ghostreader 跨库检索、逐段引用、可编辑技能及受权限控制的资料操作；另有 Reader API。[S01][S02] | 最贴近“收藏不看→代为消化→追问→复用”的产品参考 | 技能存在不等于可以无监督正确淘汰所有内容；不是本地开源整套系统 |
| Inoreader | 从 Feed/文件夹/标签等创建定时多文章 Intelligence 报告，结果保存在阅读系统中；可选择 AI 提供方。[S03][S04] | 来源到专题报告、持续消化与订阅服务的直接参考 | 定时报告不等于长期知识修订；不等于有相同能力的免费 API |
| Feedly Market Intelligence | AI Feeds、趋势/公司观察、Ask AI 与报告；有内容近重复处理。[S05][S06] | 主题观察、去噪、为什么相关、从信息进入调查 | 企业情报模块不必照搬；去重不是所有事件和观点的语义合并 |
| Folo | 多类媒体的统一订阅与列表发现，提供 AI 翻译和摘要。[S07][S08] | 每日阅读入口、源包发现、不同媒体合适的浏览方式 | 支持视频条目不等于取得完整视频语义；客户端开源不证明所有线上服务可等价自部署 |
| Karakeep | 保存链接、笔记和文件，AI 标签/摘要、搜索、规则；可消费 RSS 并提供 API。[S09–S12] | 自托管收藏收件、批量整理、机器可操作资料库的综合参考 | 自动标签不等于知识正确或已吸收；不要再给用户强加第二个权威 Lib |
| Linkwarden | 收藏、网页多形式保存、阅读/批注、全文搜索、API 与可选 AI 标签。[S13][S14] | 保留证据快照、批注与原文位置，链接失效时仍有依据 | 快照保存不等于获得公开再分发权，也不等于语义知识更新 |
| Obsidian Web Clipper | 浏览器剪藏、高亮、模板、变量与 AI Interpreter，内容保存到本地笔记；扩展源码开放。[S15][S16] | 用户可见页面→本地资产的轻入口；文件长期归用户 | 扩展开源不代表 Obsidian 全产品开源；剪藏不自动处理全平台历史收藏 |
| wallabag | 自托管稍后阅读、抽取文章正文，以及浏览器/移动端保存。[S17] | 简单、可退出的阅读存储与导入思路 | 不应当作现成的 AI 知识消化引擎 |
| Raindrop.io | 官方帮助提供收藏整理、阅读、导入导出和开发接口等入口。[S18] | 接住用户已有收藏系统，而不是要求重建收藏习惯 | 具体计划、历史数据和可导出字段须查实际账户；不视作自托管软件 |
| NotebookLM | 官方帮助说明多种来源导入、Fast/Deep Research、来源分类与基于来源的工作；与 Gemini 的交互和 Studio 能力有区别。[S19][S20] | 围绕主题资料包工作、来源导航和学习型产出 | 产品页面中的能力不等于 Gemini API 全部可调用；YouTube 来源不是完整画面理解 |
| Open Notebook | 自托管来源/笔记/笔记本、多模型、可定制转换、检索、播客生成和 API。[S21] | 把“消化”定义为有明确目的的转换，产出可继续使用的笔记 | 不把 README 路线图里的跨笔记本复用当成已经交付 |
| Khoj | 自托管个人助手，结合网页与个人文档、定制 Agent、研究和定时自动化。[S22] | 持续上下文与主动研究的整体形态参考 | 定时自动化不代表结果不需核查，也不是替换本项目团队底座的理由 |
| AnythingLLM | 桌面/服务端的文档 Workspace、模型选择、检索与 Agent 能力。[S23] | 资料范围选择、模型可替换、文档问答可用性 | 本地数据库不等于外部模型调用也离线；不把聊天加文档等同于我们的完整产品 |
| RAGFlow | 面向文档解析、分块、检索、引用和 Agent 的开源系统。[S24] | 看解析覆盖、可追溯检索和引用质量；适合作深能力参考 | 不因此要求桌面首版装下整套服务栈；解析不等于实际文档质量已验收 |
| Dify | 可视化工作流、知识检索、模型与工具集成的应用平台。[S25][S26] | 观察数据处理/产出步骤的可配置性，作为服务侧候选 | 不是普通 Apache-2.0 无附加条件；不把节点编辑器变成用户使用 ytriple 的门槛 |
| BettaFish（微舆） | 多类分析 Agent、论坛协作机制与报告生产，整合舆情/网页/媒体等资料。[S27] | 研究不同证据角色怎样影响同一份报告，而非轮流发言 | 舆情研究不等于私人收藏；不采用其规模或预测效果宣传作为事实 |

这些工具只解决输入质量的部分问题。它们不能证明网页取得正确、字幕足以理解画面、来源内容可信，或得到的摘要符合 Y 的实际目标。

## 3. 最值得深入吸收的完整产品做法

### 3.1 Readwise：把“帮我消化积压”变成库内可执行工作

**能力事实：** Global Ghostreader 可针对整个库研究，给出回到具体段落的引用；内置任务包含 Research Topic、Tag Documents、Triage Inbox/Feed、Find Similar，用户可修改技能，并对读/写工具分别授权。[S01] Reader API 则是保存和获取文档的正式集成入口。[S02]

**对 ytriple 的启发：** 用户不必逐条打开并要求摘要，可以把“围绕我的目标整理这批材料”交给团队。工作对象是选定的资料集合和已有 Lib，完成后交付主题理解、保留/过滤理由、值得进一步验证的工具，而非另一个消息列表。

真正应借鉴的是从单篇、选中段落到全库工作的连续性。用户对一条结论有疑问时，既能看到支持它的原文，又能让团队查找相反材料。权限可以是明确的长期范围，而不是每加一个标签都弹窗；改变正式资产和源端数据则不能靠模糊授权。

**不照搬：** 不以“开一个全库 Chat”取代已有团队界面，不要求用户把所有本地资料移到 Readwise。可以研究作为已有用户的输入桥梁，但 API 数据访问与整个托管产品的 AI 能力不等价。

### 3.2 Inoreader：订阅交付物可以是专题报告，而不是未读条数

**能力事实：** Automated Intelligence reports 可以从订阅、文件夹或标签等选择材料，设置周期与提示，生成的报告保留在阅读系统中。[S03] 官方还说明可选择 AI 平台或使用相应自有密钥。[S04]

**对 ytriple 的启发：** 将“订阅某主题”升级为“持续维护一个我需要理解的问题”。每次交付应突出相对已有知识的变化：新增事实、被修正的判断、仍无证据的争议，而非每天重新从零生成一篇大综述。

这个差异是我们的研究目标，不是宣称 Inoreader 做不到。它已经证明“来源集合→自动报告”是现成产品方向，ytriple 必须进一步把报告与用户自己的说明书和资产连接起来。

**不照搬：** 不增加复杂团队管理、全部推送渠道或订阅套餐配置。用户首先需要的是少读而读懂、能纠正、能复用，而不是搭建一套报告生成后台。

### 3.3 Folo 与 Feedly：阅读入口要好用，但来源视图不等于知识视图

**能力事实：** Folo 强调统一内容时间线、订阅与精选列表、不同媒体形式和 AI 辅助。[S07][S08] Feedly 提供主题/公司情报与报告，近重复识别依赖内容比较；其去重文档另有来源与时间范围限制。[S05][S06]

**对 ytriple 的启发：** 日常入口既保留新鲜内容的浏览感，也提供“团队已经理解了什么”的主题视图。按原来源浏览用于追溯，按问题/主题浏览用于吸收，两者是不同需求。

不能把同事件的所有材料删到只剩一家，也不能将多个转载来源算作多份独立证据。值得展示的是“同一事件有什么新证据与不同观点”，不只是合并重复标题。

用户添加新来源时，可先看近期实际样本、能取得的内容层次及重复情况，再决定纳入哪个关注范围。来源包应降低冷启动成本，不要求用户逐项配置爬虫。

### 3.4 Karakeep 与 Linkwarden：收藏是入口，证据与机器可操作性更重要

**能力事实：** Karakeep 能把 RSS 条目纳为书签，跳过已存在条目，并能把列表再输出为 RSS；另有 API、AI 整理及规则。[S09–S12] Linkwarden 的重点包括网页保存、阅读批注、搜索和可选 AI 标签。[S13][S14]

**对 ytriple 的启发：** 收藏应带着来源和用途进入，而不仅是一个 URL。用户为什么保存、后来用于哪次工作、AI 基于哪部分内容得出结论，比自动加十个标签更有价值。

对已有 Karakeep/Linkwarden 用户，可以研究增量读取其收藏与批注，避免重建采集入口。但原收藏状态和 ytriple 中“已读/已理解/已采纳/已验证”不能无条件双向同步：在 ytriple 过滤一条内容，不表示用户希望删除原书签。

证据快照与权威项目文档不是一回事。可以保留获准内容的观察版本以支持追溯，但不复制一份会与 Codex 文档竞争的新事实源；也不默认公开分发保存的全文。

### 3.5 Obsidian Web Clipper：轻入口和本地文件可以与 AI 配合

**能力事实：** Web Clipper 支持剪藏、高亮、模板和 Interpreter；其扩展源码采用 MIT，但图标、市场素材和商标存在例外，Obsidian 应用本身与扩展许可不能混为一谈。[S15][S16]

**对 ytriple 的启发：** 用户的资料并不只来自订阅，有时只需要“把这一段和我刚才的想法带回工作台”。浏览器动作应尽量轻，复杂分析发生在同一个工作对象中，而不是扩展里再造一套团队、知识库和模型设置。

本地结果应能被其他工具读取。模板可以帮助保留来源、标题、用户备注和内容范围，但不能把模板字段堆成用户必须填写的表单。系统先提取，用户只修正必要部分。

### 3.6 NotebookLM 与 Open Notebook：从资料包到理解与产出

**能力事实：** Google 官方来源帮助描述了网页、文件和有字幕的公开视频等输入，以及 Fast/Deep Research。YouTube 输入只导入转录文本，网页输入也不代表嵌入视频和所有子页面被导入。[S19] Gemini 中的 Notebook 入口与完整 Studio 功能有明确差别。[S20]

本次 NotebookLM 的部分官方帮助链接重定向到 Gemini Notebook 域路径，本文为便于识别保留常见产品名；只陈述读取到的能力，不据此额外推断完整更名或 API 发布情况。

**能力事实：** Open Notebook 提供来源、笔记、笔记本、可定制 transformations、多模型及产出能力。当前 README 的 roadmap 仍包括某些跨笔记本和集成增强，不能全部记作已完成。[S21]

**对 ytriple 的启发：** “消化”可以有不同目的：概念地图、方法比较、证据对照、实践说明、待核查问题。用户不用反复从空白 Prompt 写起，团队可以选择合适的处理目的；输出必须保持与材料的关系。

但知识并非切得越碎越好。原子化方法要保留前提和反例，主题总结又要能回到具体依据。对人可读的学习说明，与机器可用的工具说明，可以由同一组证据产生，不要求复制两份全文。

**不照搬：** 不因工具提供播客、信息图等就把所有导出形式加入当前目标；也不把 NotebookLM 的产品按钮当作可直接集成的 Gemini API。

### 3.7 BettaFish：多 Agent 的价值在证据互补与报告修正

**能力事实：** 项目将 Query、Media、Insight、Report 等能力与论坛式协作结合，围绕舆情产生报告。[S27]

**对 ytriple 的启发：** 把不同成员与不同证据能力匹配。研究员看到工具宣传，CTO 检查实际接入条件，统筹依据冲突要求补证据，最终报告记录判断如何变化。值得吸收的是相互影响，不是照搬角色名或“开会”动画。

研究范围也要区分：舆情样本、个人收藏、完整文章、自己的账号后台，是不同数据集合。多个 Agent 引用同一个错误源不会自然更可信，论坛一致意见也不是实际验证。

**不照搬：** 不复制其独立的整套 Agent 引擎、舆情基础设施和前端去替换已完成的 ytriple；不把其厂商描述的规模或预测效果当作本项目能力承诺。

### 3.8 TrendRadar 与 NewsNow：容易起量，难点是上游依赖与知识沉淀

**能力事实：** TrendRadar 将热点/RSS、过滤、AI 分析和推送连接起来，README 明确指出新闻热点 API 与 NewsNow 的关系。[S33] NewsNow 提供多源榜单，当前仓库有暂停接收贡献、筹备新版本的提示。[S32]

**对 ytriple 的启发：** 可以作为热榜输入和每日简报形态的样本，不必重新写所有站点榜单适配。但同一上游经过多个聚合工具转发，仍是一条依赖链，不能算独立多源冗余。

热度是发现线索，不是可信度，也不是对用户有用的充分条件。热榜事件应回到原始报道或发布方核查，然后与已有主题资产比较。不能用“增加支持平台数”替代处理用户自己收藏的实际困境。

### 3.9 RSSHub＋订阅服务：解决公共信息供给，但不承包所有吸收

**能力事实：** RSSHub 侧重来源转换，Radar 侧重发现；FreshRSS 与 Miniflux 提供持久订阅和 API，前者扩展较多，后者功能取向较聚焦。[S28–S31]

**对 ytriple 的启发：** 来源可以由独立、自部署或托管组件提供，工作台消费其条目，再做团队理解与 Lib 对照。来源层不必知道用户的所有私有认知与项目文档。

然而 RSS 未必提供全量历史，条目也可能只有摘要。OPML 主要转移订阅列表，不是完整转移用户的全部阅读历史、批注和知识资产。一个 RSS 转换路由不能替代本人授权下的私有收藏通路。

### 3.10 Khoj、AnythingLLM、RAGFlow、Dify：可参考整体，但不重复建设已完成部分

这些方案分别体现个人助手、文档 Workspace、解析检索以及应用工作流平台的取向。[S22–S26]

**研究判断：** 此时更有价值的是按问题比较：现有输入在哪些样本上丢信息？来源引用能否返回原文？跨任务复用是不是只传文件名？一个有用的转换能否稳定重用？而不是因为某套框架功能多，就迁移整个 0.1。

Dify/RAGFlow 这类服务侧平台可作为独立能力研究候选；其部署和运维成本、许可条件及与现有资产的关系，必须一起考虑。可视化流程是开发者的表达方式之一，不必成为 Y 日常工作的主要界面。

## 4. 信息源不是一种对象：接入与内容覆盖矩阵

以下是研究分类，不是数据库表设计。

| 来源类型 | 适合的取得方式候选 | 实际应知道什么 | 主要风险 |
| --- | --- | --- | --- |
| 原生 RSS/Atom/JSON Feed | 直接订阅，或 FreshRSS/Miniflux 等服务 | 原文地址、条目身份、内容范围、发布时间与观察时间 | 摘要冒充全文；Feed 截断历史；条目更新被当成新文章 |
| 无 Feed 的公开网页/目录 | 页面 Feed 发现、RSSHub 路由、正文提取、变化监控 | 是文章、栏目、目录还是能力文档；来源是否可持续读取 | 动态页面、提取误删、入口改版、一次抓取误报订阅成功 |
| 用户私人收藏 | 目标平台授权接口、用户触发的浏览器辅助、平台导出文件 | 收藏与发布内容区别、分页覆盖、本人权限、收藏分组 | 只拿到首屏；把未出现视为删除；带走登录凭据 |
| 已有收藏产品 | Readwise/Karakeep 等可用 API，或用户导出 | 外部 ID、批注、来源、增量与同步方向 | 一次导入无更新；原平台状态和 ytriple 知识状态误同步 |
| 公开账号与频道 | 平台实际允许的公开接口/Feed/页面；必要时用户授权 | 当前公开内容及采样范围，与本人后台数据分开 | “公开可见”误当完整历史；账号改名和删除造成归属错误 |
| 文章与文档附件 | 获准文件导入、正文/版面解析 | 全文、缺页、表格、脚注、图像是否被覆盖 | 纯文字误解释复杂图表；错误提取进入正式结论 |
| 视频与音频 | 可取得的转录/字幕、用户提供音频、允许的多模态处理 | 标题、描述、字幕、声音、画面分别参与了什么 | 字幕缺失、专有名词误识别、内容与简介矛盾；转录不等于看过画面 |
| GitHub 工具与模型仓库 | 作者 README、Release、文档、问题与模型卡 | 实际版本、环境、用途、许可、未解决限制 | 热榜/Star 当质量；README 宣传当运行结果 |
| 新闻与行业热点 | 原发布源、可靠报道、聚合发现线索 | 事件发生时间、发布时间、转载关系、不同观点 | 旧文重发、同源转载假多源、热点压过长期重要内容 |
| 邮件 Newsletter 等 | 用户主动转存、授权邮箱或阅读服务接入 | 订阅正文与邮件隐私边界，附件与跟踪链接 | 为一份 Newsletter 索取整个邮箱；转发私有信件 |

**本轮平台判断：** 不改写既有抖音验证结论。已观察正常登录下的收藏列表和成功批量响应，不代表自动采集或视频内容补全已完成。知乎 CLI、Grok/X 等已有线索继续以主研究文档与实际账号验证为准。本轮不补造任何用户私有收藏接口、访问凭据或采集成功记录。

## 5. 本地解析、浏览器辅助与远端服务怎样选

### 5.1 不用一个组件承担所有工作

**研究判断：** 简单公开页面先比较现有提取能力与 Defuddle/Trafilatura；需要浏览器渲染时才研究 Crawl4AI 或受控浏览器；需要专门托管能力时再比较 Firecrawl/Jina；复杂文件可以单独评估 Docling。不是每个链接都先启动浏览器、转录、调用大模型。[S39–S45]

原始采集与翻页适合可核查的程序行为，AI 主要处理来源识别、语义判断、例外与综合。不要让多 Agent 逐条“假装浏览器”采集，也不要把模型按标题补出的正文当成抓取结果。

### 5.2 浏览器入口应服务本人可见内容

Chrome 的 activeTab 提供由用户操作触发的临时标签页访问；Native Messaging 提供扩展与本机应用连接的机制。两者是入口能力，不是获得全站、全历史数据的保证。[S54][S55]

已有抖音研究指出，普通 webRequest 不是任意响应正文读取接口。正式采集需验证自己的取得内容方式，不能把开发者工具里看见 JSON 当作应用已经能收到 JSON。[S56]

对 ytriple 可研究两种边界清楚的体验：单页或选中内容主动带入；明确授权后采集一个限定收藏范围。它们不要共用一个含糊的“读取浏览器全部信息”开关。插件不需要独立承载团队和 Lib。

### 5.3 托管与自部署不保证能力相同

Firecrawl 官方自托管指南明确区分快速启动与生产环境，也说明不是所有 Cloud 能力都包含在自托管中。[S43] WeWe-RSS 即使部署在本机，仍有 README 申明的外部转发依赖。[S36]

因此，方案研究需同时说明运行地点、数据发往哪里、额外凭据、是否依赖公共实例。自部署解决的是控制与运维责任，不自动解决平台访问权、完整内容、稳定性和成本。

## 6. 可预置的信息源包与用户追加来源

### 6.1 开箱信息源应围绕问题组织

下表是**预置源包候选**，不是已经接通的列表，也不是固定用户偏好。我们验证了列出的官方入口或文档，不代表逐个 Feed 已经通过产品采集与长时间存活测试。

| 源包候选 | 可用入口样本 | 团队应产出什么 | 重要限制 |
| --- | --- | --- | --- |
| AI 模型与工具变化 | 厂商官方公告/文档、Hugging Face Blog、指定作者仓库 Release [S51][S52] | 能力变化、适用条件、对现有方法的影响 | 官方发布是能力声明，不是本机实测；社区文章与官方稿分开 |
| 独立开发与开源实践 | Hacker News 官方 API 的 Show/Ask/讨论，用户关注的 GitHub 原仓库 [S49][S51] | 问题、方法、工具线索及作者依据 | HN 帖子链接不是被链接文章全文；热门度不等于适用性 |
| 研究方法与新知识 | arXiv 分类订阅、作者材料 [S50] | 哪个问题出现新证据、哪些研究值得看 | 摘要不等于已阅读论文；预印本结论不能省略条件 |
| 技能与工具能力目录 | MCP Registry、Agent Skills 格式、维护者工具文档 [S46–S48] | 可用于什么目标、依赖与权限、候选状态 | 注册不等于安全审计；Skill 格式有效不等于运行有效 |
| AI 落地方案发现 | 用户此前指定的 AIGCLINK/AI 方案库 [S53] | 发现方案后返回原作者或官方文档核查 | 目录是发现线索，不是最终能力、许可或维护状态证据 |
| 用户主题/行业包 | 用户选择的可信媒体、创作者、领域官方源 | 对此用户有用的主题理解与变化 | 不能根据当前聊天替其他用户默认订阅一切 |

内容选择应结合用户明确目标、当前工作与已吸收知识，同时留出可调整的探索空间。不能只喂用户已同意的观点，也不能让所有源包最终都变成 AI 新闻榜。

### 6.2 添加网址时需要识别什么

**研究判断：** 输入一个地址后，先辨认是单篇资料、持续栏目、Feed、账号、工具目录还是软件本体，再提供真实样本与接入状态。系统能判断的先准备，用户修正；不能为了填写规范字段增加负担。

来源可以单次导入，也可以持续观察。识别失败、需要登录、只有摘要、暂不可达要明确。更换采集器不应导致用户丢失已确认的关注范围和原始来源。

### 6.3 给后续新增来源保留统一登记口径

这是研究登记模板，不是接口或数据库规格。用户提供新来源后可沿用同一口径，不需要再重写全局产品：

| 记录内容 | 用处 |
| --- | --- |
| 名称、准确地址、所有者/维护者 | 不把镜像、同名项目和聚合站当原始源 |
| 来源角色 | 新闻、正文、收藏、目录、工具、能力说明或结果反馈 |
| 用户为何关注、适用主题 | 解释相关性，而不是只有类别标签 |
| 可取得内容与历史范围 | 区分首屏、分页、全文、字幕和仅链接 |
| 接入方式与授权条件 | 公共、本人授权、用户主动导入或不可获取 |
| 当前证据状态与观察时间 | 文档声明、页面样本、接口样本、应用实测分开 |
| 上游依赖、内容用途与维护风险 | 判断是否适合持续提供或托管 |
| 预期进入哪类资产 | 给 Y 的知识、给 Agent 的能力、还是暂存线索 |

## 7. 从“摘要”升级到“个人知识消化”需要吸收哪些功能

以下是跨产品综合得出的研究判断，不是新增固定页面或工程工作流。

### 7.1 批量分诊，而非每篇单独提问

用户选择一个来源或一批收藏，只需给出处理目的。团队区分重复、过时、暂不相关、证据不足和有用信息，给出简短理由。低价值内容从主要阅读结果中过滤，但保留查看与纠正途径；默认不删除原平台收藏。

真正难点是“对谁有用”。同一篇文章对初学者可能是新方法，对已使用该工具的用户可能只是重复。不能用全体用户共享的一个热度分数决定全部取舍。Readwise 的 Triage 能力是相关参考，但正确性仍需要实际验证。[S01]

### 7.2 分清四种去重

| 层次 | 例子 | 适合的结果 |
| --- | --- | --- |
| 同一个内容身份 | 相同条目重复导入 | 保留一个条目和多次观察，不重复收费处理 |
| 近重复正文 | 多站转载相同文章 | 合并阅读负担，保留传播与来源关系 |
| 同一事件不同报道 | 同一个发布会的多篇解读 | 形成事件主题，保留新增事实、观点与证据 |
| 与已有知识重复 | 新文章没有带来新方法或条件 | 告诉用户“没有新增理解”，不再新增一份知识文件 |

Feedly 的近重复机制是第二类参考，不应被外推为第四类。[S06] 不同语言、引用同一通稿的文章，也不能因网址不同就成为相互独立的事实验证。

### 7.3 产出“变化”，而不是周期性改写同一篇总结

对已有主题，新材料应带来新增、补充条件、冲突、被纠正或仍未知的状态。用户主要阅读这些变化，需要背景时再展开原主题。

例如新工具取消了免费功能，更新的不是一句新闻，而是相关工具档案的适用条件，以及哪些已保存工作流可能需要复核。团队可以准备修订依据，但不能仅凭公告自动覆盖用户已经验证过的流程。

### 7.4 两类资产一起吸收，不互相冒充

**知识资产**服务人的理解：概念、方法、证据、适用条件、反例和判断。

**能力资产**服务执行：工具、Skill、MCP、流程和经过验证的使用经验。Agent Skills 的规范本身就区分指令、可选脚本、参考资料和资产，并包含环境兼容信息。[S48]

因此“找到一个 Skill”“读取说明”“运行成功”“在本用户场景可复用”是不同阶段。只有经过相应验证的部分才能标为可用，不让网络材料直接变成具有本地执行权限的安装指令。

### 7.5 从知识中提出问题，但不擅自扩大任务

团队可以发现“这项结论缺少反证”“这个方法似乎能解决已有问题”，在当前授权范围内补查。重要的新调查应明确归属和工作范围，不把一批收藏变成无限研究。

对简单条目不必召集全团队。复杂主题由研究员组织证据，CTO 处理能力与环境条件，统筹形成面向 Y 和执行者的说明书。成员之间要相互使用和纠正结果，而不是重复三次摘要。

### 7.6 用过的结果要能回流

说明书被用于脚本、项目准备或工具操作以后，用户的修正与实际结果可以更新对应资产。区别“用户觉得有启发”“工具成功运行”“项目得到正面反馈”，不要用单一点赞或 Agent 自评分混合表示成长。

学习的目标是少重复解释、少重复踩坑，并能在新任务迁移有效方法；不是保证账号增长、开源 Star 增长或自动变现。

## 8. 可考虑的整体组合方案

这里给出的是**方案类别与取舍**，不是重新指定 ytriple 架构。0.1 的运行时、UI 和持久化继续作为当前实现；任何集成由 Codex 选择与验证。

| 组合方向 | 可能借用的方案 | 得到什么 | 代价与限制 | 研究判断 |
| --- | --- | --- | --- | --- |
| 原生工作台＋轻量来源/提取组件 | 原生 Feed、RSSHub 路由、Defuddle；保留 ytriple 团队和 Lib | 统一体验、资产不迁移，来源可逐步加入 | 需承担部分采集适配与内容覆盖核查 | 与当前阶段最一致，值得优先比较，不是要求从零重造所有订阅能力 |
| 原生工作台＋自部署来源服务 | Miniflux 或 FreshRSS；必要时独立采集服务 | 增量订阅、源管理与长期在线能力可复用 | 增加部署、运行状态和同步边界；不能要求所有桌面用户先装服务器 | 与可选自部署/托管方向相符，先明确服务价值 |
| 接入用户已有的收藏/阅读产品 | Readwise API、Karakeep API 等 | 更快接住已有资料和批注，减少迁移 | 权限、导出字段、外部 ID、更新与删除语义需核查 | 适合已有重度用户的入口；不是必需依赖 |
| 完整开源知识产品作为外部能力 | Open Notebook、Khoj、RAGFlow/Dify 等选项 | 可借已有转换、检索、报告与服务能力 | 第二份状态/知识库、重复团队、许可、服务栈成本 | 更适合按明确缺口单独评估，不推荐默认合并整套 |
| 托管采集/研究服务作为补充 | Firecrawl/Jina 或已接入的 Google 研究能力 | 免去部分部署，解决特定复杂来源 | 外发、费用、服务限制和返回证据范围 | 作为明确可替换的补充，不设为本地工作台强制门槛 |

**不是“一套方案胜出，其余都无用”。** 可能借 Inoreader 的产品行为，却不接其服务；借 Karakeep 的 API，却不接它的 AI；使用 Defuddle 处理正文，却由既有团队进行消化。产品借鉴、组件复用、服务接入分开之后，功能才不会越吸收越混乱。

## 10. UI 与完整工作体验：本轮研究的观察点

现有三面板已经完成多次迭代，这份研究不要求重排界面。新增入口应沿用同一个任务、成果和团队关系。

**浏览整理结果时：** 先看到主题结论和相对已有知识的变化；保留来源、覆盖范围、分歧和过滤原因的深入入口。不能让用户在几十个 AI 摘要之间重新做一次人工聚合。

**追问时：** 选中一条结论或来源即可让团队继续；材料与目标自动带入。用户纠正的是这一条知识，还是整个任务方向，影响范围需要清楚，不能把每个追问都当新项目。

**看到工具时：** 同时知道用途、已有替代、缺失条件与验证状态。“了解工具”和“安装执行”是不同动作。需要 Codex 适配时交付清晰说明，不重新制造 IDE。

**产生新证据时：** 保留阅读位置和输入草稿；不把主题正文不断重排，导致用户读到一半内容换掉。变化应有可比较的记录，旧结论保留必要来历。

**来源失败时：** 区分无更新、未检查、部分成功、需要登录和读取失败。以前有效内容仍能查阅，不能把不可达当作用户取消收藏。

**入口增长时：** 一个平台、一个扩展或一个服务可以增加，但用户不应重新学习一套收藏—摘要—保存流程。吸收范围和产出用途应保持一致。

上述为产品研究判断；不预设按钮文案、页面数量、组件或事件协议。

## 11. 信息源订阅服务怎样提供真实价值

### 11.1 不止维护一张源列表

可研究的服务价值有三个层次：

**供给层：** 维护来源发现、适配、存活状态、基础内容取得与变化记录。

**消化层：** 按用户指定主题、目标和已有积累形成不同的知识更新，减少重复、不遗漏关键反证。

**资产维护层：** 持续核对已采用的方法和工具条件，准备修订材料，让过去产生的说明书不静默过期。

这不是已经确定的收费套餐。其价值需要通过真实用户节省的处理负担、知识复用和成果质量来验证，而非仅看推送打开率。

### 11.2 公共与个人部分分开考虑

**研究判断：** 公共页面获取、格式清理和内容身份识别可以共享基础处理；个人相关性、私人收藏和本地资产的对照，可以本地完成或在用户授权范围内托管。不能把不同用户的判断与私有资料混成公共知识。

同一公共条目可以有不同解释：对 Y 是一个内容选题，对另一用户是部署风险；但两个用户不必重复承担完全相同的基础采集。共享计算不代表获得转载整篇文章、视频或原作者材料的权利。

在应用前台运行的首版与服务器持续在线之间，状态要真实。使用现成模型/研究服务也不是“自行部署了模型”，第三方访问条件仍存在。

### 11.3 服务需要有退出能力

用户应能带走关注范围、个人知识、说明书、来源关系与必要历史，继续使用自部署服务或本地工具。源提供方更换不应该使已消化资产失去意义。

本轮未比较实际运营费用，不给出订阅价格或毛利结论。成本至少受更新频率、浏览器与媒体处理、全文保存、模型使用和维护人力影响；具体数量需真实样本测量。

## 13. 对当前 ytriple 的研究收敛

**本轮不是建议换技术栈。** 当前阶段已经有真实团队、资料与成果工具、Lib 收藏和跨任务复用，研究应帮助这些能力接住更真实的输入，而不是安装另一个全功能系统后把工作分成两套。

本轮最值得吸收的，不是某个单独界面，而是四种成熟行为：

1. **由资料集合发起工作。** 用户给一批收藏或一个主题，系统形成可核查的处理结果，减少逐条指挥。
2. **引用与知识修订相连。** 新内容必须与已有积累比较；总结可回原文，冲突可被修正。
3. **能力候选与实际可用分开。** 工具信息进入 Lib 不是终点，能否用于说明书和实际目标才决定价值。
4. **产出后继续复用。** 阅读后的知识和已验证方法能够进入其他任务，并接收实际反馈。

相应地，不值得现在照搬的是：所有平台的大而全覆盖、无限源目录、另一个独立收藏管理器、复杂流程搭建界面、重造 Agent 底层，以及尚无真实用途的订阅后台。

### 13.1 几种完整场景可以用来检验研究是否有用

以下是产品判断样例，不是测试脚本或开发排期：

| 场景 | 有价值的结果 | 不能算完成的情况 |
| --- | --- | --- |
| 一批积压文章/视频/工具 | 主题化理解、实际覆盖说明、筛选理由，并保留回原文入口 | 只取得收藏列表；每条标题生成一段泛泛摘要 |
| 关注来源出现新变化 | 对既有知识/工具条件的明确增量与证据 | 每天重新生成同一篇综述；重试造成重复条目 |
| 发现可用工具 | 结合实际环境的说明、候选状态与可验证使用方法 | 原样转载 README；下载即标“已掌握” |
| 换任务使用已有 Lib | 找到并使用相关资产，指出不适用或过时部分 | 仍由用户逐个找文件、复制全部背景 |
| 说明书实际使用后 | 用户修正和实际执行证据能回到正确资产 | 文件生成就宣布项目成功；仅用点赞量表示成长 |
| 来源或服务失效 | 不丢既有资产，明确缺口与实际更新范围 | 显示一切正常，或把未抓到当成删除 |

### 13.2 尚未得到证明的部分

没有证明任何一个候选能完整导入用户所有平台历史；没有验证音视频转录/多模态在真实材料中的完整性；没有做候选组件的对比基准或端到端 UI 实测；没有验证不同模型对批量淘汰和知识冲突的准确性；没有审查全部依赖、具体商业许可或托管服务经济性。

这些限制不妨碍产品研究成立，但禁止把本报告中的“有能力可参考”写成“已经接入并验证”。对账号与平台而言，当前仓库已有的样本证据与本次外部文档证据也要分开。

**总判断：以 ytriple 自己的团队和本地资产为中心，吸收成熟产品的处理方式，并让来源/解析能力可替换。信息源层负责供给，团队负责理解与说明书，Lib 负责积累与复用，真实使用负责判断价值。**

# ytriple 产品定义

版本：2026-09-13 · 个人开发者与个人创作者版

本文按本轮已确认方向完整重建，是当前唯一产品定义，不再作为按时间追加的讨论日志。保留 `docs/讨论总结.md` 路径以兼容本机项目登记和现有链接；旧正文被本版替换，只在 Git 历史中保留。本文定义目标、功能行为与体验底线，不指定技术栈、接口、表结构、组件或开发排期。

已有 0.1 新底座继续利用，不重做已经完成的团队、工作台和本地文档能力。本文中的目标能力不等于已经实现；实现和实测范围由当前代码及 Codex 维护的 [开发计划](开发计划.md) 说明。旧计划、历史研究中与本版冲突的产品安排不再有效，不能按旧范围继续扩张或缩减产品。

## 1. 服务谁，解决什么问题

**目标用户并列为个人开发者、个人自媒体创作者。**“个人”是本人主导目标、判断和交付，不按粉丝数、收入或是否偶尔外包划分。不把企业、工作室、MCN、代运营和多级审批作为当前设计中心，也不要求创作者成为程序员才能使用。

> ytriple 是个人的 AI 工作台。Y 与一支能够真正协作、按需调用能力的 AI 团队，共同吸收信息与方法，沉淀本地资产，形成给人、工具和 Agent 使用的有效说明书，并通过真实使用与反馈持续成长。

Y 代表用户，Triple 代表能力放大，不代表固定三个调用或三倍效率保证。多 Agent 协作是贯穿所有工作的一套底层能力；简单任务可以只由一个成员处理，不为体现团队而强制全员开会。

| 用户 | 最重要的工作问题 | ytriple 承担的责任 |
| --- | --- | --- |
| 个人开发者 | 需求与技术资料难以消化，交给 Coding Agent 容易遗漏背景，项目变化和用户反馈难以持续理解 | 研究与取舍、项目初始化、状态理解、交接说明与指定文档反馈，减少重复解释和返工 |
| 个人创作者 | 收藏来不及看，选题与表达需要支持，制作交接和作品复盘容易中断 | 频道理解、选题研究、脚本与制作说明、发布准备、作品反馈与方法积累 |

共同价值不是生成更多文件，而是更清楚的判断、更可靠的交接、更少的重复劳动和可复用的经验。少量代表资料和一个目标就应足以开始，不以完整个人画像、知识目录或 Agent 配置为前提。软件与媒体能力都保留，不把一类用户降成附属场景。

## 2. 稳定主线与长期思想

**共同吸收 → 本地资产 → 协作产出说明书 → 人与工具使用 → 真实反馈 → Y 与团队成长。**

功能是这条主线的入口，不是相互独立的应用。用户可以直接研究、写作或提出临时问题，不要求每次创建项目或走完整流程。普通阅读本身也是完整使用，不强迫每条内容变成任务。

从 0x 保留的核心在本版中直接表达，不依赖再去读取旧项目：

| 长期思想 | 产品含义 |
| --- | --- |
| Personal State | 根据获准资料理解当前目标、项目阶段和用户已确认判断；系统先准备可核查的理解，用户修正，不反复填表 |
| Intelligence | 对外部变化与已有资料去噪、关联、核查和解释，不用新闻数量与摘要篇幅代替理解 |
| Capabilities | 围绕目标组织成员、Skills、模型、MCP、工具与工作流，不让某个提供商定义整个产品 |
| Continuity | 换成员、换模型、隔天回来或转交专业工具，仍能恢复有效背景、成果与决策原因 |
| Learning | 保留用户采纳的修正、实际用途和验证条件，改善相似工作；不把聊天存档或 Agent 自评等同于学习 |

Y 的成长包括知识、思路、表达与判断能力；团队的成长包括可复用知识、方法、Skills 和工具使用经验。成长首先是资产和做事方法的改善，不默认训练模型、全天记录电脑或无限保存私有资料。

Local-first 表示用户掌握自己的资料、资产和成果，不等于所有模型在本地运行。AI-first 表示 AI 默认承担理解与协作，不是给列表旁边加聊天框。模型与 Agent 可替换，但不承诺所有提供商的工具、文件和研究能力完全等价。

## 3. 客户端与服务器

### 3.1 客户端：三个核心功能，共享一套工作台

| 核心入口 | 对象与职责 | 常见操作与结果 |
| --- | --- | --- |
| 雷达 | 外部议题、个人来源、平台收藏及已经整理的解读 | 阅读、添加来源、消化收藏、查证据、交给团队、关联项目或资产 |
| 项目 | 软件项目、媒体项目、具体工作与交付物 | 新建或导入项目、查看状态、开始研究、形成说明书、交接、登记结果与复盘 |
| 资产 / Lib | 资料、知识、说明书、Skills、工具和工作流 | 查找、关联、调用、修订、验证、停用、导出和恢复 |

团队工作台是这三个入口的共同工作表面，不是第四套孤立聊天产品。例行工作、待我处理、交付日历属于共同支持能力，不各自扩成独立任务管理或信息门户。设置管理连接、团队能力、规则路径与账户，不成为日常使用主线。

### 3.2 服务器：三个服务方向

| 服务 | 管理什么 | 对用户的交付 |
| --- | --- | --- |
| 信息服务 | 信息源与主题、取得内容的状态、筛选整理、解读更新和投递 | 持续、经过消化的信息供给；可独立服务于 ytriple 及其他获准客户端 |
| AI 能力服务 | 模型与专项能力接入、调用路由、能力可用性、用量和权益；承载适合远端运行的委托任务 | 订阅后无需配置各厂商 API；获得实际可用的推理、研究及托管任务能力 |
| 用户服务 | 登录与设备、订阅、权限、用量与数据控制 | 可理解的服务状态、使用范围与退出方式，不扩成企业组织管理 |

例行任务的远端运行是以上服务的支撑能力，不另建第四个产品中心。服务器提供模型调用，不等于自动接管客户端的团队、项目和本地工具；托管一项任务也不等于上传整个工作环境。

客户端支持使用官方服务、自部署相关服务或自带 API。基础模型接入保持 OpenAI 兼容格式，并保留 Google/Gemini 原生能力，尤其专项研究；不为了统一格式丢掉有效能力，也不全面适配所有厂商。Google 等外部研究服务是团队可调用的能力，不替代常驻研究员。

开源与可自部署方向保留，具体许可证、套餐和价格未定。本地使用不以开通官方账号或订阅为前提；没有可用模型时如实说明 AI 能力限制，不假装离线推理。订阅到期不锁住已有本地文件、资产和说明书。用户可取消授权、导出与清理数据；公共内容处理和个人上下文分开，资料不默认进入公共池或用于其他用户。

## 4. 说明书：围绕使用，而不是围绕文件数量

“说明书”是内部统一的产出概念，指接收方可用的目标、依据、方法、条件与直接结果，不是狭义手册，也不要求面向用户宣传成文档生成器。

| 接收方 | 典型交付 |
| --- | --- |
| Y / 人 | 研究结论、取舍依据、学习说明、脚本、发布文案、整理后的文档和实际结果 |
| 工具 / Agent / 专业执行者 | 目标与约束、制作要求、工具用法、Skill、工作流、交接材料、配置说明或架构思路 |

两者服务同一个目标，可由同一份材料提供不同视图，不强制生成两份重复文件。简单任务直接给结果；复杂任务才展开相应证据与条件。MD 是主要文字交付形式，保留常规文档导入、修订以及图片/演示成果方向；具体支持格式、内容理解深度与真实导出分别说明，不冒充完整办公或剪辑软件。

在成果旁应看得到：所属目标和项目、给谁使用、当前版本、实际依据、尚缺条件、完成标准，以及交接或使用证据。草案、已确认、可交接、已交接、已使用、已验证、待修订是不同含义，不要求每份文件机械经历全部状态。

复杂交付提供“检查是否准备好”：核对依据、缺失输入、要求冲突和接收方可能误解之处。可以让没有参与前面讨论的成员或子 Agent 只依据交接材料复述目标和条件，暴露歧义；这种检查不证明代码正确、内容必然有效或已经合规。

交接可通过可读取文件、复制说明、导出材料包或实际接入的工具完成。记录版本和接收对象；只有有接收或执行证据时才推进相应状态。没有接收回执时不能把打开工具表示为工具已完成工作。

## 5. 多 Agent 工作台与 Skill 能力

### 5.1 两种默认组合，同一套协作能力

| 场景 | 默认责任组合 | 工作重点 |
| --- | --- | --- |
| 软件项目 | 统筹、CTO、研究员 | 需求与方案判断、资料核查、项目准备、状态理解和交接 |
| 媒体项目 | 主编/统筹、研究员、内容编辑 | 频道与选题、事实核查、原创表达、制作说明和复盘 |

这是可调整的默认配置，不是分别开发两套引擎。用户可以直接找一个成员，也可以把目标交给团队。媒体工作需要技术帮助时再调用 CTO；不把 CTO 永久包装成内容专家。

成员要有稳定责任、必要上下文与实际能力，能委派、追问、使用彼此成果、依据新证据修正判断。常驻表示身份和工作连续，不表示一直运行。专项子 Agent 可以按需扩展，结果回到负责成员；子任务增加不自动扩大权限，也不让用户管理更多窗口。

多人赞同不等于事实正确。展示有效贡献、依据和未解决分歧，不展示伪造的团队对话、假进度或隐藏推理全文。只在任务有价值时协作，已有成果可复用时不重复调查，不以调用数量证明放大效应。

### 5.2 工作台里的实际交互

| 位置/情境 | 用户操作与应有行为 |
| --- | --- |
| 开始一项工作 | 从目标、当前资料、议题、选题或项目状态发起；带入所属对象、选定材料和有效版本，不要求重贴背景 |
| 决策与交流 | 向团队或选定成员提问，添加材料或指定 Skill；先读懂结论、依据和取舍，确实需要决定的事项再交给 Y |
| 协作过程 | 默认看到负责人、关键变化、正在用的能力及受阻事项；可展开成员、子任务、工具结果和来源，不是多个无限滚动聊天室 |
| 成果工作区 | 阅读或编辑同一份说明书，对选中段落/证据提出问题、修订、检查或交接；与当前目标及版本关联 |
| 修改方向 | 区分解释性追问、局部修订与全局目标改变；受影响的工作更新，旧目标迟到结果不覆盖当前结果 |
| 切换与接续 | 保留草稿、阅读位置、选中材料和成果；重开后说明实际运行/中断状态，不以最后一条消息充当实时状态 |

沿用已经打磨的同窗口决策、过程资料、成果关系。新功能不应夺取滚动焦点、重排正在阅读的内容、丢失输入或让重复点击产生重复工作。团队可视化服务用户理解与干预，不为显示底层拓扑而要求固定窗口数。

### 5.3 Skill 的产品生命周期

身份回答“谁负责”，Skill 提供可复用的知识与做事方法，工具/MCP 提供实际数据与动作通路，工作流组织这些能力。它们不是同一对象，也不等于一段人设 Prompt。

| 入口 | 用户与团队可以做什么 | 可检查的结果 |
| --- | --- | --- |
| 资产中的 Skills | 使用内置能力、导入可信本地包或链接，查看来源、版本、依赖、用途和使用证据；启用、停用、编辑自己的副本 | 已发现、可加载、缺依赖、待验证、已验证或停用的状态清楚，不把安装等同于掌握 |
| 成员能力设置 | 配置默认可用范围与能力组合；无需把所有 Skill 全文永久塞入角色提示词 | 该成员本次可以用什么、哪些权限尚未具备 |
| 当前工作 | 用户随时指定“使用 Skill”，团队也可按任务自动选择；在适当边界接入新能力，不悄悄改变运行中的授权 | 显示实际加载的版本、作用对象、相关工具结果与形成的成果；纯方法调用不伪造执行日志 |
| 沉淀可复用方法 | 从一次有效工作提炼 Skill/工作流草案，带上条件、样例和已采纳修正；试用后再确认 | 候选与可靠能力分开，用户可比较、撤回或保留稳定版本 |

默认提供少量能完成实际工作的场景能力，如选题评估、脚本核查、制作交接、需求澄清、项目反馈和资料消化。允许高级用户扩展，不先建设庞大商店，不让普通用户先拼插件才能工作。

方法型 Skill 可以用于研究和写作；涉及脚本、安装、付费或外部写入时仍受授权和依赖条件约束。Skill 的声明不具有授予权限的效力。联网资料和新工具也不能覆盖本机 Policy。例行工作采用已确认的方法与版本；更新影响结果或权限时显式审视，不悄悄升级自动任务。

## 6. 雷达：栏目式理解与个人信息消化

雷达不是普通新闻聚合，也不是仅供任务调用的素材列表。它像一个有编辑判断的分析栏目：围绕重要变化整合、解释和持续跟进，说明当前认识、关键依据、限制以及什么变化会改变判断。阅读本身可获得价值，不需要先与 AI 聊天。

### 6.1 入口、操作、结果

| 场景 | 操作 | 结果 |
| --- | --- | --- |
| 日常打开 | 阅读关注方向中的短解读，进入统一详情 | 主页就有新增理解；详情连贯表达背景、证据和不确定性，不靠悬念按钮或加长摘要 |
| 选择内容供给 | 使用订阅服务、添加“我的来源”、接入“平台与收藏” | 三类入口进入同一消化体验；个人来源不以购买官方信息服务为前提 |
| 导入积压收藏 | 选择一批或一个范围并说明目的 | 团队筛选、主题归纳，与已有 Lib 比较；展示保留/过滤原因和实际读取范围 |
| 深入与复用 | 查原文、追问一条判断、关联项目、创建选题或吸收资产 | 当前材料与版本随工作带入，不再由用户转述与拼接 |
| 跟进同一议题 | 查看新证据与修订，纠正判断或调整关注 | 更新原有理解，不每天重写相似报告，不把同源转载当独立证据 |

来源可以是官方服务的内容、公开网址/RSS、用户导入材料，以及通过实际获准的 API/浏览器辅助取得的平台收藏。继续保留知乎、抖音、GitHub、X 等来源方向，但不写成已全部接通；用户后续提供的来源共用相同范围与状态表达。

新闻、工具、文章与视频是材料类型，不各建一个孤立产品。标题、摘要、完整文字、字幕和画面理解分别声明覆盖；无法读取不等于没有价值。过滤默认只影响主要阅读结果，可解释、可纠正，不擅自删除原平台收藏。

### 6.2 个性化与工具吸收

判断相关性要使用用户明确目标、项目与获准资产，不假装知道用户已掌握什么。内容可形成新增知识、补充条件、冲突或待核查问题，不只增加标签和文件数。团队可以在授权范围内批量整理，重要判断更新和安装执行另行确认。

工具发现先形成用途、依赖、已有替代与验证状态；经过实际使用才形成可靠工作流。公共材料整理与个性化判断分开，私有内容不进入公共内容池。

原来科技、AI、金融、股票等关键词可作为初始源包或编辑验证范围，不再代表所有目标用户的固定兴趣。用户/订阅服务是正式产品方向，但不要求先做复杂画像或推荐训练才有可用内容。金融内容仍区分事实、分析与情景，不提供收益保证或把模拟当实际证据。

可选情景推演保留为议题内的深层能力，可研究付费，不是基础阅读门槛。事实、假设、模拟结果与现实反馈分开；基础解读的证据、条件和限制不能为了收费被移走。它不阻塞当前核心功能。

## 7. 项目：软件与媒体的具体工作

### 7.1 共同基础

项目提供目标、正式资料归属、当前状态、交付物和结果反馈。临时工作不强制创建项目。项目状态注明来自文件/接口、用户登记还是待验证推断；外部工具未回传时不猜测完成。

每项重要工作保留简短的目标与取舍：服务谁、预期价值、已有依据、关键条件及明确不做什么。可从资料中得出的由团队先准备，不变成长表。AI 提出反证和限制，不用主观评分伪装商业成功概率。

### 7.2 软件项目

| 位置 | 用户操作 | 明确交付与边界 |
| --- | --- | --- |
| 新建/导入 | 给出目标、讨论材料或既有目录，选择软件项目 | 读取本机规则；缺失体系时先建立规范底座；建立身份、登记、必要文档和适用的 Git/worktree；导入不擅自搬迁已有目录 |
| 状态与资料 | 查看项目/分支/文件与真实变化，对具体内容询问团队 | 解释目标进展、变化与风险；只读观察不等于执行开发 |
| 需求与交接 | 整理研究、目标、约束、条件和完成含义，进行就绪检查 | 形成可交给 Codex 等工具的材料，不把当前工作台重做为 IDE 或 Coding Agent |
| 开发反馈 | 对发现的问题讨论并写入指定反馈位置 | 保留版本与依据；不直接改代码、配置或正在维护的正式开发方案，不擅自宣称 Codex 已采纳 |
| 发布与回验 | 登记版本或获准读取 Release、Issues、讨论和执行证据 | 将实际结果与原目标对照，形成待采纳反馈；不是复制 CI/CD、部署或客服平台 |

ytriple 可准备目标、方案思路与执行者说明，不禁止有用的技术讨论；具体工程设计、任务拆解、代码和验证仍由 Codex 等专业工具完成。普通研究文档可编辑，开发项目内的正式变更遵循指定交接边界。

### 7.3 媒体项目

媒体项目代表频道或栏目；作品承接一次具体内容生产。同一作品的不同平台、语言和版本相互关联，不各建孤立项目。短文案可以直接完成，不强制经过所有环节。

| 位置 | 用户操作 | 团队和 Skill 形成的结果 |
| --- | --- | --- |
| 频道与栏目 | 添加账号、代表作品、受众、制作条件；修正团队整理的理解 | 频道/栏目说明、有效表达标准，供后续选题与作品复用，不模仿他人身份 |
| 选题 | 从雷达、收藏、观众问题或手动想法创建；比较候选 | 受众价值、原创角度、证据缺口、制作条件和取舍，保留待验证假设，不承诺爆款 |
| 研究与脚本 | 关联资料，补充研究，生成/修订文章或脚本；对段落提出意见 | 有依据的原创表达；编辑与研究员互相核查，不把换写对标内容当原创 |
| 制作说明 | 选择作品形式、已有工具与可用素材 | 所需镜头、素材、录制说明、生成要求和适用工作流；不默认一次生成全套附件 |
| 发布准备 | 选择平台与语言，检查标题与内容承诺、材料完整性 | 标题、封面方案、简介、字幕等适用材料；实际设计、剪辑和发布留在相应工具 |
| 发布与复盘 | 登记发布链接或时间，导入/授权取得成品、数据与评论 | 将结果与创作假设对照，形成修正依据；数据不足保留解释候选，不制造因果 |

账号入口区分自有与对标。自有数据通过实际授权取得，对标只使用公开或另行授权内容。YouTube、TikTok、X、抖音为首批关注方向，平台覆盖渐进；公开内容更新可进雷达，经营数据回到作品复盘。用户可先提供报告与反馈，不等待全部平台接通。未知素材授权明确标注，不自动标为可用。

不默认代登录、互动、批量发帖、直播带货、投放或商务管理。创作者保持自己的判断和风格，团队不是批量内容农场。

## 8. 资产管理与本机规则

Lib 统一组织知识、参考资料、说明书和能力，不要求全部物理迁移到一个目录。项目权威正文跟随项目，跨项目知识与资源按本机 Policy 归属；引用、观察快照与独立可复用副本要分清，不制造相互竞争的正式版本。

| 操作 | 实际效果 |
| --- | --- |
| 搜索/让团队查找 | 找到相关资产及其出处、条件和版本；团队在获准范围内主动复用，不要求用户逐个找文件 |
| 吸收/关联 | 识别新增、重复、补充或冲突，关联项目与用途；保留需要核查的材料 |
| 修订/验证 | 对已有资产形成可比较的修订；记录真实用途和结果，未知修改保留，未验证工作流仍是草案 |
| 调用/停用 | 能力用于当前工作或例行工作；停用后不再自动调用，已有使用记录保留 |
| 导出/备份/恢复 | 带走正文、来源、用途与必要版本关系；恢复不静默覆盖同名资产，不把同步功能作为前提 |

初始化遵守用户拥有的 Policy：已有规则先识别和保留；新用户按自己的主目录与配置路径建立对应体系，不硬编码开发者机器、不复制私人账号或项目。残缺与冲突不能当空目录重建。规则更新应可比较，应用升级不自动覆盖用户定制。

用户的修正只作用于实际范围：一条作品的改法不自动变成全频道标准，一次失败不直接停用所有工作流。是否采纳为长期方法要有依据与用户决定。

## 9. 例行工作：把有效委托变成可持续处理

**例行工作属于正式产品能力，不只是日历提醒或定时发送 Prompt。**它复用既有团队、资料范围、Skill、说明书和结果归属。默认以读取、分析、草稿和待确认修订为自动化范围，不自动授予发布、删资料、改代码或安装权限。

### 9.1 入口与管理

用户可从已经有效完成的工作点击“设为例行工作”，或选择开发者/创作者的内置模板。系统继承目标和方法，用户主要确认触发条件、运行位置、资料/动作授权、交付位置与通知策略；不要求写 cron、配置多节点流程或每次重写完整 Prompt。

任务归属原项目、主题或资产。每次运行有历史，但不必产生新聊天或重复全文。管理入口显示上次检查与结果、下次预计触发、实际运行位置、所用能力、用量、失败原因，并提供立即运行、暂停、修改和停止。修改运行中任务时，说明影响本次还是以后，不默默改变正在执行的权限。

| 例行工作 | 触发示例 | 实际结果 |
| --- | --- | --- |
| 新增收藏消化 | 每日或新增一批材料 | 与已处理内容及 Lib 对照后的增量理解，保留真实覆盖 |
| 项目变化简报 | 定期或获准来源的重要变化 | 目标进展、相关反馈、阻碍与待核实点，不复述全部提交 |
| 栏目准备 | 每周或计划创作前 | 结合频道、既有作品和新资料的选题/材料准备，最终取舍留给用户 |
| 发布后复盘 | 作品或软件版本实际发布若干时间后 | 对应版本/作品的真实数据和反馈，回到原假设与说明书 |
| 资产有效性检查 | 周期性或工具/证据出现相关变化 | 哪些知识、Skill 或工作流条件可能失效，以及修订依据，不覆盖稳定资产 |

支持时间、事件/变化、实际节点后的相对时间三种语义。用户本地时区、下次实际运行时间、时区变化后的影响应清楚。节点尚未发生不提前开始复盘；事件来源未接通不显示实时触发可用；轮询发现变化与实时事件接收要如实说明。

### 9.2 运行位置与可靠性

| 位置 | 能做什么 | 必须说明的限制 |
| --- | --- | --- |
| 客户端正在运行 | 按授权使用本地资料、工具及可接入服务 | 电脑休眠、程序退出或网络不可用时可能等待；不能靠界面定时器冒充永久运行 |
| 本机后台执行 | 在用户明确启用且实际实现的本机运行环境中处理任务 | 属于可扩展的实现选择，不等于当前已经存在；仍依赖机器在线和权限 |
| 自部署/官方服务器 | 对实际有权取得的内容和能力持续处理 | 不自动读取本地文件、浏览器登录态或未上传素材；混合任务缺本地能力时显式等待，不伪造完成 |

旧版“全部本机任务只限前台、服务器只做雷达”的范围不再作为长期产品限制。本版允许例行与托管任务，但不因此声称后台执行已上线，也不把已有手动任务默认转换为后台任务。具体实现范围由工程证据说明。

没有新材料就记录检查结果，不强行重复召集团队。中断后合并需要补做的工作，不机械重放所有错过时点。重复事件、本机与服务器同时恢复不能重复产出或执行；未知结果先核对，不能一律重试。提供用量、可选额度/次数限制、停止与失败暂停；自用未设总额度不再是所有用户的默认承诺。

版本与授权变化需要清楚：Skill 升级、资料范围扩大或外部动作变化不能悄悄进入长期任务。已有批准范围内的常规处理不反复弹窗，越界事项进入待确认。外部服务取消尚未确认时保留真实状态。

## 10. 支持个人用户的轻量工作管理

### 10.1 待我处理

统一呈现少量需要判断的事项、已准备好的成果和真实受阻的工作。每项直接关联原项目/任务/说明书，用户可查看依据、继续讨论、采纳、拒绝或暂缓。它是聚合视图，不建立跨项目竞争的反馈正文，也不是每次模型响应都生成通知。

雷达回答外界出现什么值得理解的变化；待我处理回答自己的工作哪里需要注意。通知可汇总、静音和调整重要程度，源失败与重要风险不能被伪装成无更新。未通知不等于任务未运行，推送到客户端也不等于通知轰炸。

### 10.2 用户和观众反馈

在软件项目或作品中选择一批 Issues、评论、讨论、数据报告或手动记录，执行“整理为问题与机会”。团队合并相似反馈，保留原话、来源、时间与覆盖，区分问题、需求、误解和少数意见，并关联已有功能、作品或说明书。

用户采纳后才形成正式目标或方法修订。低样本、公开指标与后台数据分开；不把一次点赞、播放或 Star 增长当因果证明，不把模拟角色意见当现实反馈。平台接入逐步增加，手动导入的真实资料也可工作。

### 10.3 交付节奏与就绪检查

项目提供轻量交付列表或日历：开发者看版本/交接，创作者看作品。记录目标日期、当前说明书、缺失输入与外部执行状态；未完成内容可以计划，但计划时间不是实际发布时间。

“检查是否准备好”具体检查材料、依据、要求一致性和交接歧义，并留下检查结论及未解决问题。日期改变时，相关提醒/相对任务的影响可见。这里不建设甘特图、工时、客户审批或团队考核系统。

### 10.4 轻量进入与带走

浏览器保存链接/选中文本、分享内容、导入已有文件和反馈，都可以归到项目或临时工作。先接实际可用入口，移动分享可逐步增加，不先重做完整移动端工作台。保留来源和用户附言，避免反复复制粘贴。

导出说明书和能力材料应让现有工具能够读取。备份/恢复保留必要关联，不上传或导出平台登录凭据；私有项目资料不因迁移方便自动外发。基础可用性不能依赖复制开发者本机环境。

## 11. 用真实工作判断产品是否成立

下列是产品行为与交付依据，不是固定测试脚本或任务排期。工程实现、模型调用和真实用户价值分别验证；不以页面存在、工具返回或测试数量代表全链路完成。

| 工作场景 | 可以确认的价值 | 不能算完成 |
| --- | --- | --- |
| 新用户开始 | 个人开发者或创作者用目标和少量材料获得可用结果，能理解所需授权 | 必须先配置角色图、完整目录、全部 API 或迁移全部资料 |
| 收藏与雷达 | 实际内容被理解，主题解读有新增信息、证据和可纠正筛选；缺失明确 | 把标题当全文、逐条等量摘要、模拟数据和热榜重复转发 |
| 团队与 Skill | 成员实际使用方法或工具，相互补证据/修正结果，用户不用转述 | 角色换名、三份答案拼接、已启用标签冒充能力运行 |
| 软件交接 | 规范项目底座、清楚说明与指定反馈可交给 Codex；结果有独立证据 | 写文件即宣布开发完成，直接改开发项目或覆盖未知修改 |
| 媒体作品 | 频道背景进入选题与脚本，制作材料可以交给实际工具；反馈回到同一作品 | 套模板批量文案、复制对标内容、保证爆款或只做数据图表 |
| 跨任务复用 | 重开/换工作仍能找到并采用相关资产，指出过期和不适用部分 | 仍需用户找齐文件、搬运背景，未采纳意见变成全局规则 |
| 例行任务 | 按实际触发和权限处理增量，回到原对象；离线、失败与用量清楚 | 模型无新输入反复生成、重复执行、本地离线冒充远端有权限 |
| 说明书实际使用 | 接收方理解目标，使用结果和修正能回到正确版本与资产 | 文件生成等同成功；预演替代真实执行与效果 |
| 体验连续 | 阅读、输入、成果和目标在切换/停止/恢复时不丢失 | 依赖用户反复发现草稿、焦点、重复提交和真假状态问题 |

用户负责价值判断和重要取舍，不应成为唯一的测试员。产品说明把行为和“不算完成”写清，Codex 负责具体设计与验证，不需要网页 AI 为此另建工程合同。

## 12. 七层成熟度与自动化演进

沿用项目已经采纳的七层语义；这是成熟度坐标，不是七个页面或七期排期，更不是外部视频中“自动赚钱”等说法的保证。

| 层 | 项目语义 | 在本产品中的价值 |
| --- | --- | --- |
| L1 | Ask / Find | 找到资料并提出有效问题 |
| L2 | Act | 在授权范围内完成具体工作，形成可用结果 |
| L3 | Persistent Context | 保存目标、背景、修正，跨成员和时间继续 |
| L4 | Structured State | 组织项目、知识、能力、成果与验证状态 |
| L5 | Indexed Retrieval | 为当前工作主动找回相关积累 |
| L6 | Semantic & Relational Intelligence | 理解关系、矛盾和缺口，把方法迁移到新目标 |
| L7 | Composable Production + Learning | 组合可靠能力持续产出，通过结果改进说明书、资产与例行工作 |

“高度自动化”来自经过验证的方法、明确的授权和真实反馈，不来自更多 Agent 或无限自循环。新的目标、重要取舍和无法验证的判断仍由 Y 与团队共同处理。成长看说明书用途、判断改善、复用和项目实际反馈，不看文档数、粉丝数或 Agent 自评分。

## 13. 范围与文档分工

**当前产品范围已确认：** 两类个人用户；客户端多 Agent 与 Skill；雷达、软件/媒体项目、资产；说明书与实际反馈；例行工作、待处理视图、反馈整理、轻量交付检查和可进可出的资料；服务器信息、AI 能力和用户服务。

范围完整不等于一次实现全部来源、模型和平台。优先把实际用户工作做通，继续利用 0.1；不能以“先做底座”为由只交付新的配置页，也不能因实现一条路径就删除长期主线。具体增量和工程计划由 Codex 维护。

**暂不建设：** 企业/MCN/客户审批、万能可视化流程编辑器、全平台代运营、自动批量发布互动、无人值守改代码、完整 IDE/剪辑/设计软件、庞大工具市场与强制云迁移。可选情景推演、更广平台覆盖和深层个性化不阻塞当前工作。套餐、额度数值、移动端形态和具体调度/托管技术仍未锁定。

[产品调研](产品调研.md) 是本版能力证据与候选取舍，不是第二份需求。`docs/参考/` 中旧专题仅作为注明时间的研究/验证材料，不能恢复已被本版替换的产品边界。旧两份主文档不并列保存、不继续追加；历史仅查 Git。

用户决定方向、取舍与授权；网页 ChatGPT 维护产品定义、能力研究和方案审视；Codex 维护工程方案、实现、计划和验证。更改本版时围绕受影响的稳定章节，不重回“一次聊天增加一套定义”的方式。

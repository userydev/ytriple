## 2. 定位与边界

> ytriple 是以 Y（用户）为中心的 Local-first Personal AI Workbench：Y 与一支真正协作的 AI 团队共同吸收信息、知识和能力，沉淀本地 Lib 资产，产出给人理解与使用、给 Agent 和工具执行的有效说明书，再通过真实使用和项目反馈促进双方成长。

Y 是用户本人；Triple 是放大器，不表示固定三个 Agent，也不是三倍效率承诺。多 Agent 团队交互是贯穿吸收与产出的底层核心，但产品仍是完整的 AI 工作台，不缩成角色聊天、新闻阅读器、资料柜、PRD 生成器或 Codex 启动器。

全局主线是：**共同吸收 → 消化并积累本地资产 → 协作产出说明书 → 人与工具实际使用 → 项目反馈 → Y 与团队共同成长。**入口和功能围绕这条主线增加，不因新增一个功能就重新定义整个产品，也不要求每项工作走完同一条流程。

ytriple 不接管所有专业工作。它重点处理研究、文档、资料组织、能力吸收、项目初始化和监控；真正的软件开发继续交给 Codex 等本地工具，设计、剪辑等深度生产继续留在专业软件。不替代专业工具不等于只给建议：在自己的能力范围内应交付可使用的结果。AI Forge 可以描述建立项目底座的能力，不另造一个接管电脑的操作系统。

### 核心产出：两类说明书

“说明书”不是狭义手册，而是把目标、依据、方法和判断变成接收方能够使用的成果。

| 接收方 | 价值 | 典型成果 |
| --- | --- | --- |
| Y / 用户 | 帮助理解、学习、判断，提供指导方案或直接结果 | 研究结论、决策依据、指导方案、脚本、整理好的文档 |
| Agent / 工具 / 专业执行者 | 说明怎样达到用户目标、需要什么条件、怎样判断结果 | 任务说明、工具用法、Skill、工作流、架构思路、方法、配置和约束文件 |

两类说明书服务同一个目标，不强制每次生成两套重复文档。小任务可以直接交付结果。有效说明书应能说明目标、依据、方法、适用条件和完成标准；生成、保存、被使用、验证有效是不同状态，不以字数或文件数量证明价值。

给机器的说明书不是另建详细工程指令体系：涉及正在开发的项目，仍按初始化、监控、指定反馈文档的边界协作，具体工程设计与代码修改留给 Codex。

### 共同吸收与成长

Y 吸收思路、思维方法、知识和认知，用更清楚的目标与判断指导团队；团队也应通过证据、不同视角和纠正帮助 Y 成长，而非只迎合用户。

Agent 团队吸收知识、方法和用户修正，也吸收 Skills、工具、MCP、workflow 及实际使用经验。找到工具、写出用法、完成接入和验证有效不是同一件事；候选能力与已验证能力要区分。

双方留下的有用知识、判断、方法、能力和实践证据进入本地 Lib。成长首先体现为判断改善、资产复用、减少重复沟通与错误，不等于默认训练模型、无限保存聊天或自动安装所有工具。

### 从 0x 继承的长期核心

团队回答“谁和用户一起工作、怎样协作”；0x 的思想回答“工作围绕什么积累、为什么会越来越懂用户”。两者需要同时存在，不能用常驻团队替代个人知识、外部情报和工作连续性。

> **Personal State × Intelligence × Capabilities × Continuity × Learning**

| 核心 | 在 ytriple 中的含义 |
| --- | --- |
| Personal State | 理解用户当前的 Goal / Focus、工作领域、项目阶段和已确认判断，为相关性提供依据；不只是角色资料或某次会话历史 |
| Intelligence | 理解外界变化与个人资料，去噪、关联、比较并判断其意义，而不是堆积新闻、文件和数据 |
| Capabilities | 围绕任务组织团队、模型、研究服务、本地工具和外部资源；先看需要什么能力，不让某个工具反过来定义整个产品 |
| Continuity | 跨会话、时间、项目与工具恢复“做到哪里、为什么这样决定、怎样继续”；换成员或模型不丢失用户自己的有效上下文 |
| Learning | 从用户纠正、信息的真实用途和工作结果中改进后续筛选、理解与复用，而不是只根据点击或 Agent 自评判断成功 |

**Local-first** 表示用户掌握自己的 State、Knowledge、Project Context 和历史；**AI-first** 表示 AI 是默认理解与判断层，不是给普通列表再加一个聊天框；**Agent-neutral / Model-neutral** 表示用户的知识、结论和工作历史不依附某个模型或 Agent。当前先支持有限接入范围，不改变这些长期属性。

这里的 Personal State 与 Learning 是面向真实工作的理解与改进，不要求先建立完整个人画像、全天采集或模型训练系统。用户的明确修正和授权仍优先，推断不能悄悄变成规则。

### 三个长期工作锚点

| 锚点 | 用户得到的价值 |
| --- | --- |
| Understand My Work | 从真实来源知道项目与工作状态、变化和风险，并回到正确的专业工具继续 |
| Understand What I Consume | 外部信息、账号变化、收藏和资料进入后，先被理解、压缩、关联和判断，而不是增加阅读负担 |
| Continue Across Time & Tools | 今天的研究、判断与成果在以后仍能找回；在 ytriple、Codex、浏览器和其他工具之间工作，不必反复解释同一背景 |

这三个锚点定义完整产品，不是三个独立页面。当前可以把一条真实工作做深，但不能用该局部重写整个长期目标。

## 3. 核心：稳定的最小 AI 团队

用户面对一支团队，或直接面对其中一个成员；不需要反复解释背景、手动转发成果和协调每个 Agent。当前最小常驻团队为：

| 身份 | 责任 | 需要匹配的能力 |
| --- | --- | --- |
| 统筹 / 工作伙伴 | 承接用户意图，维护当前工作主线，组织成员协作，收敛结论和成果 | 工作上下文、任务协调、成果整合、文档处理 |
| CTO / 产品技术伙伴 | 理解产品与项目，进行产品技术审视，组织项目初始化、状态观察和开发反馈 | 本机 Policy、项目资料与状态读取、受控初始化、指定反馈文档写入；不接管代码开发 |
| Deep Research / 研究员 | 搜集、比较、核查和综合材料，为团队提供证据与研究结论 | 本地检索、Web 研究、来源核查及可接入的外部深度研究服务 |

固定的是身份、职责和协作关系，不是每项任务的参与人数、调用次数、模型或执行顺序。小任务可以直接交由合适成员完成，复杂任务再协作；必要时可以调用专项能力或临时助手，不提前建设庞大的角色配置平台。

“常驻”表示身份稳定、工作可持续，不表示所有成员一直运行或持续消耗模型费用。文档处理是团队共同能力，暂不为每种功能增加一个身份。

### 协作必须真实发生

- 成员围绕同一有效目标工作，能委派、追问、使用彼此的材料和结果，并收敛分歧；不是把同一个问题发给几个身份 Prompt 后拼接答案。
- 用户可以直接与团队或成员交流。换成员不应要求用户重讲项目背景；用户修正方向后，旧目标下的结果不能悄悄混进新结论。
- 共享必要的工作上下文，不默认向所有成员、模型或服务暴露全部项目资料。不同项目的规则与结论不能串用。
- 展示真实贡献、证据、分歧和成果变化，避免多个同质聊天框、预设台词和假进度；不把内部推理全文当作产品成果。

常驻成员可以按需调用子 Agent，完成提取、专项研究、比较和验证，也可以继续扩展必要的子任务；负责成员仍承担核查、整合和交付责任。成员间协作不等于子任务委派。子 Agent 的扩展不应让 Y 管理更多窗口，也不自动扩大资料、工具和执行权限。

问题模糊或超出 Y 当前认知范围时，主要由团队判断、拆解、研究和推进，不要求 Y 先能回答专业问题。团队用简短、易懂的总结说明判断与必要分歧；Y 明确否定或修正时，受影响的任务与成果随之调整。这是对任务内判断的委托，不改变已有资料、工具及外部动作授权边界。

### 交互与底层能力一起成立

团队在日常阅读、资料与其他工作中保持轻量入口；明确交给 ytriple 的研究、知识扩展、头脑风暴或产出任务，则完整显示目标、协作进展、依据、结果与继续交互的入口。从知识点发起扩展时，带入当前材料和有效背景；切去其他工作后，可以通过入口返回任务。

当前交互方向为主窗口支持决策、两个辅助窗口承载详情：主窗口用总结和人话讨论，详细报告、证据、信息图、PPT 或其他成果可在辅助窗口按需查看。三个窗口服务同一项工作，不按三个 Agent 各占一栏。具体窗口组织、展开与切换方式由 Codex 设计。

能理解当前交流对象、按需查看子任务、围绕证据或说明书局部修正、辨认等待与失败、继续上次工作，是核心体验，与底层能力一起实现。

具体交互细节与候选机制见 [团队协作与交互调研](参考/团队协作与交互调研.md)。该文是专项参考，不锁定框架、运行拓扑或 UI 组件。底层扩展能力与用户沟通的简单性应同时保留。

统一的是理解：团队在 Project、Knowledge、Radar、Research 或具体文档中工作时，应理解当前对象与相关上下文，而不是每个入口重新建立一个孤立会话。**System prepares → user corrects**：能从获准来源知道的，先形成可核查的理解，让用户修正，不要求用户重复填报。

## 4. 围绕吸收与产出的主要能力

### 当前真实使用场景

用户提出的六个场景整合为三条相连的工作流，共用团队、资料与成果，不要求建立六套独立功能：

| 工作流 | 覆盖场景 | 用户得到的结果 |
| --- | --- | --- |
| 项目孵化 | 产品雏形与需求讨论、项目初始化；结合头脑风暴与研究 | 规则和必要文档齐全、可由 Codex 接手的项目环境 |
| 信息吸收与学习 | 整理用户指定信息源、推荐产品提供的通用信息源、学习新知识与扩展认知 | 经筛选、归纳和关联的主题理解、知识更新与能力线索 |
| 研究与创意产出 | 深入研究、头脑风暴、创意扩展及知识点深入探索 | 有依据的判断、方案、文档与可视化成果，并可继续讨论和修订 |

### Research、文档与本地 Context

Research 是第一等能力，不是 Radar 的附属按钮；可以从用户问题或外部信号开始，结合本地资料与外部来源，完成搜索、比较、核查、分析和综合，形成 Knowledge / Decision。文档是持续工作的对象，不只是聊天结束后的导出附件：研究报告、讨论总结、决策记录、内容 Brief、脚本等可以继续整理、修订和复用。

文档编辑处理属于第一版，主要通过核心多 Agent 交互完成：用户提出目标或修改意见，成员围绕同一份有效文档开展读取、分析、撰写和审视，形成修订并保存。用户能查看成果与改动、继续提出意见，换成员或重新打开工作台后仍能接续。

文档以 MD 输出为主；输入覆盖 PDF、TXT、MD、JSON、DOC/DOCX 等常规格式，重点是可靠理解内容，不要求首版对所有输入格式做原样排版编辑。输出还包括图片，主要是信息图，以及 PPT 等成果。用户提供的 [HumanLayer show-me](https://github.com/humanlayer/skills/blob/main/plugins/show-me/skills/show-me/SKILL.md) 可作为知识解释、信息图和 HTML 幻灯片的参考；PNG 与原生 PPTX 导出需要另行实现与验证。

产出应利用已有资料、判断和经过验证的能力，缺什么再调查什么；不能每次从空白上下文生成泛泛建议。团队在授权范围内使用工具并核查结果，深度专业执行仍留给对应工具，返回的真实结果再次进入吸收。

吸收入口还包括本地文件与项目材料、用户主动提出的问题、工具使用经验和项目结果，不要求都从雷达开始，也不要求一次建设全部入口。

项目专属资料跟随项目；跨项目知识和可复用 Skill、workflow、模板等按本机规则组织。不为了检索方便复制另一份权威正文，也不要求先搭好庞大知识库才能工作。收藏需要消化，知识需要来源；旧聊天、缓存和模型记忆不能自动成为正式规则。

### Saved / Knowledge / Lib：从保存到理解与复用

**Saved ≠ Knowledge；存在本地 ≠ 已经消化。** Radar、主动收藏、导入和 Research 可以是不同入口，但后续共享知识吸收与复用的语义：

```text
Observe / Save / Import / Research
→ 保留来源
→ 去重 / 聚合
→ 摘要 / 提炼 / 理解
→ 用户判断
→ 分类 / 关联 Goal、Project、Topic
→ 检索 / 综合 / 复用
→ Outcome / Learning
```

一个主题或事件的多篇文章、多个视频和多次研究，可以共同形成持续演进的理解，不要求“一篇内容 = 一条知识”。这不是要求把所有原文搬到中央目录，而是让已有材料能够可靠地找回、关联和复用。

本地 Lib 是知识、能力与成果的统一理解和检索入口，不等于新建一套重复目录。认知资产包括知识、判断依据和方法；能力资产包括工具档案、Skills、MCP 使用资料、工作流与适用条件；结果证据包括说明书、实际成果、用户修正和失败经验。它们遵守本机 Policy 的知识、资源与项目归属。

资产要体现解决什么问题、依据和适用条件、是否验证及后续修正。工具吸收不止保存链接或下载仓库，应形成适合用户的用法，必要时由获授权工具验证；未经验证的流程保留草案身份。实际安装、适配或项目开发由相应授权工具或 Codex 完成，不因“吸收”自动获得执行权。

长期记忆主要围绕产品、工作过程、成果与反馈积累，从反复出现的有效做法中形成可复用资产；不以建立 Y 的个人画像为先决条件。Y 的习惯可以在长期工作中逐步理解，无需先列出完整偏好。未来绑定自媒体账号后的真实表现与反馈，也应帮助团队改进资产和方法。

学习不仅是保存结果，还要知道哪些信息有用、哪些判断被纠正、哪些内容真正进入研究、决策或成果；据此改善后续理解，不把未经采纳的 Agent 观点自动升级为用户知识或全局规则。

### 项目初始化、监控和反馈

项目初始化属于第一版：从在 ytriple 讨论产品雏形、需求与相关问题开始，依据本机 Policy 和授权实际建立项目身份、规则、目录、登记、必要文档和适用的 Git/worktree，形成 Codex 可以接手开发的环境。首阶段重在这些基础完整、结果可核查，不要求初始文档一次性准确完备；文档质量随后续使用与反馈持续提高。

**本机管理体系的识别与建立也是首版必备功能。** 当前机器以 `/Users/Admin/AI` 为规则根目录，项目初始化必须遵循其中的文档与项目管理规则。若本地不存在这套目录，ytriple 先实际创建目录、对应规则和必要登记接口，再完成项目初始化；不能只提示用户手工建立，或仅输出建议文档。已有体系与全新环境都必须完成可交接的项目。

项目能力分清三个边界：

| 阶段 | ytriple 负责 | 不代替什么 |
| --- | --- | --- |
| 初始化 | 根据 Policy 和授权建立项目身份、登记、路径、规则入口、必要文档，以及适用的 Git/worktree 等项目底座 | 不把初始化扩成完整开发平台 |
| 开发期间监控 | 读取项目资料和真实状态，解释进展、变化、风险和待讨论事项 | 不直接改代码、配置或正式产品/开发方案 |
| 用户提出意见 | 整理意见与相关证据，落实到该项目约定的反馈文档 | 不自行将意见改成已采纳方案或已完成修改；回到 Codex 端判断、修改和验证 |

Project 也是连续工作的核心对象：理解目标、阶段、有意义的 Activity、状态新鲜度、blocker / risk、待用户决定事项，以及相关研究、知识、信号和 Outcome / Evidence。软件可看 Git 等证据，内容工作可看脚本、素材、版本和发布，研究工作可看问题、来源与结论；不能把所有项目都缩成 Git 状态或 Codex 会话列表。

反馈应进入指定项目和指定位置，不建立跨项目通用收件箱。写入反馈文档不等于 Codex 已读、已采纳或已执行，状态以实际证据为准。即使只写反馈，也要保留该文件的已有内容与未知修改。

普通研究与文档工作的编辑能力仍保留；上述限制针对正在由 Codex 等工具开发的项目，不能因此把整个工作台变成只读阅读器。

### 本机 Policy

产品必须能接入已有的本地管理规则，也必须能为缺少体系的用户建立对应目录与规则。当前实际入口是 `/Users/Admin/AI/system/system.json`，由它指向 Policy、工作领域、系列、项目登记、知识与资源目录及校验接口；项目初始化以这些当前规则为依据。其他机器默认从当前用户的 `~/AI` 发现或创建体系，支持配置根路径，项目路径继续按本机规则解析。

新建体系包含 `system/`、`knowledge/`、`resources/` 及对应规则、配置、schema、目录清单和必要接口，建立 AI 与 Code 的规则入口；遵循规则与项目登记集中管理、项目正文跟随项目、跨项目知识与资源各归其位的组织方式。新机器使用随产品提供、经过校验的默认规则模板，并生成自身路径和空的个人登记，不能复制当前机器的其他项目、账号或私人资源信息。

已有环境应被识别和尊重；不自动整理整个 Home、不覆盖未知项目修改、不因应用升级覆盖用户规则。规则投影只维护约定区域。规则文件是依据，不等于自然获得写入、联网、上传或付费权限。

目录存在但配置残缺时，区分可补齐的缺项、损坏配置和版本冲突；保留已有有效内容，补齐可确认的缺项并核查结果。完整已有环境、全新环境和残缺环境分别验收，重复运行不产生第二套规则或重复项目登记。

### Radar：持续制作的分析栏目

**雷达不是新闻收集展示，而是一档持续制作的分析栏目：信息源是素材，经过选题、整合与分析的解读才是产品。** 借鉴自媒体栏目的明确定位、编辑取舍、稳定方法与内容质量，不以追热点、制造争议或更新数量为目标，也不因此新增自媒体发布与代运营功能。

编辑主张是：**围绕用户关注的重要变化，连接分散的信息与证据，解释事情如何发展、当前判断为什么成立，以及什么新变化会改变判断。** 不做第十一家转发相同消息的媒体；更长、更好看或引用更多来源不自动形成新增价值。新增理解可以是补足背景、连接线索、澄清分歧、说明证据缺口或修正旧认识，不强求独家观点。

雷达的主要内容对象是值得理解的问题与持续议题，不是单篇文章或装满链接的主题文件夹。**整合、解释、跟进是一套方法，不拆成多个栏目或功能专区。** 普通阅读本身就是完整体验；用户不必聊天、收藏、建立任务或开启推演，才获得基本价值。深度加工集中在明确关注领域的重要问题，底层来源可以多样，表现形式保持少、交互简单。

#### 独立服务与三类来源

**雷达服务器是可独立发展的信息订阅服务，ytriple 是它的首个客户端，不是把整个工作台搬到服务器。** 服务负责集中维护来源、筛选整理和内容交付，长期承接不同用户的订阅；客户端承接栏目阅读、来源选择、纠正与本地理解。服务器可按独立项目或开发单元升级，先明确双方服务边界，使增加来源与内容能力不必反复改造客户端；仓库、分支和接口细节由 Codex 决定。

当前与长期范围分开：开发期先围绕第 6 节的预设关键词形成真实整理供给，不要求先开放用户、收费订阅或完成个性化算法。长期个人订阅仍保留，但不把“订阅服务”入口等同于当前必须上线账号和商业后台。

| 来源入口 | 主要范围 | 产品职责 |
| --- | --- | --- |
| 订阅服务 | 服务器提供的主流媒体、专业或特定网站、公开自媒体账号动态和主题内容，覆盖逐渐增加 | 提供持续、已经整理的信息供给；长期同时支持来源目录与主题订阅 |
| 我的来源 | Y 自定义的网址、RSS 和 ytriple 实际可以读取的其他来源 | 不受服务器目录限制，也能获得理解与消化，不依赖购买官方订阅 |
| 平台与收藏 | 抖音等平台收藏、关注内容；必要时通过浏览器、插件、官方工具或 API 接入 | 用户面对平台和内容，而非工具运行列表；逐项扩展，不先建设插件市场 |

三类入口保留来源管理、自主浏览与实际更新的查看，但不支配主内容形态。同一议题可以组织三类来源中的有关材料；同一材料重复进入不重复制造内容。收藏刚导入不等于值得再次推送，收进来的是材料，交付的是经过取舍的解读。当前继续关注知乎收藏、抖音收藏或视频链接、GitHub 和 X 信息，具体接入与覆盖见调研。

公共材料可共享整理，私人收藏、完整 Lib、项目背景和个人偏好不默认进入公共内容池；跨来源阅读不扩大上传授权。官方服务不可用、未订阅或取消订阅时，已有本地资料、Lib 与个人来源基本能力不应失效。

#### 展示：一个雷达主页，一种解读详情

主阅读收敛为两种形态，不再为每项底层能力增加页面。**主页直接交付理解，详情解释依据，持续更新说明认识有什么变化。** 来源管理与深层辅助不另造一套阅读产品。

| 主阅读形态 | 用户直接得到什么 | 体验底线 |
| --- | --- | --- |
| 雷达主页／短解读 | 关注分类中的新解读和议题更新；每项清楚表达议题、当前解读和关键关系或变化 | 不点开也能获得有用理解；不以原标题加摘要、来源数量、监控数字或悬念按钮代替内容 |
| 统一解读详情 | 围绕同一问题连贯阅读当前理解、背景与条件、关键证据和分歧，以及后续修正 | 先读懂，再按需查依据和深入；不是跳进空聊天框，也不要求先操作图谱或在多个工具页拼凑答案 |

主页可以按科技、AI 等关注方向切换，保留三类来源入口；“新解读”与“后续更新”沿用同一种内容结构。主次由选题和内容决定，不退化成等尺寸新闻卡片墙或单一无限混合流，也不靠空分类、重复信息与占位条目制造丰富。

详情是一条阅读主线，不要求固定生成四篇长文或四个标签页。关键判断与支持它的材料就地关联，用户能展开核查，而不是文末列十个链接便声称多链路证据。主要不确定性与影响判断的条件必须在正常阅读中呈现，不能全部藏进深层。

时间线、对照、关系表达、图片或原视频按解释需要使用，都是同一份解读的表达手段，不各自成为默认功能专区。保持作品感、内容丰富度和视觉完成度，但不为每条内容机械生成所有形式。详细过程、历史、来源、Lib 复用和团队追问按需深入；复杂能力放深层，基本价值不能藏深层。

#### 整合、解释与持续跟进

材料先经过取舍和理解再交付。围绕同一问题组织事实、前因后果、条件差异与多条证据；区分原始材料、转载、独立观察和分析判断。十家媒体引用同一公告不算十份独立证据，时间上的先后也不能直接冒充因果。新证据、不同观点与事实纠正不能因去重被丢掉；资料不足时说明缺口，不编造关系、概率或确定结论。

有意义的后续材料应回到原议题，展示当前有效解读和本次变化，保留必要的判断演变，不悄悄覆盖旧结论，也不每天重写相似报告。值得长期观察的问题持续跟进；小变化可以简述或并入已有议题，不强制把每条消息都做成长专题。没有新增理解时不为凑更新而制造内容。

结合获准使用的已有 Lib 和用户修正，识别新增、补充、重复或冲突；不假装知道用户已经掌握什么。过滤可解释、可纠正，默认不删除原平台收藏。读取不完整时注明证据范围，不以标题摘要冒充全文、视频或图表理解；外部信息和未经采纳的分析不自动升级为用户正式结论。

长期个性化主要影响选题相关性、背景深度与用途说明，不改变事实与分析标准。保留自主浏览、重要不同观点和适量探索；不能只追点击或把用户困在已知兴趣里。当前先实现关键词范围内的高质量栏目内容与明确纠正，用户及订阅开放后再逐步研究推荐算法，而非当前建设画像、协同过滤或训练系统。

在用户设定的范围内，团队可完成低风险的筛选、归纳和关联；重要冲突、改变已确认判断或安装执行另按授权处理。有价值的内容可继续进入 Research、Lib、说明书或项目工作，不强迫每条内容转成任务，也不在雷达重新建设聊天和知识管理系统。

#### 可选情景推演

**基础雷达负责持续理解现实，情景推演负责按需探索可能。** 推演放在具体议题的深层，是可选的增值能力，可研究单独收费；不作为首页主角，不默认每条运行，也不阻塞当前栏目交付。基础解读必须已经提供整合、因果与条件分析、证据和限制，不能为了收费把这些价值移到推演之后。

用户围绕已整理议题提出具体问题，比较不同条件下的可能影响与参与者反应；使用有关材料与必要背景，而不是把整个信息库交给模拟器。资料丰富提供准备优势，不构成预测准确的保证。复杂配置和 Agent 过程不是使用门槛。

真实事实、分析判断、情景假设与模拟结果必须区分，模拟角色的言论不能作为实际反馈或独立证据回流。后续现实变化可以用来检查原来的前提与判断，不因新消息自动触发收费重跑。具体候选、效果、成本和许可见调研；收费方式与价格未定，不承诺确定未来、证券走势或收益。

**运行边界：** 独立服务的持续供给不依赖 ytriple 保持打开；本机任务和依赖浏览器登录的平台接入按实际能力运行。持续供给不等于逐条弹通知或全部本地任务后台化；展示实际观察时间与失败状态，不能把已确认方向写成已上线能力。

### 自媒体账号与对标监控

自媒体能力包含自己的账号和对标账号的组织、监控、比较与复盘。首批关注 TikTok、YouTube、X、抖音，后续再扩展其他平台；这不是已接入清单，也不要求首版同时完成。

公开账号的内容更新可以属于雷达订阅；账号经营数据、表现分析与完整对标复盘是进一步的专业能力，不与基础雷达阅读捆成同时交付。先验证本地自用价值，工作台基本雏形建立后再逐步增加；自有账号基于用户授权，具体接入方式与限制见产品调研。

商业接入、公开分发与服务化条件随产品化研究，不提前铺设全套合规工程；本地自用仍以公开或用户有权访问的数据为边界，不以绕过权限、取得他人私有后台或转移登录凭据作为能力前提。这里的账号管理不默认包含发布、互动或代运营。

### 能力之间的连续关系

外部信号可以触发研究，研究可以形成知识与判断，判断可以进入说明书或指定项目反馈；人和专业工具实际使用后，ytriple 从获准来源理解结果，再把有效经验带入之后的工作。用户也可以从已有项目或资料直接开始，不必每次走完同一条流程。

**Prepare 必须留下可继续使用的成果**，不是只给建议；**Continue 必须恢复有效背景**，不是只提供一个打开工具的按钮。团队是把这些能力串起来的协作方式，不是另一座与知识、项目和外部情报分离的聊天孤岛。

## 5. 模型与 Agent 能力来源

### 第一版的核心底座

AI 能力与多 Agent 能力是产品核心，第一版要建立可实际使用、职责清楚并可持续扩展的底座：

- **AI 能力**：接入真实模型与工具，让成员能读取资料、开展研究、处理文档，并执行已授权的项目初始化动作。
- **多 Agent 协作**：支持团队交流与成员直聊；按需委派、追问、共享必要上下文、使用其他成员的成果并收敛结果。
- **上下文与工作连续性**：保留当前有效目标、用户修正、必要资料、成果和工作状态；切换成员、修改目标、中断或重新打开后可以恢复有效背景、继续工作。

底座与项目初始化、信息消化、文档产出等真实流程同步建设和验证。扩展方式需要在设计时考虑，但首版接入范围保持精简，不把“底座搭好”解释为提前完成全部模型、工具或平台适配。

### 模型与通用能力接入

当前基础模型接入以 OpenAI 兼容格式为主，同时允许接入 Google/Gemini 及其有价值的原生能力，尤其是 Deep Research。不能因为统一格式而舍弃需要专用接口的有效能力，也不提前追求所有厂商全面适配。

首版支持多套模型连接配置，当前明确包括 Gemini、DeepSeek 与本机 Ark API。可为不同成员设置默认模型，并在具体任务中覆盖；切换模型不丢失用户自己的有效目标、资料与成果。连接成功、工具可用和专项研究可用分别验证，不把同一 API 格式理解成全部能力相同。

团队的 Deep Research 成员是 ytriple 自己的稳定工作身份；Google Deep Research 是该成员可调用的外部研究能力，两者不等同。团队仍负责当前目标、必要上下文、结果核查和与其他成员协作，不能把整个团队变成某个外部服务的转发界面。相关接口能力与限制见产品调研。

ytriple 掌握团队协作、上下文、权限、工作连续性和成果语义；通用 Agent 底层优先复用成熟方案，不从零重造完整框架。模型 API、Agent SDK、工具、角色资料和外部专业 Agent 分别承担不同责任，不能混为一种能力。

不要求安装某个本机 Coding Agent 才能开展研究和文档工作。具体框架、运行环境、接口设计和实现方式由 Codex 决定，不在此锁定 Kernel、SDK 或技术栈。

## 6. 当前重心与长期目标

**长期产品目标：** 持续理解用户、外部信息、个人知识和项目状态，通过吸收、说明书、真实使用与反馈促进 Y 和团队共同成长，并跨时间、项目、工具、模型与 Agent 帮助用户工作。能力放大既包括当前任务做得更好，也包括有效知识、判断和经验持续积累；不是“装了很多 AI 功能”或“几个 Agent 会合作”就代表产品成立。

**当前重心：** 在第一阶段已完成的新底座上，推进“真实信息消化与资产复用”。以科技、AI、金融、股票等相关关键词先形成雷达分析栏目的真实供给，围绕重要议题交付可读、可核查、可跟进的解读。独立服务与三类来源方向不变；已有研究、项目初始化、文档修订与工作接续继续使用和提升，不重做技术栈，也不把这一阶段缩成接通一个采集接口。

本节落实 2026-09-12 的阶段讨论与最新栏目取舍，说明产品目标、功能安排与体验底线，不是工程计划。代码状态以当前实现及 [开发计划](开发计划.md) 的证据为准；来源与整体方案的研究见 [产品调研](产品调研.md) 及 [信息源与知识工作台方案调研](参考/信息源与知识工作台方案调研.md)。公开资料研究、源码审阅和 Codex 的实测记录分别看待，不相互替代。

**阶段目标：** Y 不必先搜齐来源或提问，打开雷达就能阅读整理后的议题解读；主页有理解，详情有依据，再次回来知道什么变了。个人来源与真实收藏也能参与消化；有用资产在另一项工作中被找回和使用，形成说明书并接收实际反馈。普通阅读不必走完资产化或任务流程。

**当前关键词与供给范围：** 开发期先以 **科技、AI、金融、股票** 等相关关键词作为选题、筛选和内容分类的起点，不是要求对四个宽领域做全量覆盖，也不限定未来只能有这些领域。关键词命中只让材料成为候选，仍须经过选题、去重、背景与证据整合，形成有新增理解的解读后再推送；不能把“先用关键词”做成原标题和摘要的转发流。金融、股票同样按公开信息的解释与证据分析呈现，不因关键词或推演功能变成荐股、买卖指令或收益承诺。

**当前与后期的取舍：** 先面向 Y 验证真实供给、栏目质量和简单阅读，不以开放用户、收费订阅、复杂画像或推荐算法为前提。用户与订阅开放后，再结合真实使用逐步研究个性化算法和服务分层；当前保留明确的方向选择与内容纠正即可，不要求推荐训练闭环。可选推演与收费能力保留为深层扩展，不是本轮雷达成立的必备交付。此处取代早先把个人推荐完善与雷达同时推进的泛化要求，不取消长期理解用户的目标。

**大致功能安排：结构完整，覆盖渐进。** 客户端以第 4 节的主页短解读和统一详情承接栏目；独立服务先交付预设范围内的真实整理内容，再丰富来源；个人网址/RSS 和平台收藏进入同一消化体验，逐项验证。三类来源不长成三套阅读产品，不等待服务覆盖全部来源才做客户端，也不先交付简单列表再无限推迟内容质量。具体开发拆分、技术选型和排期由 Codex 设计。

| 提升方向 | 用户应得到什么 | 不算完成的情况 |
| --- | --- | --- |
| 关键词范围内的真实供给 | 科技、AI、金融、股票等关注范围内，有限但持续、已经整理的信息内容；服务与客户端边界清楚 | 只有接口、关键词匹配或原始消息；要求先开通多用户订阅或训练推荐系统才能体验 |
| 分析栏目与简单阅读 | 主页面直接得到新增理解，详情解释背景、关系与依据，关键限制正常可见；三类来源可查可管理 | 第十一家改写同一消息；只有新闻卡片、加长摘要或聊天按钮；用图谱和功能数量代替内容价值 |
| 议题跟进与纠正 | 同一问题出现重要新证据时，当前解读接续更新，能看清本次变化，用户纠正能够生效 | 反复生成相似报告、悄悄覆盖旧判断、没有新增理解仍凑推送；将模拟结果当现实证据 |
| 个人来源与平台收藏 | 可用的自定义网址/RSS，以及至少一条真实平台收藏通路；明确实际内容与历史覆盖，能继续取得新增材料 | 只有模拟数据、首屏列表或标题；未订阅官方服务就不能使用个人来源 |
| Lib 主动复用 | 在获准范围内找出相关资产，区分新增、补充、重复和冲突；新任务可以利用既有判断、方法和来源，不要求 Y 记住文件位置并逐个搬运 | 仅增加收藏数量、标签或搜索框；每次任务仍从空白开始；未经确认就覆盖已采纳判断 |
| 说明书用途与反馈 | 选择真实用途，交给 Y 或专业工具使用；记录是否有效、适用条件、失败原因与用户修正，并回到对应资产 | 文件生成就算成功；工具介绍或工作流草案被标成已经验证的能力 |

来源顺序按实际可取得的内容和用户用途收敛。抖音已有小样和批量响应线索，可作为优先验证候选，但不锁死唯一入口；收藏列表、文字/图文、转录和画面理解分别计覆盖。一条平台尚未打通时，其他真实来源仍可验证消化与复用，不用模拟采集冒充完成，也不取消真正的收藏接入目标。用户后续提供的来源纳入同一判断口径。

**底座同步提升，而非单独重构：** 团队复用已完成贡献，只为实际缺口追问，减少重复成员调用和同主题成果；用户修正应改变相关判断与说明书，而非只增加一句回复。给人的说明书支持理解和取舍，给工具的说明书明确目标、条件、方法与验证方式；两者不以机械复制两份文件交付。

**交互继续打磨：** 保留已经迭代的单应用窗口与决策/过程/成果关系，把“阅读整理结果 → 查证据 → 找团队追问 → 修正理解 → 用于产出”接入同一工作。成员与子任务可按需展开，不增加 Y 的协调负担；新来源不能破坏草稿、阅读位置、成果版本和重新打开后的接续。不为了 Radar 再造一个独立聊天、收藏或知识工作台。

**完整使用证据：** 一批真实材料包含重复、过时、读取不完整和有用内容；团队形成具有新增理解的解读并保留证据。后续加入相关新材料或由 Y 纠正一个判断，原议题能说明哪些认识改变。换一项任务、重开应用后，团队能找回并利用至少一项有关资产形成说明书；说明书经过实际使用，修正和结果能回到正确资产。来源失败、过滤和未验证内容如实呈现，不以测试数量或篇幅代替栏目质量。这是用户旅程与价值判断，不指定脚本或固定调用顺序。

**范围保持收敛：** 当前不做全量新闻门户、全平台账号分析、复杂图谱工作台、工具市场、完整订阅后台或万能预测平台。推演、个性化算法和商业化不能阻塞关键词栏目；也不能借此推迟核心的整合、解释与跟进。资料授权和项目只初始化/监控/指定反馈的边界不变，尚未完成的首版义务不因阶段切换被取消。

### 第一版交付范围

第一版是可在本机自用的 AI 工作台，以下四部分均在首版范围内：

| 部分 | 首版应形成的能力 |
| --- | --- |
| AI 与多 Agent 底座 | 真实模型与工具调用、按需团队协作、必要上下文共享、成果交接与工作接续；作为核心优先建设 |
| AI 工作台基本功能 | 团队交流与成员直聊、工作和项目组织、资料与成果查看、历史接续、模型及工具配置；具体页面和交互形式由后续设计确定 |
| 项目初始化 | 接入已有本机 AI 规则体系，或在缺失时先实际创建完整目录与规则；通过团队交互明确项目，再建立身份、目录、登记、必要文档和适用的 Git/worktree 基础，并呈现真实结果 |
| 文档编辑处理 | 主要通过多 Agent 交互读取常规文档、创建与修订 MD，并产出信息图、PPT 等可使用成果 |

**开发主线：** AI 与多 Agent 底座是第一优先级，以项目初始化、信息消化和文档产出贯穿建设与验证，工作台承载完整体验。初始化、文档编辑处理与工作台基本功能都应随首版交付。

**首版验收重点：** 能从产品讨论建立规则与必要文档齐全的项目，交给 Codex 继续开发；能整理实际信息源形成可用的阅读与学习内容，并围绕具体问题开展研究、创意扩展、文档修订与可视化产出。团队能消费彼此成果，用户改方向、切换成员或重新打开后仍可接续。初始文档不以一次生成完美方案为门槛。

Codex 已据此形成 [开发计划](开发计划.md)，记录工程选型、模块边界、实施增量与验收。先贯通真实 AI 团队、资料到文档、修订保存与历史接续，再逐项补齐首版；当前产品正文不重复维护工程规格。

### 首版运行范围与预留能力

- **本机与独立服务分开**：工作台本机任务保持前台运行、保存后接续，不承诺退出后继续执行；这不再限制独立雷达服务的持续供给。雷达服务器按第 4 节单独发展，依赖本机浏览器或平台登录的接入不因服务器存在就变成全天在线。已实现范围仍以开发记录为准。
- **时长与费用**：用户暂未设置任务总时长或调用预算上限，可以等待有实际进展的长任务。仍需辨认失败与停滞，支持停止和恢复；提供可配置限制的扩展方式，具体额度在使用中再确定。
- **资料范围控制**：哪些资料必须只在本机处理，当前暂未定义；首版不展开完整的细粒度配置功能，保留后续实现方式。现有资料范围与授权边界继续适用。

### 渐进扩展与服务方向

**渐进扩展：** 雷达保持独立服务与三类来源，主体验围绕分析栏目而非来源堆积。当前先用预设关键词检验供给与栏目价值；后期开放用户与订阅，再逐步研究推荐算法、服务分层及可选情景推演。账号监控、浏览器辅助和其他能力按实际价值扩展。实现顺序与具体方案由 Codex 设计，不因分步建设删掉长期目标。

**开源与服务方向：** 产品开源；可独立封装的服务器能力允许用户自部署，也可以提供付费托管订阅，减少用户部署和维护负担。本地基础能力不应强制依赖官方托管服务。

**独立信息订阅服务已明确，不再只作为候选。** 服务价值是持续的信息源获取与维护、筛选整理及个人订阅交付，而不是单纯增加新闻条数；内容订阅与收费套餐是不同概念。用户不订阅官方服务，仍可使用 ytriple 的个人来源、收藏消化和本地工作台能力。公共来源处理可以复用，个人理解不默认上传完整 Lib、私人收藏或项目资料；适合本地处理的仍可留在本机。

独立雷达之外的通用持续监控、较长时间研究及其他托管处理仍属于可研究的服务候选。具体来源覆盖、套餐、价格和开源许可证尚未确定，不为商业化先建设复杂云平台；确认雷达方向不等于服务已经发布。

用户自部署的是 ytriple 相关服务，不代表 Google 等第三方托管模型和研究服务也能搬到自己的服务器。第三方 API 的访问、费用和数据处理条件仍需单独考虑。开源方向也不是本次将仓库公开或发布产品的授权。

### 用实际价值检验成长

每项工作和项目应有明确的价值目标，不能以说明书写完或 Agent 自评作为成功证据。价值关注三个层面：

| 层面 | 观察什么 |
| --- | --- |
| 说明书的实际用途 | Y 能否理解采用，工具能否据此完成目标，是否减少重复解释、错误和返工 |
| Y 与团队成长 | Y 能否将新认识用于判断；团队能否复用有效知识和已验证能力，并避免重复错误，而非只增加阅读量或 Skill 数量 |
| 项目成长 | 自媒体的内容表现与受众反馈，开源项目的真实使用、问题反馈、贡献和解决问题的情况；粉丝、播放量与 Star 是信号，不单独代表全部价值 |

反馈要帮助区分问题来自目标判断、说明书、执行过程还是外部条件。数据不足时保留假设，不制造因果解释。不能保证每个项目成功，但结果、失败经验和用户修正都应可检验，并用于改善以后工作。

### 七层成熟度：长期坐标，不是开发排期

沿用 0x 的七层框架理解各工作领域与能力的深度，原定义保留，结合吸收与说明书解释如下：

| 层 | 原产品语义 | 在本工作台中的体现 |
| --- | --- | --- |
| L1 | Ask / Find | 提问、阅读和搜索，找到所需信息 |
| L2 | Act | 通过授权工具完成具体任务，使说明书产生实际作用 |
| L3 | Persistent Context | 保留有效目标、背景与修正，换成员或隔天继续不从零开始 |
| L4 | Structured State | 组织知识、能力、项目与成果，区分草案、验证与失效状态 |
| L5 | Indexed Retrieval | 为工作找回合适的资料、说明书和工作流 |
| L6 | Semantic & Relational Intelligence | 理解关系、缺口和矛盾，将已有认识与方法用于新目标 |
| L7 | Composable Production + Learning | 组合成熟能力持续产出，以真实反馈改善说明书、资产和后续工作 |

七层不是七个页面、七个版本，也不是先完成所有基础设施才能使用。L2 / L7 的执行与生产可以由授权工具和专业软件承担，不突破“ytriple 不接管项目开发”的边界。

高度自动化是共同成长后的长期方向，来自反复验证的说明书与工作流在明确授权下被可靠复用，不来自 Agent 数量或无限自循环。新目标、重要取舍和不确定事项仍由 Y 与团队共同判断；常驻身份不等于持续耗费模型调用。

坚持 **少而深、Product Proof before Engineering**：先看一个真实工作能否从真实输入形成可继续使用的结果，不用每层各有一点功能、一次模型返回或测试通过代替产品价值。跨全局的综合判断要建立在足够的状态、知识和观察之上，不能用少量最近数据的一次摘要冒充“已经全面理解用户”。

## 7. 保持简单时仍须守住的边界

**AI 先理解再展示**，原始列表与文件作为证据和深入入口；**Capability 优先**，先理解任务需要什么，再选择执行能力；**外部权威源不迁移**，代码、网页原文、媒体工程与外部平台数据继续在其权威位置，ytriple 组织必要的引用、理解和成果。以下边界共同约束这种连接与复用：

| 注意点 | 产品应表达清楚的结果 |
| --- | --- |
| 团队协作 | 用户修改方向后仍围绕新目标协作；多人同意不自动等于事实正确 |
| 成果与反馈 | 正式文档、研究草稿、开发意见和已经执行的变更不是同一种状态 |
| 资料与权限 | 知道用了什么项目和来源；事实、用户确认、AI 判断和假设可区分；外部网页不是指令；外部服务只获得需要且获准发送的资料 |
| 成本与中断 | 常驻团队不等于持续运行；小任务不过度调度；停止、失败和部分成果不能伪装为完成 |
| 监控与服务器 | 区分本机与远端运行、最近检查时间、过期与失败；本机离线不冒充持续在线 |
| 接入与可用性 | API 可调用、账号授权成功、拿到目标数据和形成可信分析应分别验证；暂缺某项能力不应让整个工作台失效 |

这些是产品边界，不是要求先建设大型治理系统。具体实现和验证方式留给 Codex。

## 8. 文档与研发协作

主要正文只维护两份：本文保存讨论结论；[产品调研](产品调研.md) 研究实现产品所需的能力、竞品、工具、模型、接入方式、运行限制及其他参考，不局限于竞品。可以按需补充独立参考，如 [团队协作与交互调研](参考/团队协作与交互调研.md) 和 [信息源与知识工作台方案调研](参考/信息源与知识工作台方案调研.md)，但不形成重复产品定义。

用户决定目标、优先级、重大取舍和授权；网页 ChatGPT 负责总结、产品与能力调研及方案审视；Codex 负责具体产品设计、技术选型、工程方案、开发拆解、实现和验证。

**产品讨论规则：** 与 Y 讨论定位、功能范围、产品之间的关系和大致功能安排，客观审视并扩展方案，不只附和，也不把讨论展开为技术选型、实现方案或微观交互细节。本文保留已确认的产品方向、用户所得与体验底线；技术问题、成熟方案比较及其他细节归入《产品调研》或已有专项参考，由 Codex 判断并承担具体设计与实现。

**调研必须影响产品判断：** 能力目录不能代替产品探索。研究应围绕真实困境留下明确的体验主张、与普通方案的对照样例、取舍理由和待验证效果；不以调查数量或文档篇幅证明价值。网页 ChatGPT 给出可比较的产品判断与样例，不把“不指定工程细节”变成只写抽象原则；Codex 在既有设计与验证记录中说明采纳、替代或暂缓理由，并回看真实体验是否变化，不要求另建调研承接或验收文档体系。

**本轮协作改进：** 多次迭代不自动证明每处问题都来自文档；需要区分目标表达不足、已写要求未落实和必须通过实际使用收敛的体验。产品讨论要写清用户得到什么、体验底线和什么不算完成，Codex 将已采纳要求落实为自己的设计与验证，并区分工程检查、真实接入和实际使用证据。不能仅追加原则而不核查结果，也不能以测试数量代替产品价值。

用户负责方向与实际价值判断，不应成为唯一发现基础交互遗漏的人。草稿和阅读保护、正确文件与版本、失败可见、用户修正生效及成果可继续使用等已明确要求，应随相关功能一起验证；发现的反复问题沉淀到受影响章节，不扩建第二套验收文档或由网页 AI 接管工程计划。

调研可以包含技术选项与约束，但不直接给本项目指定页面、接口、数据表、Prompt、开发任务或实施路线。事实、用户已确认方向、研究判断和待验证事项分开记录；研究不自动成为需求。后续仅更新受影响章节，避免聊天越多文档越臃肿；近期取舍可以收窄当前实现，但不能在没有用户明确变更方向时覆盖或删掉已经确认的长期核心。

# ytriple 讨论总结

更新：2026-09-11。

本文保存用户已确认的产品定位、主要能力、体验边界和稳定原则，不是开发规格。竞品事实、研究判断和其他参考统一见 [产品调研](产品调研.md)，不自动成为需求。

## 文档与协作边界

项目的长期正文主要维护两份：本文回答“ytriple 是什么、为什么、有哪些已确认边界”；产品调研回答“其他产品怎么做、有什么可借鉴、有什么限制”。可以按需补充来源明确的参考材料，但不另起一套重复的产品定义。

- 用户决定目标、优先级、重大取舍、真实验收与外部动作授权。
- 网页 ChatGPT 负责讨论总结、产品框架、竞品调研、资料核查和方案审视；只更新受影响内容，不把局部讨论扩写为工程合同。
- Codex 负责具体产品设计、技术选型、实现方案、开发拆解、代码、测试与验证，并自行管理相应工程材料。

本文不规定页面数量、固定布局、接口、数据表、类或组件、Prompt、SDK 版本、开发顺序和里程碑。研究中出现某种做法，不等于 Codex 必须采用；实现进度也不能反向缩减长期产品目标。

## 定位与名称

> ytriple 是以 Y（用户）为中心的 Local-first AI Workbench，通过 Agent、研究、文档、本地 Context 和外部资源，放大一个人的思考、信息处理、判断与工作准备能力。

Y 代表用户本人。Triple 代表能力放大，不代表固定三个 Agent，也不是三倍效率的数值承诺。ytriple 继续作为项目和产品名称；多 Agent 协作是重要特色，而不是产品的全部。

AI Workbench 是整体定位。AI Forge 可以描述把想法和讨论成果变成规范项目底座的能力，不另造一个接管整台电脑的系统。

后续以 ytriple 为产品与代码基础，吸收 0x 的 Local-first、AI-first、模型与 Agent 可替换、信息理解和工作连续性思想。0x 不再作为独立产品继续建设；未来处理其仓库不等于本次文档操作获得删除授权。ytriple 的正式说明应自包含，不依赖未来继续读取 0x 仓库。

## 做什么，不接管什么

重点是研究、核查、分析、比较、讨论、评审、文档处理、知识复用、外部信息监控，以及项目底座和工作上下文准备。用户已有的本地工具、资源与外部服务应能被组织起来，而不是要求用户全部迁入 ytriple。

软件项目可以在 ytriple 中讨论方向、研究资料、形成文档并创建好项目底座；真正开发继续在 Codex 等本地专业工具完成。设计、剪辑等深度生产也继续留在对应专业工具。允许在授权范围内读取状态、准备交接和理解结果，不以替代 IDE、Coding Agent、剪辑软件或部署平台为目标。

不能因“不接管所有工作”而把 ytriple 缩成只有一个 PRD 生成器、一个聊天窗口或一个 Codex 启动器。研究、文档、资料组织、Intelligence、项目上下文和连续工作共同构成工作台。

## 核心体验：用户参与的多 Agent 工作台

聊天是输入方式之一，不是唯一工作表面。用户应能围绕当前工作看到相关材料、来源、各角色的有效贡献、分歧、当前结论和正在形成的成果，并在关键判断处修正方向。

多 Agent 根据任务需要参与：可以研究、专业分析、质疑、审查或综合；简单任务不必强行多 Agent。数量、分工和展示方式不固定，也不要求用户先搭建复杂的 Agent 工作流才能开始。

原有 Conductor / Researcher / Specialist 和主工作区、辅助工作区的交互思路值得保留，但三角色、三栏与 PRD 都不是整个产品的固定约束。不能把多 Agent 做成多个同质聊天框、预设台词或“正在思考”的表演。显示真实的任务、工具结果、来源和结构化贡献，不把内部推理全文当成交付物。

多视角的意义是补足用户能力，而不是让用户旁观 AI 开会。最终需要收敛出可理解、可修正、可继续使用的结果；Agent 多不等于结果必然更好。

## 主要能力

### Research 与文档

Research 是一等能力，能够结合本地资料和外部来源开展搜索、比较、核查、反证与综合。事实、来源、AI 判断、用户确认和未决假设需要区分。

文档是高频工作对象，不只是聊天结束后的导出附件。讨论应能沉淀为研究报告、产品总结、PRD、决策记录、内容 Brief、脚本等成果；用户可以继续修订和复用。产品可以帮助用户处理各类文档，但这不改变本仓库中网页 AI 与 Codex 的职责分工。

### 本地 Context、知识与资源

读取用户已有项目、正式文档、知识和资源，为当前工作找到真正相关的材料。收藏不等于知识，保存之后还需要理解、关联、检索和复用；不要求用户先搭建庞大知识库才能工作。

项目专属资料跟随项目；跨项目知识和可复用 Skill、workflow、模板等分别进入本机规则定义的知识与资源区域。不要为方便搜索再复制一套权威正文。跨时间继续工作，应恢复相关目标、已确认结论、资料和成果，不把旧聊天或模型记忆自动当作事实源。

### 项目底座与本机 Policy

用户提供的《本机项目与 AI 系统政策》（POLICY.md）是这一方向的既有依据；真正操作时以用户本机的当前 Policy、项目 manifest 和当前授权为准，仓库不另存一份竞争的全局规则。

产品应能安装或接入同一语义的本地管理规则，为其他用户按自己的路径和环境建立相应体系。已有规则应被识别和尊重，不硬编码某台机器路径，不自动整理整个 Home，也不因应用升级覆盖用户规则。

项目底座可以包括项目身份、规范路径、项目登记、规则入口、必要文档，以及按项目类型与授权建立的 Git/worktree 和远端对应关系；并非所有项目都必须是代码仓库。底座建立好、上下文准备好后，专业工具继续工作。

读取、建议、准备与实际写入必须区分。既有项目迁移和规则同步需要保留未知修改；中央规则投影不得覆盖项目自有规则。项目状态需区分登记的期望状态和真实观察结果，读取失败、过期和漂移不能表示成正常。本地项目创建是授权的写入能力，不是只读监控自动获得的权限。

### Radar

Radar 关注用户关心的主题、产品、公司、模型、工具、GitHub 项目、行业及其他外部变化。核心是去噪、理解和关联，形成少量有价值的 Signal、Change、Pattern，并解释为什么与用户有关，而不是堆积新闻或收藏链接。

Signal 可以进入研究、知识或项目讨论，最终转化为判断与成果。用户修正以及信息是否真正被使用，比单纯增加信息数量更重要。

### 自媒体账号与对标监控

Creator Intelligence 是已确认能力，既服务自己的账号，也服务对标账号的监控与管理。

- 自有账号：组织账号及其频道/项目关系，在授权和实际数据可用范围内理解发布节奏、内容表现、增长、互动与异常变化，辅助复盘。
- 对标账号：组织对标对象，基于可获得的公开证据比较主题、标题、封面、时长、发布节奏和表现变化，不把推测写成竞争对手的后台事实。

价值不止是数据仪表盘，还包括解释变化、发现内容模式和形成选题研究、内容 Brief 或脚本。这里的管理不默认包含代用户登录、自动发布、互动或代运营。

YouTube、TikTok、抖音、小红书等是讨论中的服务对象方向，不是已经接通的平台清单，也不承诺它们具有相同的数据能力。授权、公开数据和可见性限制应明确呈现。

## Agent 能力的已确认原则

模型可以通过 API 对接，但模型、角色说明、工具和 Agent 运行能力不是同一件事。

ytriple 掌握自己的工作语义、上下文、权限、协作交互与成果；通用 Agent 底层能力优先复用成熟方案，不从零重造完整框架，也不依赖用户必须安装某一个本机 Agent 才能开展研究与文档工作。Codex 等是可以交接或集成的专业工具，不是整个工作台的底座。

本地处理不等于给 Agent 无限制 Shell 权限；安装 Skill、规则或连接器也不自动获得联网、上传、付费或写入授权。Local-first 不等于所有调用都在本地：向外部模型或服务发送什么资料，需要由用户可理解的权限边界约束。

以上是能力归属与产品边界，不指定 Kernel 结构、接口或唯一 SDK。具体技术设计和验证由 Codex 完成。

## 如何判断产品方向是否成立

关注真实工作是否变得更容易：是否减少重复解释和来回搬运资料，是否补充了有效事实与不同视角，是否留下可以继续使用的成果，是否能交给专业工具继续。

项目研究与底座准备、已有文档的持续处理、Radar 信号调查、自有账号复盘和对标内容分析，都是讨论中的真实场景，不是开发排期。不能用页面、Agent 数量、一次模型返回或单独测试通过代替产品价值判断。

当前仓库保留 V1 PRD 原型作为可检查的已有资产。旧文档中“固定三 Agent”“只能 PRD”等不再定义长期产品；已有原型是否完整可用，以代码与真实运行验证为准，不因先前文档写过“已验证”就视为完成。

# ytriple 产品调研：竞品与能力参考

更新与公开资料核查：2026-09-11。本文覆盖实现 ytriple 所需的产品方法、模型与 Agent 能力、本地工具、浏览器辅助、数据接入、服务器服务及其他参考，不局限于竞品研究。已确认方向见 [讨论总结](讨论总结.md)。

研究对象是从零建设的新工作台，不审计、不依赖 ytriple 旧实现。下文区分官方资料中的能力事实、对本产品的研究判断和未验证条件；没有进行真实账号授权、付费 API 调用、安装体验或性能测试。候选方案不是开发指令，具体实现由 Codex 设计。

## 1. 本轮结论

| 主题 | 结论性质与含义 |
| --- | --- |
| 常驻最小团队 | 已确认产品方向。重点是稳定身份、匹配能力和协同处理，不是多个身份 Prompt 各自回答 |
| 模型接入 | 已确认以 OpenAI 兼容格式为基础，并允许 Google 原生能力；兼容接口不能代表全部功能等价 |
| Google Deep Research | 官方提供可调用的专用研究 Agent，但有独立接口、异步运行和数据存储条件，不能仅当作一个聊天模型名称 [M2][M3] |
| 本地与项目 | 已确认以初始化、监控和指定文档反馈为边界；实际开发修改留给 Codex |
| 账号监控 | 已确认后置、先本地自用；API 与浏览器辅助可以互补，但权限和实际数据范围不能假定 |
| 开源与服务化 | 已确认开源、本地、自部署和可选付费托管方向；收费能力只是候选，不是当前工程清单 |

## 2. 团队能力从哪里来

### 可复用的协作能力

| 参考 | 官方资料可确认的能力 | 对 ytriple 的研究判断 |
| --- | --- | --- |
| OpenAI Agents SDK | 提供 Agent 作为工具参与协作，以及由其他 Agent 接管对话的 handoff；两种责任分配不同 [A1] | 可参考“面向团队统一交流”和“直接找成员”两类协作，不必从零重造全部通用能力 |
| Google ADK | 支持协调者与指定子 Agent 协作，以及顺序、并行、循环等工作流形式 [A2] | 可研究固定团队如何灵活处理任务；不要求用户或本项目先造可视化编排平台 |
| MCP | 用于连接 AI 应用与外部数据、工具等系统的开放协议 [A3] | 是能力互操作选项，不等于团队协作本身，也不替代本机 Policy 与授权 |

以上是候选资料，不表示已选定某个 SDK，更不要求同时集成多套框架。选型应看能否支撑真实团队协作、当前模型范围和本机使用，而不是功能表最长。

### 协作质量的研究判断

稳定身份应同时有职责、可用工具、资料范围和明确产物。用户提出一个目标后，成员能互相委派、补问、消费研究成果、指出缺口，再形成统一结果；不能把三次独立生成加一次拼接当成全部协作能力。

需要关注的不是让所有成员看见所有聊天，而是让他们共享当前有效目标和必要事实。用户修改方向、切换成员、隔天回来，都不应要求重新组织整套上下文；不同项目则不能互相污染。

“常驻”不应造成持续付费调用；小任务由适合的成员处理，多成员协作只在有价值时发生。成本、等待、部分失败和恢复属于体验考量，不据此规定运行时结构。

## 3. OpenAI 兼容格式与 Google 能力

### 基础模型接入

Google 官方提供 OpenAI 兼容入口，可以沿用 OpenAI 客户端调用 Gemini；同时也提供原生 API。[M1]

研究判断：基础模型调用可保持精简，但工具、引用、文件处理和托管 Agent 不能仅凭“兼容格式”判定完全可替换。当前只围绕兼容接口与有明确价值的 Google 能力验证，不扩成覆盖所有厂商的适配工程。

### Google 值得研究的能力

| 能力 | 已核实的官方描述 | 对产品的意义 |
| --- | --- | --- |
| Gemini Deep Research | 自主进行多步研究并产生带引用报告；支持协作规划、文档输入及部分工具扩展。当前为 Preview，仅通过 Interactions API 使用，不通过普通 generate_content 调用 [M2] | 团队研究员可以委托专门研究服务，而不是自行模拟每个研究步骤 |
| Interactions | 支持服务端会话状态与后台任务；默认存储 interaction，后台执行与 store=false 不兼容 [M3] | 外部研究的任务状态与资料保存范围必须明确；不能把服务端会话当作永久本地记忆 |
| Google Search grounding | 可以利用实时网页搜索并返回引用信息 [M4] | 适合较轻量的事实补足，与长时间 Deep Research 分开考虑 |
| Gemini 文档理解 | 官方描述对 PDF 的视觉与文字内容进行理解，包括图表、表格等；非 PDF 输入的处理并不保证同样保留视觉结构 [M5] | 为研究、资料阅读和文档分析提供候选能力；理解文档不等于保证原格式无损编辑 |

当前 Deep Research 的关键限制：要求后台执行，且要求保存请求；暂不支持自定义 Function Calling 工具和结构化输出，但可使用远程 MCP。[M2] 因而不能假设它直接调用本机所有工具、永不存储资料，或可靠返回任意约定 JSON。

**团队的研究员与 Google Deep Research 不是同一层。** 前者维持用户的工作目标、资料范围和团队协作，后者可以作为受托研究能力。返回报告仍要结合项目事实核查和整理，不能自动变成已采纳结论。

还需实际验证：当前账号与地区可用性、凭据与计费条件、真实延迟、引用质量、任务取消/恢复和文件处理效果。供应商托管任务不一定支持任意时刻原地修改目标，不能仅凭“可协作规划”就承诺运行中可以随意重定向。模型 ID 和版本不在本文写死。

## 4. 本地 Context、文档与工具

用户提供的 POLICY.md 是本地治理的已有依据，实际操作应读取本机当前规则与项目登记。本文不复制用户绝对路径或另立一份全局 Policy。

| 能力问题 | 研究判断 |
| --- | --- |
| 读对资料 | 项目归属、文档版本、权威入口和观察时间比“读入更多文件”更重要；检索不能把历史草稿升级为当前规则 |
| 文档处理 | 区分读取、研究整理、正式成果编辑和复杂格式保真；对不支持的格式或缺失内容明确说明 |
| 项目反馈 | 开发中主要读取状态，把意见写入约定文档，由 Codex 处理；不需要为此建设通用多人文档协同系统 |
| 工具接入 | 优先复用已有本地工具和稳定接口，也允许必要的原生辅助能力；不把无限制 Shell 当作默认方案 |
| 资料外发 | 本地保存、发送给模型、上传给研究服务、导出诊断记录是不同动作，不能用 Local-first 一词掩盖 |

一个容易漏掉的例子：OpenAI Agents SDK 的追踪可以记录模型与工具活动，并在支持的运行环境中默认启用导出；可以配置或关闭。[A4] 研究判断是，采用成熟 SDK 仍须核对其外发行为，而非认为本机程序的数据自然只留在本机。

### 反馈闭环，而非直接接管项目

已确认产品边界是：用户在工作台观察项目、讨论意见、形成指定文档反馈，再回 Codex 修改。需要区分“已记录”“已采纳”和“已执行”，但这些区别不等于需要复杂任务管理平台。

反馈不能被自动当作新的项目权威结论，尚无执行证据也不能显示为完成。指定反馈文件存在外部修改时仍需保留未知内容。这一小范围问题保留，不再把广义文档并发编辑作为整个项目的主要障碍。

## 5. 浏览器插件与本地辅助

插件或其他辅助工具是允许研究和开发的能力，不要求全部功能只能通过官方 API 完成，也不要求当前就建立完整插件平台。

| 选项 | 官方依据或验证状态 | 用途与边界 |
| --- | --- | --- |
| 用户主动触发的浏览器插件 | Chrome activeTab 可在用户操作后临时取得当前标签页权限 [B1] | 可研究保存、提取和理解用户当前可见内容；不是天然的全站持续访问授权 |
| 插件与本机应用通信 | Native Messaging 支持扩展与注册的本机程序通信 [B2] | 可把浏览器观察接入本地工作台；插件安装和本机辅助程序仍是两部分 |
| 后台扩展任务 | 扩展 Service Worker 有休眠、终止和状态持久化约束 [B3] | 不能把插件视为永不中断的常驻服务器 |
| 其他本地浏览器方案 | 候选，未对目标平台实测 | 可按真实数据需求研究，暂不锁定工具或实现方式 |

研究判断：插件看到的内容与官方 API 返回的数据可能不同，需要保留来源与时间，不把页面暂时不可见当成数据为零。研究、账号管理和浏览器操作的授权应分开；不采集或转移密码、会话 Cookie 等登录凭据，不以绕过访问控制为前提。

本地自用验证与公开分发可以分阶段处理；是否需要额外插件由实际能力缺口决定，不让插件平台本身变成主要产品。

## 6. 自有账号与对标账号：首批平台

以下只是官方能力线索和待验证范围，没有接通真实账号。当前先建立工作台雏形，再逐步加入监控。

| 平台 | 官方资料可确认的入口 | 暂不能假定的部分 |
| --- | --- | --- |
| YouTube | Analytics/Reporting 面向授权频道的报告；Data API 提供频道元数据及部分统计 [P1][P2] | 自有频道授权不等于对标后台权限；公开视频也不等于可通过官方字幕下载接口取得完整字幕，该接口要求视频编辑权限 [P3] |
| TikTok | Display API 提供用户资料、视频列表与查询；接入要求相应产品批准、scope 和用户授权 [P4][P5] | 展示 API 不等于完整创作者后台或任意对标历史库 |
| X | 提供用户帖子时间线，指标区分公开与需用户身份访问的自有内容数据 [P6][P7] | 不假定所有指标、历史范围和账号权限一致，实际费用与额度需在接入时核查 |
| 抖音 | 已找到官方“查询视频基础信息”能力说明，标明申请权限、用户授权和对应 scope [P8] | 不同应用形态与能力包有区别；尚未验证适用于 ytriple 的具体申请路径和完整账号分析覆盖 |

自己的账号优先尝试官方授权接入；对标账号使用实际可获得的公开或另行授权资料，必要时研究浏览器辅助。不是每个平台都能取得同样的数据，也不应因一个平台暂不可用而阻塞工作台本体。

共同注意：标题/封面分析、视频内容分析、后台经营分析是不同证据层；拿到前者不能声称完成后两者。比较还要考虑内容发布时间、观察窗口、内容格式与缺失值；没积累历史就不能制造过去的完整趋势，相关性不等于因果。

账号管理包含对象组织、分组、授权状态、监控与复盘，不自动包含代用户发布或互动。公开分发与商业使用时应再核查接口用途、保留/删除、应用审核和平台条件；现阶段不铺开复杂合规工程，但自用不改变接口本身的权限条件。

## 7. 竞品与相邻产品参考

以下来自官方资料，不是安装实测或性能背书。

| 产品 | 可确认的产品做法 | 可借鉴之处与不照搬的部分 |
| --- | --- | --- |
| Notion Research Mode | 综合 Workspace、连接来源和 Web，研究结果可保存为页面 [C1] | 借鉴材料、来源和成果相连，不要求用户迁移整个本地项目 |
| Genspark | 公开展示 Mixture-of-Agents 和多种工作成果 [C2] | 借鉴协作与成果导向，不照搬接管所有办公和专业生产的范围；不把宣传中的质量优势当作实测结论 |
| Tana Agents | Agent 的指令、能力、工作空间上下文和可选计划任务可以结合 [C3] | 借鉴身份与实际能力匹配，不把创建角色和配置工作流作为使用前提 |
| AnythingLLM | 文档、模型和 Agent 的本地应用，同时有自部署与托管形态 [C4] | 借鉴本地与可选服务并存，不把它的产品或技术方案直接搬成 ytriple |
| Pieces | 本机工作上下文可搜索、跨工具使用，并提供暂停、排除和删除控制 [C5] | 借鉴连续性与控制权，不默认全程采集桌面活动 |
| Readwise Reader / Ghostreader | 库内研究可以定位相关段落并回到原文 [C6] | 借鉴收藏后的理解与复用，不仅做资料列表 |
| Feedly Market Intelligence | 持续关注信息、趋势和公司变化，并综合报告 [C7] | 借鉴 Radar 从信息到信号，不追求新闻数量 |
| Hootsuite Lumen | 品牌、趋势、竞争表现等 Social Listening 与解释 [C8] | 借鉴监测后进一步调查，不把企业舆情平台等同于个人创作者工具 |
| Sprout Social | 对自有与竞品的增长、互动、发布量等进行比较 [C9] | 借鉴同口径对标与复盘，不照搬完整代运营和发布管理 |

综合判断：ytriple 的差异不能只写“有多 Agent”；关键是用户能以低沟通成本与稳定团队合作，围绕真实资料形成成果，再把专业执行交给原有工具。Radar、知识和账号信号进入同一个团队工作过程，而不是彼此孤立的列表页。

## 8. 开源、自部署与可选托管服务

AnythingLLM 的桌面、自部署和托管形态提供了相邻参考。[C4] 但它不能证明 ytriple 应采用相同商业模式，也不能替我们确定收费项目。

以下为服务候选判断，不是已确认开发任务：

| 候选能力 | 托管价值 | 仍需验证的边界 |
| --- | --- | --- |
| 持续监控与定时情报 | 用户电脑不在线时，获准在服务器运行的采集和处理仍可继续 | 数据源是否适合服务器访问、授权维护、运行成本；不能假定依赖本机登录态的插件会因此继续运行 |
| 长时间研究任务 | 统一管理适合远端运行的任务与结果，减少用户维护 | 部分供应商本身已提供后台执行 [M2][M3]；不能只把转发包装成不可替代的收费能力 |
| 文档与媒体资料处理 | 重任务不占用用户本机，维护服务可作为价值 | 敏感资料是否适合上传、处理质量与成本；保持本地或自部署选择 |

本地、自部署和官方托管之间应保持同一工作语义与可继续使用的成果，不用私有数据格式制造锁定。离线、本机暂停、远端仍在运行和真实失败需要区别呈现。

自部署 ytriple 的服务，不等于自部署 Google 的托管研究 Agent；第三方凭据、API 费用、条款和可用性仍然存在。开源许可证、组件许可证适配、服务范围与收费方式尚未确定；这不影响先形成自用工作台，也不授权当前公开仓库。

## 9. 后续调研应持续回答的少量问题

1. 团队是否真正减少重复沟通，还是让用户多看了几份答案？单成员与团队模式的切换是否自然？
2. 基础兼容模型与 Google 专项能力分别能可靠完成什么，成本、资料外发和 Preview 变化有什么影响？
3. 项目反馈是否进入正确位置，和已采纳结论、已执行变更分开，且不越权修改开发项目？
4. 各平台与浏览器辅助实际可取得什么数据，哪些资料只是缺失，哪些功能尚未授权或未连接？
5. 什么任务确实值得持续在线或托管，什么任务留在本机更简单？

这些问题用于产品与能力判断，不扩写成代码架构、接口、表结构或开发排期。新资料可以更新本文，也可以作为独立参考；只有用户采纳的方向进入讨论总结。

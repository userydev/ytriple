# ytriple 产品与能力参考

版本：2026-09-13 · 与本轮产品定义配套

本文完整替换旧《产品调研》的汇总正文。当前目标用户、功能边界和应有行为以 [产品定义](讨论总结.md) 为唯一依据；本文只保存能够支持这些目标的能力事实、方案取舍和待验证问题，不构成另一份需求、工程架构或开发排期。

本轮重新读取了一手资料，重点是 Skill、团队协作、例行工作、服务器能力与结果反馈。没有安装候选框架、调用付费模型、进行账号授权或实机 UI 测试。旧专题中的样本证据按原日期保留，不能把“文档支持”写成“ytriple 已实现”。当前 0.1 的工程状态仍查 [开发计划](开发计划.md)，本次不重选其技术栈。

## 1. 研究结论与产品定位的关系

两类用户已由用户确定为个人开发者和个人创作者；具体痛点、使用频率、愿付价格和能力包受欢迎程度仍是需要真实使用验证的假设。粉丝数、工具安装量和 Star 数不足以代替工作方式，也不能据此增加工作室/企业管理需求。

**本轮研究判断：** 值得强化的是目标取舍、证据核查、Skill 的实际效果、交接是否清楚以及结果回验。它们应分别进入雷达、项目与资产的真实操作，不再只写成抽象理念。多 Agent、定时和 AI 摘要已经有现成机制可借，不能单独当作独占卖点。

研究时分开三件事：借鉴一个产品的工作方式、复用某个组件、接入外部服务。不因为喜欢一个功能，就把对应产品的界面、数据库、团队与商业模式全部引入。

## 2. 本轮一手能力证据

下表第二列是官方资料支持的事实；第三列是针对 ytriple 的判断或待验证条件，不是已完成效果。

| 能力与来源 | 本轮读取到的能力事实 | 借鉴与边界 |
| --- | --- | --- |
| Agent Skills 格式 [R01] | Skill 以 `SKILL.md` 描述，可带脚本、参考资料与模板；规范包含环境信息，`allowed-tools` 仍有实验性和实现差异 | 把方法、资源和可执行依赖区分。格式校验不等于有效、安全或已获工具权限 |
| Skill 接入 [R02] | 官方接入指南覆盖目录发现、按需加载、模型自动激活和用户显式激活，也讨论可选子 Agent 执行 | 用户能指定，团队能自动用；本机与远端发现机制不同。不能假定其他产品目录里的每个 Skill 在当前运行环境都可直接执行 |
| OpenAI Agents SDK 协作 [R03] | 区分将 Agent 作为工具调用并返回结果，与把对话责任交给其他成员；支持代码侧与模型侧编排 | 可支撑现有团队责任关系，但不自动形成项目资产、跨工具连续性和可用交接 |
| SDK 人工介入与事件 [R04][R05] | 有审批/中断相关机制和完整流式事件；文字输出不是全部运行状态 | 界面要依据真实工具结果、委派和等待呈现状态；SDK checkpoint 不是产品授权政策，也不证明外部动作可无损重试 |
| MCP [R06] | 提供 AI 应用连接外部数据与工具的通用协议 | MCP 是能力通路，不是 Skill、团队或权限保证；插件声明不能自行取得本机执行权 |
| Gemini Deep Research [R07] | 专项研究使用 Interactions API；当前文档要求后台模式，且后台执行要求保存 interaction；支持的远程工具和输出有独立限制 | 是可受托的研究服务，不是普通聊天 endpoint，更不等于本地所有工具可用。运行位置、资料保存和取消能力需实际验证 |
| Readwise Global Ghostreader [R08] | 跨库研究与段落引用、可编辑技能、集合分诊和用户控制的读写权限 | 可借鉴“选定资料集合→处理→追问→原文”的连续体验。不把一篇篇摘要或全库 Chat 当成我们的全部产品 |
| Inoreader Automated reports [R09] | 可选择来源范围、报告目的和周期，预览并保存报告；有任务管理和用量条件 | “有效工作转成例行”有产品参考；ytriple 还需要关联已有资产与原交付，不反复输出相似报告 |
| GitHub Webhooks [R10] | 可订阅具体事件向服务器投递，访问范围取决于实际安装位置与授权 | 为项目变化触发提供候选；不是任意公开仓库都允许配置 webhook。无该授权时需采用实际可用的观察方式并如实标明 |
| GitHub Actions 定时 [R11] | 官方提醒定时事件可能延迟甚至丢弃，有默认分支与运行条件限制 | 说明现成调度也有语义边界；不能把 CI 定时当作个人工作台准点任务的无条件保证，不据此指定本项目采用 Actions |
| YouTube Channel reports [R12] | 频道分析请求需授权，指定频道的授权者必须为该频道所有者 | 自有账号与对标数据不能混用；接口存在不证明已接通。缺数据可先使用用户提供的真实报告，不能生成虚假经营分析 |
| Chrome 轻入口 [R13][R14] | activeTab 提供用户操作触发的临时访问，Native Messaging 连接扩展与本机程序 | 可以作为保存与本地输入的候选；单页权限不等于全历史收藏，浏览器登录态也不自动同步到服务器 |

以上事实不规定 ytriple 的接口、模型 ID、调度框架或组件。供应商状态随时间变化，具体依赖要按采用的版本与账户条件核查。

## 3. 团队与 Skill：从“能配置”到“真的有用”

### 3.1 能力模型的研究取向

稳定成员承担对用户的责任；场景默认组合适应软件/媒体项目；Skill 提供可复用方法和必要资源；工具/MCP 提供实际操作；子 Agent 承担限定专项工作。它们可组合，但不能互相冒充。

建议保留当前团队运行基础，增加能力发现、适用范围、按需加载及可追溯结果的产品语义，而不是把媒体项目做成另一套引擎。研究员核查事实、内容编辑组织表达、统筹负责取舍；专业技术问题再调用 CTO。单成员可以解决的工作不召集全员。

### 3.2 三种可参考的 Skill 使用方式

| 方式 | 好处 | 需要核查的地方 |
| --- | --- | --- |
| 用户明确选择 | 让方法可控，可对同一成果使用不同审查方法 | 指定是否真正加载了正确版本，而不是只在 Prompt 里提到名称 |
| 成员按需选择 | 减少普通用户配置负担 | 是否识别适用条件、避免重复激活、明确缺少依赖，以及上下文缩减后仍能正确使用 |
| 专项子 Agent 执行 | 隔离较长的分析或验证工作，把结果交回负责成员 | 共享什么资料、如何追问、如何判断完成；不能因开了助手就跳过授权或把成本隐藏 |

按需加载和显式激活已有格式/接入资料支持。[R01][R02] 技能调用记录应说明作用对象、输入范围和形成的结果；纯方法型技能没有工具执行不等于无效，但不得伪造工具使用。

### 3.3 场景能力包与质量样本

下列是产品研究样本，不是已安装 Skill 列表：

| 场景能力 | 合适的输入 | 有价值的输出 | 不能冒充什么 |
| --- | --- | --- | --- |
| 收藏消化 | 实际可读材料、处理目标及获准 Lib | 主题理解、过滤原因、来源与知识变化 | 不能只看标题就声称阅读全文/视频 |
| 选题与脚本审查 | 频道说明、脚本和证据 | 承诺一致性、结构问题、证据缺口与可采用修订 | 不能预测必然爆款或复制对标风格 |
| 需求与交接检查 | 目标、约束、现有材料及接收对象 | 暴露歧义和缺失输入，明确完成含义 | 不能用阅读预演保证真实工程正确 |
| 反馈归纳 | 原始问题/评论、版本/作品和观察范围 | 相似问题、少数意见、未证实解释与关联资产 | 不能把热门意见自动变成需求或因果结论 |
| 资产检查 | 实际使用条件、新证据与稳定版本 | 需要复核的条件和修订草案 | 不能自动升级所有例行任务的方法 |

内置能力包应带适用条件、代表输入输出与已知失败情况。能工作的一小组优于大量未验证包；包版本、依赖与用户自定义可分开管理。第三方许可、安全和实际执行条件需要按具体包核查，不能把 Registry 或一个 `SKILL.md` 当作审计认证。

## 4. 例行工作的整体方案取舍

### 4.1 定时只是触发，委托才是产品对象

Inoreader 展示了来源范围、处理目的、周期和结果管理的结合。[R09] 对 ytriple 的研究判断是：从已经有效的工作建立例行模板，继承相关项目、材料、方法和输出位置；默认交付增量或待确认修订，不每次新增一个聊天。

自动化应区分三个触发：时间；实际可观察的事件/变化；真实发布等节点后的一段时间。把尚未发生的计划日期当实际发布、把轮询当实时事件、把通知发送成功当任务成功，都会破坏用户信任。

### 4.2 可比较的运行方式

| 方式 | 适用工作 | 收益 | 边界 |
| --- | --- | --- | --- |
| 当前客户端进程执行 | 本地资料消化、项目观察、简单例行处理 | 沿用现有环境，授权和资料范围容易理解 | 必须运行且机器可用，退出或休眠不能继续冒充运行 |
| 明确启用的本机后台执行环境 | 需要本地文件或登录会话的重复工作 | UI 关闭时可独立处理的潜力 | 安装、系统生命周期、权限和恢复要单独验证，不默认用户已经拥有 |
| 自部署/官方服务器执行 | 公共信息、获准远端资料与托管研究 | 用户电脑关闭时仍可提供适用能力 | 无权访问本地资源时只能等待、要求授权输入或转交本机 |
| 提供商原生长任务 | Google 等有实际后台接口的专项研究 | 减少重复建设专项过程 | 不等于我们已经有完整任务托管、用户管理、跨工具执行与结果交付 |

表中是运行选择，不是要求全部同时实现或指定任务系统。现有通用调度和外部事件能力可复用，但不能借用一个名词就保证精确触发或任意失败恢复；GitHub 的事件/定时文档就是范围与可靠性不同的例子。[R10][R11]

### 4.3 决定是否可靠的体验问题

应能辨认工作是否有新输入、是否需要跑模型、是否正在等待本机/授权、结果保存在何处。离线补做需要避免重复事件、重复收费和重复写入；失败可以保留有效部分，不无限重新生成全文。取消远端任务没有确认时不能显示已停止。

触发按用户时区表达并显示下次实际时间；发布节点改变后说明影响，错过多个时点不机械重放。额度可配置、用量可查、失败可暂停；不能将原作者自用“不设总额度”的偏好强加给其他用户。

Skill、资料范围或权限改变时，不静默改变长期任务。自动化产生的文件/事件也不应反复触发自身，形成无收益循环。这里定义结果边界，不规定去重键、数据库结构或具体调度算法。

## 5. 客户端与服务器：不止 API 转发

**产品已确认**服务器有信息、AI 能力和用户三项责任。研究需进一步验证这三项怎样减少普通用户负担，而不是只完成登录和计费页面。

| 服务 | 值得验证的用户收益 | 容易遗漏的问题 |
| --- | --- | --- |
| 信息 | 打开就有经过整理的主题理解，个人来源也能吸收 | 公共和个人材料隔离；有新认识才交付；不把来源失败表示为无新闻 |
| AI 能力 | 不配厂商密钥也能使用有效模型/研究能力，结果可查 | 能力与用量清楚；服务端凭据不分发给客户端；备用通路不悄悄扩大资料外发或费用 |
| 用户 | 订阅、设备、授权、数据控制和退出简单 | 付费权益不等于本地文件授权；取消订阅不锁本地资产；不演变为企业组织后台 |

个人服务、自带 API 与自部署的工作语义应一致，不利用私有数据格式制造依赖。云端任务返回的是特定版本下的结果；在它运行时本地资产发生变化，不能静默覆盖较新版本。不同设备或本机/服务器恢复同一委托，也不能各自执行一遍。

这些是研究取舍，不表示已经建立订阅服务、用户系统、跨设备同步或所有数据删除能力。模型/研究 API 的数据保存、地区、账号条件与费用须按真实接入核查。Google Deep Research 当前的独立后台与存储条件尤其不能被普通 API 包装掩盖。[R07]

## 6. 雷达、反馈与轻入口的取舍

### 6.1 吸收端保留深度，而非另造新闻 App

当前产品保留栏目式雷达：主页就能读懂，统一详情表达证据与条件，同一议题持续跟进。信息订阅、我的来源、平台收藏共用处理。筛选可纠正，去重不能丢掉反例和独立证据。

Readwise 的库内分诊、局部/全库连续操作与原文引用提供参考；Inoreader 则提供持续报告的样本。[R08][R09] 对 ytriple 更有价值的差别是与已有判断、说明书和能力使用条件比较，而非更多摘要和工具按钮。是否真的更有效，需要同一组真实材料比较，不宣称独占优势。

已有来源与完整方案的详细证据见旧专题索引，仍可针对具体问题查阅；不重新复制 32 项长名单进入主文档。借鉴其采集、解析、来源维护和阅读方式，不默认引入另一套团队/Lib/数据库。

### 6.2 反馈进入原项目和作品

开发者需要理解用户问题和版本反馈；创作者需要理解评论、作品表现与原先的内容假设。先保留实际资料、观察范围和对应交付，再做归并与分析；不因接口未全部接通而阻止手动导入真实反馈。

YouTube 授权条件说明自有分析与对标数据的本质差异。[R12] 平台名称不能代表同样的数据覆盖；没有留存、收入或完整转录，就不能生成看似准确的私有分析。误解、需求、缺陷、赞同和情绪不能都算成同一种信号。

金融类作品可以用于检验数值与断言核查，但不是当前另一个目标用户层或自动合规承诺。个人创作者的特点通过可调整的方法体现，不靠粉丝门槛和行业角色名决定可信度。

### 6.3 轻入口与退出

浏览器主动保存可研究 activeTab 与 Native Messaging 等机制。[R13][R14] 扩展只负责适用的采集和归属，不再建立第二个模型设置和知识系统。私有收藏批量读取、原文/字幕取得要独立验证，不能把页面首屏成功扩大成全量同步。

手机分享、已有资料导入和文件导出应降低迁移成本；完整移动端不是前提。备份需要保留来源、版本与用途关系，恢复需要处理冲突；“复制几个文件”不一定恢复全部状态，也不应打包密码或会话 Cookie。

## 7. 交互与交付质量：研究应回答的具体问题

| 问题 | 候选做法/研究判断 | 需要真实检查的结果 |
| --- | --- | --- |
| 用户回来先看什么 | 用待处理聚合判断、成果和受阻事项，而非全部活动 | 每项可回到原对象，普通过程不抢注意力，未通知与未运行区分 |
| 什么时候团队介入 | 用户从问题、材料、段落或变化发起，继承必要背景 | 换成员不重讲，读全文权限不随一个按钮无限扩大 |
| 怎么体现 Skill | 资产管理、成员能力范围和当前调用三处互相对应 | 加载版本可查，实际工具结果明确，新增技能不需要重建整个项目 |
| 怎样减少交接返工 | 只凭最终材料复述目标、条件、缺口，形成就绪检查 | 暴露真正歧义，而非另写一篇泛泛建议；检查不冒充实际执行 |
| 怎样让结果回流 | 比较目标、说明书、执行与外部条件，记录可检验修正 | 不将一次作品失败升级为永久风格，不把点击数当学习效果 |
| 怎么支持两类用户 | 软件与媒体默认责任/方法不同，共用同一底座 | 创作者不被迫配置 Git；开发者不经过频道设定；两者都能完成真实任务 |

具体布局沿用既有工作台继续打磨；不要为了新增雷达或任务系统重排全部体验。默认可读结论与证据、细节可展开、输入和阅读位置稳定，比多显示几棵 Agent 树更重要。

## 8. 完整研究样本与未决问题

可以用以下完整场景判断组合是否值得，而不只看各组件的功能表：

**个人开发者：** 获准项目资料和一批真实反馈进入团队；形成明确目标与交接材料；专业工具执行后，实际结果回到指定反馈。相似工作能复用以前的方法，不重开技术选型，也不由 ytriple 越权改项目。

**个人创作者：** 代表作品和收藏进入频道/选题；编辑与研究员调用合适 Skill，形成脚本与制作说明；发布后真实评论/报告回到同一作品，更新可采纳的方法而不保证流量。

**例行与服务器：** 一次有效工作转成委托；运行中遇到无新数据、离线、授权失效或方法升级；用户回来仍能分辨已做、没做和待决定部分，原资产不被旧结果覆盖。

尚未证明的重点：真实用户是否接受这些操作；场景 Skill 是否比通用模型减少返工；一个用户的资产如何稳妥迁移；平台账号覆盖；长任务恢复；公开服务成本与用量策略；具体开源许可与依赖安全。默认团队与功能方向已确定，不把这些未决验证重新包装成定位未定，也不把它们写成已全部可用。

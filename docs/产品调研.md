## 2. 团队能力从哪里来

### 可复用的协作能力

| 参考 | 官方资料可确认的能力 | 对 ytriple 的研究判断 |
| --- | --- | --- |
| OpenAI Agents SDK | 提供 Agent 作为工具参与协作，以及由其他 Agent 接管对话的 handoff；两种责任分配不同 [A1] | 可参考“面向团队统一交流”和“直接找成员”两类协作，不必从零重造全部通用能力 |
| Google ADK | 支持协调者与指定子 Agent 协作，以及顺序、并行、循环等工作流形式 [A2] | 可研究固定团队如何灵活处理任务；不要求用户或本项目先造可视化编排平台 |
| MCP | 用于连接 AI 应用与外部数据、工具等系统的开放协议 [A3] | 是能力互操作选项，不等于团队协作本身，也不替代本机 Policy 与授权 |

以上是候选资料，研究结论本身不锁定 SDK，也不要求同时集成多套框架；Codex 的当前选型与验收另见 [开发计划](开发计划.md)。研究应优先判断候选方案能否支撑 AI 与多 Agent 核心底座，并在项目初始化、信息消化和文档产出等真实场景中验证，而不是只比较功能表。

### 协作质量的研究判断

稳定身份应同时有职责、可用工具、资料范围和明确产物，并通过真实模型与工具调用完成工作。用户提出一个目标后，成员能互相委派、追问、交接并使用彼此的成果、指出缺口，再形成统一结果；不能把三次独立生成加一次拼接当作全部协作能力。

需要关注的不是让所有成员看见所有聊天，而是让他们共享当前有效目标和必要事实。用户修改方向、切换成员或隔天回来，都不应要求重新组织整套上下文；不同项目则不能互相污染。首版各场景都应检验这种工作连续性，以及成果是否实际落到正确的项目和文档中。

“常驻”不应造成持续付费调用；小任务由适合的成员处理，多成员协作只在有价值时发生。成本、等待、部分失败和恢复属于体验考量，不据此规定运行时结构。

已有底座上的提升重点，是成员是否提供新证据、补足缺口、纠正判断和复用已完成贡献，而非增加调用数量。用户反复指出的体验问题，应与当前实际工作一起验证；完整交互研究见专项文档，不由这里重新定义面板或消息协议。

## 3. OpenAI 兼容格式与 Google 能力

### 基础模型接入

Google 官方提供 OpenAI 兼容入口，可以沿用 OpenAI 客户端调用 Gemini；同时也提供原生 API。[M1]

研究判断：基础模型调用可保持精简，但工具、引用、文件处理和托管 Agent 不能仅凭“兼容格式”判定完全可替换。当前只围绕兼容接口与有明确价值的 Google 能力验证，不扩成覆盖所有厂商的适配工程。

### Google 值得研究的能力

| 能力 | 已核实的官方描述 | 对产品的意义 |
| --- | --- | --- |
| Gemini Deep Research | 自主进行多步研究并产生带引用报告；支持协作规划、文档输入及部分工具扩展。当前为 Preview，仅通过 Interactions API 使用，不通过普通 generate_content 调用 [M2] | 团队研究员可以委托专门研究服务，而不是自行模拟每个研究步骤 |
| Interactions | 支持服务端会话状态与后台任务；默认存储 interaction，后台执行与 store=false 不兼容 [M3] | 外部研究的任务状态与资料保存范围必须明确；不能把服务端会话当作永久本地记忆 |
| Google Search grounding | 可以利用实时网页搜索并返回引用信息 [M4] | 适合较轻量的事实补足，与长时间 Deep Research 分开考虑 |
| Gemini 文档理解 | 官方描述对 PDF 的视觉与文字内容进行理解，包括图表、表格等；非 PDF 输入的处理并不保证同样保留视觉结构 [M5] | 为研究、资料阅读和文档分析提供候选能力；理解文档不等于保证原格式无损编辑 |

当前 Deep Research 的关键限制：要求后台执行，且要求保存请求；暂不支持自定义 Function Calling 工具和结构化输出，但可使用远程 MCP。[M2] 因而不能假设它直接调用本机所有工具、永不存储资料，或可靠返回任意约定 JSON。

**团队的研究员与 Google Deep Research 不是同一层。** 前者维持用户的工作目标、资料范围和团队协作，后者可以作为受托研究能力。返回报告仍要结合项目事实核查和整理，不能自动变成已采纳结论。

还需实际验证：当前账号与地区可用性、凭据与计费条件、真实延迟、引用质量、任务取消/恢复和文件处理效果。供应商托管任务不一定支持任意时刻原地修改目标，不能仅凭“可协作规划”就承诺运行中可以随意重定向。模型 ID 和版本不在本文写死。

## 4. 本地 Context、文档与工具

用户已明确：本机 AI 目录中的规则是文档与项目管理的依据；ytriple 首版必须接入已有体系，并在新环境缺少目录时实际创建对应目录与完整规则，再初始化项目。实际操作应读取本机当前规则与项目登记。2026-09-11 的调研当时只核查现有规则与配置，尚未实现全新环境的初始化器；此处保留证据时间，不代表当前仍未实现，后续实现与实测以 [开发计划](开发计划.md) 为准。本文不另立一份竞争的全局 Policy。

| 能力问题 | 研究判断 |
| --- | --- |
| 工作台基本功能 | 首版应让用户围绕当前目标、资料、团队贡献和成果持续工作；这些能力与 AI 底座一起验证，不预设页面布局，不推迟到后续版本 |
| 项目初始化 | 首版必备：接入已有 AI 规则体系，缺失时先建立完整体系；团队再按其规则与授权建立项目底座并核查交接。已有、全新、残缺环境分别验证 |
| 读对资料 | 项目归属、文档版本、权威入口和观察时间比“读入更多文件”更重要；检索不能把历史草稿升级为当前规则 |
| 文档处理 | 首版真实场景之一：通过核心多 Agent 交互读取、整理、编辑并继续修订实际文档；区分研究整理、正式成果编辑和复杂格式保真，对不支持的格式或缺失内容明确说明 |
| 项目反馈 | 开发中主要读取状态，把意见写入约定文档，由 Codex 处理；不需要为此建设通用多人文档协同系统 |
| 工具接入 | 优先复用已有本地工具和稳定接口，也允许必要的原生辅助能力；不把无限制 Shell 当作默认方案 |
| 资料外发 | 本地保存、发送给模型、上传给研究服务、导出诊断记录是不同动作，不能用 Local-first 一词掩盖 |

一个容易漏掉的例子：OpenAI Agents SDK 的追踪可以记录模型与工具活动，并在支持的运行环境中默认启用导出；可以配置或关闭。[A4] 研究判断是，采用成熟 SDK 仍须核对其外发行为，而非认为本机程序的数据自然只留在本机。

### 本轮指定资料入口与输出能力核查

以下记录用户指定方向与已有核查结果。此前的专项记录在公开资料核查之外，使用用户登录的 Codex 浏览器只读检查了抖音收藏小样，并在 Chrome 开发者工具中核实收藏请求成功返回批量 JSON 与分页字段；本次雷达文档更新没有复做这些观察，也没有进行程序化完整收藏导入、媒体下载、模型调用或工具安装。本机确认的安装信息与页面/响应小样不等于产品接入测试通过。

| 对象 | 已观察或公开文档支持的能力 | 仍需验证的范围 |
| --- | --- | --- |
| 知乎官方 Zhihu CLI | 官方发布的 Skill 包说明支持近期收藏、收藏夹列表及夹内条目；需本人在官方开放平台生成 Access Secret，不依赖导出浏览器 Cookie。[S1] | 文档列出的收藏结果含标题、摘要和链接；近期收藏及收藏夹列表没有完整分页承诺，不能据此保证全部历史、私密收藏或全文覆盖。实际账号与可取得内容待实测 |
| 抖音收藏与视频链接 | 网页 DOM 小样累计观察到 49 条，含视频与图文；Chrome 实际收藏 POST 返回成功的 `aweme_list`、`cursor`、`has_more`，请求体有 `count: 10`。详见[接入验证](参考/抖音收藏接入验证.md)。官方嵌入能力还可用于标题与播放展示。[S2] | 49 不代表全部收藏总量。程序采集、直接分页重放、大量历史、非空收藏夹及内容补全尚未验证；单条详情未发现 DOM 字幕。现有视频基础信息接口面向授权用户上传的视频，不能当作收藏接口。[P8] |
| GitHub 与 AIGCLINK | 用户确定 GitHub 和作者官方仓库为主源。[AIGCLINK](https://d.aigclink.ai/) 提供带日期、标签、摘要等的 AI 方案目录，抽查条目可见原始 GitHub 链接。[S3] | 聚合目录适合发现线索，能力、版本、许可证和维护状态需回原始仓库核查；不能把目录评分当成已验证结论 |
| Grok Build 与 X | 本机已确认安装 Grok Build CLI 1.0.0；官方更新记录包含 X search，CLI 文档提供无界面与结构化输出接入方式。[S4][S5] | 本机账号、真实搜索覆盖和引用质量待实测；不能直接套用 xAI API 的全部参数与计费，也不能推定可读取私有收藏或登录账号数据 |
| show-me | 已按用户提供的准确链接核对 HumanLayer Skill，支持 Mermaid、单页 HTML 信息图与短幻灯片，适合在成果面板呈现；说明未要求专用付费服务。[S6] | Skill 未提供 PNG 或原生 PPTX 导出流程，需要另接导出能力；宿主模型的费用与可用性另计。本次只读核查，尚未安装或运行 |

调研应围绕“取得材料 → 看清实际内容范围 → 消化并关联 → 形成可用成果”分别验证。前台刷新、本机退出后是否仍能采集、独立服务器持续供给分别判断；旧的前台限制不再作为拒绝独立雷达服务的产品依据，也不表示依赖本机的收藏接入已经支持持续在线。常规文档读取、MD 编辑、信息图和 PPT 产出也分别验收，研究发现的某项工具只承担它实际支持的部分。

既有抖音专项方案以结构化响应与批量分页为主要研究路径，页面 DOM 作备用。此前找到维护者源码线索，并在用户 Chrome 会话中实测收藏 JSON 与请求/响应的分页字段；直接修改游标后的签名有效性及程序采集尚未验证。[接入验证](参考/抖音收藏接入验证.md)区分页面小样、响应实证、源码证据与待实施方案。采集由程序按批次执行、AI 负责材料消化，是该专项的方案参考；具体正式实现与验证仍由 Codex 决定。

长期记忆按产品、工作过程和反馈组织可复用资产；用户习惯从真实使用中逐步提炼，不以先建立个人画像为接入条件。细粒度的本机资料外发配置暂不展开，保留后续实现方式；当前授权边界仍须遵守。

### 反馈闭环，而非直接接管项目

已确认产品边界是：用户在工作台观察项目、讨论意见、形成指定文档反馈，再回 Codex 修改。需要区分“已记录”“已采纳”和“已执行”，但这些区别不等于需要复杂任务管理平台。

反馈不能被自动当作新的项目权威结论，尚无执行证据也不能显示为完成。指定反馈文件存在外部修改时仍需保留未知内容。这一小范围问题保留，不再把广义文档并发编辑作为整个项目的主要障碍。

## 5. 浏览器插件与本地辅助

插件或其他辅助工具是允许研究和开发的能力，不要求全部功能只能通过官方 API 完成，也不要求当前就建立完整插件平台。它们对应雷达“平台与收藏”等接入需要，前台展示平台及其内容，不将工具配置本身作为主要阅读体验。

| 选项 | 官方依据或验证状态 | 用途与边界 |
| --- | --- | --- |
| 用户主动触发的浏览器插件 | Chrome activeTab 可在用户操作后临时取得当前标签页权限 [B1] | 可研究保存、提取和理解用户当前可见内容；不是天然的全站持续访问授权 |
| 插件与本机应用通信 | Native Messaging 支持扩展与注册的本机程序通信 [B2] | 可把浏览器观察接入本地工作台；插件安装和本机辅助程序仍是两部分 |
| 后台扩展任务 | 扩展 Service Worker 有休眠、终止和状态持久化约束 [B3] | 不能把插件视为永不中断的常驻服务器 |
| 其他本地浏览器方案 | 候选，未对目标平台实测 | 可按真实数据需求研究，暂不锁定工具或实现方式 |

研究判断：插件看到的内容与官方 API 返回的数据可能不同，需要保留来源与时间，不把页面暂时不可见当成数据为零。研究、账号管理和浏览器操作的授权应分开；不采集或转移密码、会话 Cookie 等登录凭据，不以绕过访问控制为前提。

本地自用验证与公开分发可以分阶段处理；是否需要额外插件由实际能力缺口决定，不让插件平台本身变成主要产品。

以下只是官方能力线索和待验证范围，没有接通真实账号。当前先建立工作台雏形，再逐步加入监控。

| 平台 | 官方资料可确认的入口 | 暂不能假定的部分 |
| --- | --- | --- |
| YouTube | Analytics/Reporting 面向授权频道的报告；Data API 提供频道元数据及部分统计 [P1][P2] | 自有频道授权不等于对标后台权限；公开视频也不等于可通过官方字幕下载接口取得完整字幕，该接口要求视频编辑权限 [P3] |
| TikTok | Display API 提供用户资料、视频列表与查询；接入要求相应产品批准、scope 和用户授权 [P4][P5] | 展示 API 不等于完整创作者后台或任意对标历史库 |

自己的账号优先尝试官方授权接入；对标账号使用实际可获得的公开或另行授权资料，必要时研究浏览器辅助。不是每个平台都能取得同样的数据，也不应因一个平台暂不可用而阻塞工作台本体。

共同注意：标题/封面分析、视频内容分析、后台经营分析是不同证据层；拿到前者不能声称完成后两者。比较还要考虑内容发布时间、观察窗口、内容格式与缺失值；没积累历史就不能制造过去的完整趋势，相关性不等于因果。

公开账号更新可纳入雷达的信息供给，但不等于承诺完整经营分析。账号管理包含对象组织、分组、授权状态、监控与复盘，不自动包含代用户发布或互动。公开分发与商业使用时应再核查接口用途、保留/删除、应用审核和平台条件；现阶段不铺开复杂合规工程，但自用不改变接口本身的权限条件。

### 信息源与整体解决方案：2026-09-12 专项建议

详细能力事实、来源、许可证和限制统一见 [信息源与知识工作台方案调研](参考/信息源与知识工作台方案调研.md)。下面只提炼与当前阶段相关的研究建议，不能把“值得借鉴”解释成已经选定、安装或验证。专项早先关于服务器只是候选的判断，已由《讨论总结》本轮确认的独立雷达方向更新；组件证据仍按原记录保留。

| 要解决的问题 | 重点参考对象 | 值得吸收的产品行为或能力 | 对应专项位置 |
| --- | --- | --- | --- |
| 积压收藏来不及看 | Readwise Reader、Karakeep | 从一批材料发起筛选与综合，保留理由和引文；让团队处理集合，不逐篇要求用户发 Prompt | 第 3.1、3.4、7.1 节 |
| 每天读什么、什么是新知识 | Inoreader、Folo、Feedly | 预置来源发现、按主题整理和持续报告；在本产品中进一步突出与已有知识的差异，而非重复推送摘要 | 第 3.2、3.3、7.3 节 |
| 资料与原文依据留在哪里 | Linkwarden、Obsidian Web Clipper | 可携带的本地内容、批注与来源位置；理解有疑问时可以回到证据 | 第 3.4、3.5 节 |
| 从资料变成可用知识和说明书 | NotebookLM、Open Notebook、BettaFish | 围绕主题资料做不同目的的转换，不同证据角色共同修正报告；保留当前 ytriple 团队 | 第 3.6、3.7 节 |
| 持续来源如何取得 | RSSHub/Radar、FreshRSS、Miniflux | 分开来源发现、转换、增量订阅与内容管理；来源服务可以独立，但用户不必再维护第二个工作台 | 第 3.9、4、8 节 |
| 内容提取不完整怎么办 | Defuddle、Trafilatura、Crawl4AI、Firecrawl、Jina Reader、Docling | 按公开正文、动态页面、远端采集和复杂文件的真实缺口选择候选，明确覆盖与运行代价 | 第 2.3、5 节 |

**组合取向是研究建议，不是架构命令：** 保留当前工作台；对独立雷达服务比较合适的聚合、来源维护、整理和推荐能力，对个人来源与平台收藏比较适合的本地或授权输入桥梁。完整开源知识产品也可以研究，但不默认把它的 UI、团队、数据库和 Lib 一起搬进来。借鉴功能、复用代码、连接 API 和部署完整服务，是四种不同选择。

**消化深度要分开：** 相同条目重复导入、近重复正文、同一事件的多份报道、与已有知识重复，不能用一个去重按钮混为一谈。保留新证据与不同观点；对已有主题交付新增、补充条件、冲突或修正，而不只是另存一篇摘要。过滤默认不删除源端收藏，未取得内容不等于没有价值或已被删除。

**后续用户来源直接补入已有框架：** 记录准确地址、来源角色、关注理由、实际内容与历史范围、授权条件、证据时间、上游依赖和预期资产用途。预置源包与用户自带来源共用这些语义；可以先少量做深，不要求把全部调研候选同时开发。私有收藏、公开 Feed、工具目录和平台后台数据分别判断，不因一个站点有 RSS 就认为它覆盖本人历史收藏。

**整体体验与价值一起看：** 把材料消化、原文核查、成员追问、Lib 更新和下一次说明书产出连接起来；沿用现有工作台，不重复建设独立阅读/聊天应用。能力候选与已验证工作流分开，最终由实际使用和修正判断价值，而非收藏数、摘要数或调用次数。

## 8. 独立雷达服务、成熟方案与其他托管候选

### 已确认方向与研究边界

独立信息订阅服务与 ytriple 客户端的关系、三类来源及丰富分层阅读已由用户确认，产品正文见《讨论总结》第 4、6 节。服务器可以单独升级，个性化和信息源能力优先研究已有方案；独立仓库还是分支、具体接口与推荐实现由 Codex 设计，本文不指定服务协议、数据表或工程任务。

下面补充于 2026-09-12，依据官方文档和维护者仓库；本轮未安装、未接入 ytriple、未验证真实账号与推荐效果。候选方案有可复用能力，不等于已经适配本产品，更不能把组合后的整体质量当成已验证事实。

### 信息供给、阅读与推荐的现成参考

| 研究对象 | 本轮官方资料支持的能力 | 对雷达的研究判断与待验证部分 |
| --- | --- | --- |
| FreshRSS | 自托管、多用户、RSS/Atom 聚合、过滤搜索、OPML 和客户端兼容 API。[R1] | 独立订阅聚合服务候选；比较来源管理和客户端承接能力，不将它视为现成的个性化情报整理服务 |

**研究判断：成熟能力应按职责复用，而不是寻找一套万能系统。** 信息来源与增量订阅、正文提取、内容组织、推荐、浏览器辅助分别比较；公共材料的获取与整理可以研究复用，私人收藏和私人背景保持独立授权与数据边界。产品需要自己的订阅语义、证据质量和阅读体验，不必因此从零重造全部基础组件，也不应把多个完整产品直接堆到客户端。

### 个性化：比较方案，不预先指定算法

用户明确的主题、关注目的和反馈可以作为方案比较的基础；Gorse 等引擎提供的是可研究的实现路径，并非已经证明优于较简单的方案。研究应区分选出哪些内容、如何排序、怎样说明个人相关性，以及怎样理解用户纠正，不把“不断学习”直接等同于必须反复训练大模型。

对实际产品需要验证：不同订阅是否互相污染；“已经知道”“内容太基础”“暂时不需要”和“不关注”能否区分；偏好变化与明确修正是否生效；是否保留重要变化、不同观点和探索范围。点击或停留只能作为待解释的信号，不能单独证明有用；结合真实使用结果评价，而非只看点击提升。这里是研究判断，不是本轮完成的推荐测试，也不指定评分公式或训练流程。

### 独立信息服务与平台接入的待验证问题

| 问题 | 研究与验证关注点 |
| --- | --- |
| 来源持续可用 | 媒体、特定网站和公开账号分别能持续取得什么；正文、摘要、历史和新增覆盖是否清楚；来源失效能否被发现，不以来源数量代替质量 |
| 内容整理质量 | 区分转载重复、同事件的新证据、不同观点与事实纠正；保留原始出处和观察时间，缺正文时不声称完整理解 |
| 统一阅读与独立升级 | 来源分组、跨来源主题、不同媒体与专题之间能否衔接；新增服务类别能否由客户端承接，不能只验证接口可连通 |
| 供给、通知与本地运行 | 持续整理、用户读取结果和弹出通知分别评价；设备不在线或本机插件停止时如实表现，避免把积压旧通知当新变化 |
| 平台辅助覆盖 | 逐一比较官方工具/API、浏览器扩展或其他获准方式；账号授权、收藏列表、完整历史、正文与音视频理解分别计证据 |
| 运营、成本与许可 | 比较公共处理复用、个性化加工和深度研究的维护代价；核查选定版本许可证、来源商业交付条件与 API 限制，不直接从开源或公开可读推定服务可用 |
| 私人信息与可退出性 | 私人收藏、Lib、项目和个人偏好只在必要且获准范围使用；不默认进入共享内容池，取消托管后保留已有本地资产与个人来源能力 |

已有详细信息源专题继续作为来源和组件证据，本节补充独立服务与推荐视角；不另建第二套工程计划。研究结论应明确是借鉴交互、复用组件还是连接外部服务，真实效果留给接入和使用验证。

### 其他可选托管服务

AnythingLLM 的桌面、自部署和托管形态提供了相邻参考。[C4] 但它不能证明 ytriple 应采用相同商业模式，也不能替我们确定收费项目。独立雷达是已确认方向；以下是雷达之外的候选判断，不是已确认开发任务：

| 候选能力 | 托管价值 | 仍需验证的边界 |
| --- | --- | --- |
| 超出雷达的通用持续监控与定时情报 | 用户电脑不在线时，获准在服务器运行的处理仍可继续 | 对象是否适合服务器访问、授权维护与运行成本；不能假定依赖本机登录态的插件会因此继续运行 |
| 长时间研究任务 | 统一管理适合远端运行的任务与结果，减少用户维护 | 部分供应商本身已提供后台执行 [M2][M3]；不能只把转发包装成不可替代的收费能力 |
| 文档与媒体资料处理 | 重任务不占用用户本机，维护服务可作为价值 | 敏感资料是否适合上传、处理质量与成本；保持本地或自部署选择 |

本地、自部署和官方托管之间应保持同一工作语义与可继续使用的成果，不用私有数据格式制造锁定。离线、本机暂停、远端仍在运行和真实失败需要区别呈现。

自部署 ytriple 的服务，不等于自部署 Google 的托管研究 Agent；第三方凭据、API 费用、条款和可用性仍然存在。开源许可证、组件许可证适配、具体套餐与收费方式尚未确定；确认雷达方向不等于服务已发布，也不授权当前公开仓库。

## 9. 后续调研应持续回答的少量问题

1. 在初始化、信息消化与文档产出等真实场景中，模型和工具调用、委派追问、成果交接是否有效，团队是否真正减少用户协调负担？
2. 工作台能否围绕当前目标、资料和实际成果继续工作，切换成员、修改方向或隔天恢复时仍共享必要上下文？初始化和文档修改是否落到正确位置？
3. 基础兼容模型与 Google 专项能力分别能可靠完成什么，成本、资料外发和 Preview 变化有什么影响？
4. 项目反馈是否进入正确位置，和已采纳结论、已执行变更分开，且不越权修改开发项目？

这些问题用于产品与能力判断，不扩写成代码架构、接口、表结构或开发排期。新资料可以更新本文，也可以作为独立参考；只有用户采纳的方向进入讨论总结。

## 分阶段开发路线

阶段按能力依赖安排，不按页面逐个做孤立样板。第一阶段交付可运行骨架和真实核心能力，后续逐步补齐完整用户路径。阶段可包含多个增量；不以阶段名称或入口已经出现推定功能完成。

| 阶段 | 建设内容与新增可用结果 | 主要依赖 | 阶段完成依据 |
| --- | --- | --- | --- |
| P0 文档与工程设计 | 校准完整产品、模块责任、数据关系、当前路线；设计独立编排核心及其事件契约，选定桌面壳、运行时、存储与模型适配实现 | 当前任务 | 文档无冲突，关键技术选择有依据；未知事项有归属，不需要把所有远期参数一次定完 |
| P1 项目骨架与协作核心 | 独立服务与桌面客户端，可选本地模式；统一工作／运行／成果；独立可升级的默认团队流程；角色和能力配置；真实委派与汇报；三窗口基本联动、处理步骤与多轮修正、Markdown 成果、停止与重开；基础 Skill 和过程总结／阶段复盘 | P0 的相关工程设计 | 见下方 P1 任务及验收；必须有真实团队、过程学习和实际 UI 证据，不能只有静态壳或预设对话 |
| P2 成果处理与日常工作 | 完善材料捕获、独立工作命名／找回／归档、首页开始／继续／处置；成果编辑、版本比较、就绪检查、导出／交接与基本备份恢复 | P1 的身份、持久化与版本机制 | 工作切换不丢草稿；局部修订准确；历史与当前版本清楚；可把真实成果交出去并恢复自己的资料 |
| P3 项目、资产与反馈 | 软件方向优先接入“产品共创 → 标准初始化 → Codex 接手”，再完善既有项目的全面理解、状态与固定建议；媒体频道、作品及版本；Lib 查找复用、流程草案与局部反馈复用；轻量交付列表 | P2 的材料、成果和交接 | 新项目初始化有真实产品内容及明确接续点；已有项目读取覆盖可核查、建议不越界；创作路径和有范围的复用逐步验收，不宣称 Agent 自主进化已实现 |
| P4 雷达与来源消化 | 来源识别与管理、真实内容取得、栏目／议题阅读、收藏去重与主题理解、增量更新、与项目及 Lib 关联 | P2；复用资产与项目上下文部分依赖 P3 | 选定真实来源，记录读取覆盖与失败；获得可纠正的主题理解而非批量摘要；普通阅读无需建工作 |
| P5 定时任务与持续工作 | 独立任务入口、两种创建方式、触发条件、方法版本、运行历史、用量、暂停／停止、首页归并、通知与可靠恢复 | P1 运行机制、P2 处置入口，以及被委托的实际业务能力 | 无新输入、重复触发、离线、未知远端结果和权限变化不导致假成功或重复执行；执行位置和边界真实可见 |
| P6 托管服务与订阅完善 | 信息服务、AI 能力服务、账户与权益、获准远端委托、自部署与数据控制；分别接入已有客户端能力 | P1 已建立的服务和多端基础、P4 信息模型；托管任务依赖 P5 | 本地资料不被订阅锁定；服务器只处理获准数据；独立信息服务与远端任务按各自实际能力验收 |
| P7 覆盖扩展与深化 | 更多来源与平台、文档格式／信息图／演示、浏览器与移动分享、Skill 导入与方法维护、MCP、Google/Gemini 原生专项能力、日历和长期方法改进 | 对应已有模块稳定可用 | 每项扩展声明输入、编辑、预览、导出及真实调用边界，沿用原对象和反馈关系；不另造竞争体系 |

P4 的来源取得可在 P2 后与 P3 并行，前提是材料接口已稳定；服务／客户端边界已按 USER 决定提前至 P1，P6 承接账户、权益及托管服务完善。软件方向的初始化优先级不改变软件与媒体并列定位，也不把完整初始化业务追加为 P1 必须同时交付的内容。是否提前某项平台、后台或服务能力由实际使用需要决定，调整时同步依赖与验收，不恢复为全部一次交付。七层产品成熟度不是这张路线图的开发顺序。

## P1：骨架与核心能力的可执行拆分

以下为 CODEX 对 USER 所定第一阶段方向的工程拆分。P1 的代表性任务用于证明基础真实可用，不要求完成全部项目管理、雷达、生产交接和长期学习流程。

| 任务 | 交付内容 | 依赖 | 验证与完成条件 |
| --- | --- | --- | --- |
| F1 工程与应用壳 | 服务与桌面项目结构、启动／构建／检查入口、模块依赖检查、基础导航与工作空间、明确空态；相关技术选择写回 ARCHITECTURE | P0 | 目标开发环境能启动和构建；没有数据的页面不显示虚构统计，尚未接入的入口明确状态 |
| F2 工作对象与执行端持久化 | 工作、目标修订、运行、成员任务、过程记录、材料引用、成果版本与设置；统一读写入口及数据升级机制 | F1 | 重开能恢复已保存的工作、过程、成果和编辑草稿；记录能关联准确目标与版本；凭据不混入正文或日志 |
| F3 模型与能力通路 | 服务器统一配置与本地可选的一条实际可用模型适配路径、能力差异描述、流式返回、失败／用量记录、授权检查和调用替身 | F2 | 服务端配置 Gemini 或 OpenAI 兼容提供方后，客户端可真实调用；缺少配置如实显示；不把接口兼容当成专项能力支持 |
| F4 独立协作编排核心 | 以默认团队组织多视角工作，负责成员委派、追问、利用返回并汇合；策略与角色／能力配置分离，通过统一事件和能力入口运行；支持直接找成员及纠正目标 | F2、F3 | 不经业务页面也能验证编排；真实委派与结果利用可见；变更配置或替换策略不改业务页，不丢工作身份和历史版本；简单任务仍在团队上下文中完成 |
| F5 三窗口与过程学习 | 主窗交流和结论，思维窗成员关系及实际步骤／方法／要求，结果窗真实 Markdown 成果；多轮修正、按对象追问、同一成果修订、过程总结／阶段复盘 | F4；应用布局可与 F3 并行 | 用户能就未达要求的步骤追问，并看懂修正如何影响后续结果；角色变化可辨认；旧结果不抢焦点或覆盖草稿；公开分析和事后解释边界明确 |
| F6 基础 Skill 与恢复 | 至少一个实际使用的方法型 Skill，记录版本和作用；停止、异常、重开与迟到结果处理 | F3、F4；UI 观察依赖 F5 | 缺依赖不伪装执行；停止请求与实际结果分开；重放不重复记成果，未知结果不盲目重试 |
| F7 集成、审查与本地交付 | 整合 F1～F6，独立审查修复，提供真实启动／使用说明、验证证据及可运行开发产物 | F1～F6 | 自动检查、实际 UI 操作、获授权真实模型调用分别记录；USER 可以运行并体验骨架与核心，未实现业务明确列出 |

技术栈、存储库、进程组织和测试框架由 CODEX 依据本地文件访问、模型调用、流式事件、恢复及打包需求选择。先做必要的代表路径检查再扩大实现，不要求 USER 逐个选库。首个运行环境建议使用当前 Apple Silicon Mac；正式首发平台与发行方式仍按实际交付阶段明确，本机验证不冒充跨平台通过。

## 软件项目能力的接入顺序

在骨架和基础成果能力可用后，软件方向按以下顺序逐步接入；可与媒体工作并行，不要求所有项目能力一次齐备。

| 增量 | 新增能力与依赖 | 验收重点 |
| --- | --- | --- |
| S1 产品共创与初始化 | 复用默认团队、方法与成果修订，把目标、主要使用方式、约束、取舍和验收写入标准项目材料；依据项目 Policy 初始化目录、规则及必要文档 | 模板含真实讨论结论，未决技术问题有接续位置；不让用户重抄聊天，不覆盖既有冲突目录 |
| S2 专业工具接手 | 对 S1 的初始化结果检查交接就绪，交给 Codex 等开展工程设计和开发 | 接收方能从明确入口理解目标与下一步；材料齐全、实际接手和实际执行分别有证据 |
| S3 已有项目理解与状态 | 全面读取获授权项目，建立内容覆盖及版本记录，再随变化更新理解；复用原工作和成果关系 | 源码、配置、测试、文档等实际内容支持状态判断；未读范围清楚，不能用索引代替读取 |
| S4 固定建议与反馈 | 基于 S3 状态，在一个固定项目文档持续写建议，关联后续专业工具执行和用户反馈 | 既有建议保留；不直接整改项目；反馈可用于修订当前材料或形成方法草案，不据此声称完整学习机制已经成立 |

模板的目录、文件名称和适配方式由 CODEX 按现行项目规则设计；标准化的是产品内容、规则和交接关系，不把所有产品锁在一个技术框架。模板生成和既有项目建议写入分别验证，避免混用写入权限。

## 整体设计中的问题与讨论建议

这些问题影响后续体验，需要保留讨论；其中已能依据产品约定处理的部分由 CODEX 直接落地，不作为当前文档工作或骨架开发的统一阻塞。

| 问题 | 为什么值得讨论 | CODEX 的建议与决策归属 |
| --- | --- | --- |
| 默认团队怎样呈现清楚的方法与合作 | 默认团队与学习目标已确认，具体流程仍需在真实内容上验证；固定全员发言或重复长文会削弱体验 | CODEX 设计可替换的编排策略和过程表达；观察用户能否说清方法、定位不足和利用修正，同时记录耗时与用量。USER 体验验收，不重新讨论要不要默认多 Agent |
| 标准项目模板怎样帮助接手 | 新建初始化的核心地位、全面理解已有项目与固定建议边界已确认，模板细节尚需设计 | CODEX 准备带真实产品内容的代表模板，核对讨论到文件再到 Codex 接手的关系；缺少工程决定明确留给专业工具。只在改变主要使用方式或写入边界时请 USER 决定 |
| 用户成长与 Agent 改进如何逐步验证 | 用户成长是确定目标；Agent 的学习进化机制尚未确定，不能把一次反馈复用等同于全部进化 | P1 先支持观察方法和多轮定位问题，后续逐步做流程草案、局部反馈复用及方法改进；用真实工作检验效果，技术路线由 CODEX 持续研究与提案，无需 USER 先给出学习算法 |
| 自动化能替用户做到哪一步 | 不重复弹授权与“不自动扩大权限”需要同时成立；长期任务还会遇到方法和来源变化 | 以工作／持续委托中清楚的资料范围、动作、用量与执行位置沿用授权，越界才集中确认。具体默认用量和方法升级体验在 P5 设计时讨论，不现在填一张全局权限表 |
| 官方托管的运营边界 | 服务端统一配置、客户端订阅方向已确认，P1 单用户自部署不等同于运营级托管 | CODEX 在 P1 建独立服务与桌面客户端，手机后续复用服务接口；P6 前再确定账号、权益、套餐和服务承诺 |
| 雷达必须取得哪些内容才有价值 | 网站正文、平台收藏、字幕、经营数据的覆盖不同，手工导入不能证明自动接入 | P4 前依据 USER 日常资料选首批真实来源；先按“取得什么、如何更新、缺失时怎样处理”定义覆盖，再实现连接。具体平台和必需来源届时由 USER 确定 |

已直接澄清的边界：PRODUCT 第 7.2 节区分工作草案、项目正式正文和反馈路径；草案修订不表示正式文件已改。“说明书”是广义成果概念，具体界面可以使用报告、脚本、交接材料等真实名称，不因统称额外制造文档或页面。

## 验收覆盖与证据要求

现有 AC 保留为整个产品的验收定义，阶段逐步覆盖。同一 AC 可能横跨多个阶段；基础部分通过不能将整条场景标为完成。

| 能力组 | 验收场景 | 主要承接阶段 |
| --- | --- | --- |
| 低门槛开始、成员协作与三窗口 | AC-01、03、04、11、12、16、18、22 | P1 建默认团队及可升级核心，P2／P3 补齐真实业务与高级操作 |
| 成果与工作连续性 | AC-06、10、17、20 | P1 建版本和恢复基础，P2 完整编辑、交接与数据恢复 |
| 项目、媒体与成长 | AC-02、07、08、13、21、23、24 | P1 支持过程学习、总结／阶段复盘，P3 验证初始化接手、全面理解、固定建议和方法复用 |
| 服务配置与手机工作入口 | AC-25、26 | P1 验证服务与桌面，AC-26 在桌面完善后启动手机阶段验收；P6 完善账号、权益与托管 |
| 信息消化 | AC-05 | P4 |
| 首页、定时与状态一致性 | AC-09、14、15、19 | P2 建入口及处置；P5 验证真实长期委托和跨入口一致性 |

自动检查覆盖身份、版本冲突、范围隔离、事件重放与恢复；UI 实际操作覆盖三窗口对照、追问、编辑和焦点；真实调用覆盖能力、委派与公开分析；实际使用反馈覆盖交接与改进效果。测试替身、受控异常、真实调用、目标环境与 USER 验收分别记录，不相互冒充。多人一致或日志数量不能证明判断正确。

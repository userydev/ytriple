## 为什么投入没有及时变成可用结果

1. 范围没有冻结。桌面逻辑、UI、账号、云端存储、授权和运行宿主交替展开；发现问题就再开一层，没有先交付有限版本。
2. 先补模块，后验完整路径。远端模块各自存在，但没有桌面入口与 HTTP 控制联通；这类投入不能算用户已获得能力。
3. 验证环境存在落差。后台授权单元夹具未开启真实 Auth 的 RLS，造成局部测试通过、真实环境失败；现已复现并修复，但暴露出验证选择问题。
4. 版本管理滞后。ytriple 本次一次性补入 154 个文件，说明可追溯提交间隔过大。长期未跟踪实现增加恢复、审查和交付成本；不以本次新增行数证明产出质量。
5. 状态文档只追加、不替代。早期“工程清空”和历史失败与后期进展并列，读者难判断当前事实；本次重写 PLAN，DELIVERY 明确标识历史部分。
6. UI 按功能堆叠。对象关系、入口与返回规则没有始终先于视觉，导致反复调整卡片、边框与排版，却没有消除操作负担。
7. 缺少停止条件。检查、修复与扩展形成循环；用户要求阶段总结后又继续实现，进一步破坏进度控制。

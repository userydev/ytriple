# yTriple 产品需求文档（PRD V1）

## 文档信息

- 产品名：yTriple
- 口号：Three Agents, One Perfect Output.
- 文档版本：V1
- 文档状态：Draft Baseline
- 适用阶段：0 -> 1 产品定义

## Problem Statement

很多产品想法并不是“完全没有内容”，而是长期停留在模糊表达、零散讨论和不成文档的状态。团队或个人往往会遇到几类典型问题：

1. 想法模糊，用户自己也说不清，前期追问很多，但信息质量并没有明显提升。
2. 需求讨论可以持续很久，但最后落到正式 PRD、方案稿或执行文档时，经常结构不完整、方向不稳定。
3. 调研、专业判断和最终成稿分散在不同对话或不同工具里，导致结论难以复用，也难以形成正式交付物。
4. 普通单 Agent 聊天产品更擅长回答问题，不擅长把模糊输入稳定收束成一个可继续迭代的正式文档。

yTriple 第一阶段要优先解决的，不是“让 AI 更能聊”，而是“让模糊需求更快落成一份有方向的正式文档”。

## Solution

yTriple V1 是一个面向文档落地的桌面端 AI 协作工具。它首先聚焦 `PRD 首稿产出` 这一条高价值链路：

1. 用户用自然语言描述一个模糊需求或产品想法。
2. 系统进行一次极轻量的 `Quick Clarify`，只在必要时补 0 到 2 个关键问题。
3. 主 Agent 把任务拆解给两个固定副 Agent：
   - `Researcher`：做轻量 Web 调研，补足关键事实、概念和少量竞品样本。
   - `Specialist`：根据模板切换专业视角，例如产品专家、架构专家、营销专家。
4. `Conductor` 负责审查、合并、收敛，输出一个可继续迭代的第一版交付包。

V1 的核心不是一次性写出最完整答案，而是先快速给出方向正确、结构完整的第一版正式产物，让用户据此再修正。

## Product Definition

### 产品定位

- 形态：桌面端独立效率工具
- 阶段定位：文档落地工具，而非泛用聊天工具
- 首个核心场景：PRD 首稿交付
- 核心价值：把模糊输入快速收束成正式文档和参考资料包

### 核心用户假设

- 经常需要把想法、需求、方案整理成正式文档的个人用户或小团队
- 输入往往模糊、不完整，但希望快速拿到一个有方向的第一版
- 不想在前期被复杂表单或过多追问打断
- 希望 AI 既能调研，又能提供专业判断，还能最终整理成文档

### 核心体验原则

1. 先给方向，再求精确。
2. 先产出，再追完整。
3. PRD 是主产物，过程材料是参考资料。
4. 用户需要被轻量引导，而不是被前置审问。
5. 首稿允许带假设前进，但必须显式暴露未决问题。

## V1 Scope

### 首版聚焦

- 只优先解决 `PRD 首稿产出`
- 只采用固定三 Agent 工作流
- 允许模板扩展，但首个一等公民模板是 `PRD`
- 允许工作区只读上下文
- 允许新建输出文档

### 明确不做

- 不做用户可编排 Agent 工作流
- 不做 Git 能力
- 不修改用户现有文档
- 不做团队协作、评论、共享会话
- 不做深度研究报告型产品

## Core Workflow

### Fixed Tri-Agent Workflow

```text
用户自然语言输入 + 可选工作区上下文
                 |
                 v
Conductor 判断任务类型并做 Quick Clarify
                 |
                 +--> Researcher: 轻量 Web 调研
                 |
                 +--> Specialist: 模板化专业视角审查
                 |
                 v
Conductor 审查、合并、收敛
                 |
                 v
输出 PRD 终稿 + 独立参考资料
```

### Quick Clarify 策略

- 默认先尝试直接执行
- 信息模糊但仍可推断时，允许系统带假设前进
- 只有在无法判断产品对象或目标时，才追问最关键的 1 到 2 个问题
- 首轮确认的目标不是补齐信息，而是避免明显跑偏

### Agent 职责

#### Conductor

- 识别当前任务是否属于 PRD 交付
- 决定是否发起 Quick Clarify
- 把任务拆解为调研任务和专业审查任务
- 对 Researcher 与 Specialist 的结果做审查与收敛
- 负责输出最终 PRD 和配套参考文档

#### Researcher

- 进行轻量 Web 调研
- 补足关键概念、公开事实、术语解释和少量竞品样本
- 不追求深度行业报告
- 为 PRD 提供必要但轻量的事实支撑

#### Specialist

- 不固定单一身份，而是按模板切换专业角色
- PRD 模板下默认使用产品专家视角
- 后续可增加架构专家、增长顾问、品牌顾问等角色
- 负责指出结构问题、缺失项、范围风险和专业判断建议

## User Experience

### 入口模式

- 采用 `自然语言开始 + 轻量结构化确认` 的混合模式
- 用户先直接说想法
- 系统识别任务类型后，必要时补少量关键问题
- 不要求用户先选模板再填写完整表单

### 输出形态

一次任务的核心不是一条聊天回复，而是一个交付包。V1 默认输出：

- `01-final-prd.md`
- `02-assumptions-and-open-questions.md`
- `03-research-notes.md`
- `04-specialist-review.md`

其中：

- `01-final-prd.md` 是唯一主产物
- 其他文件是独立参考资料，不混入 PRD 正文

### Tri-Panel Layout

#### 左侧舱：Research Workshop

- 展示 Researcher 的轻量调研轨迹
- 可显示关键词、来源、摘要片段和竞品样本
- 开启 Web 能力时显示联网状态

#### 中间舱：Conductor Nexus

- 展示用户与 Conductor 的主交互
- 承载 Quick Clarify、任务分派、收敛总结和最终交付入口
- 保持结果导向，避免过程噪音淹没主线

#### 右侧舱：Specialist Workshop

- 展示 Specialist 的专业视角审查过程
- 可显示问题清单、结构建议、范围风险和专业判断
- 重点服务于“首稿质量提升”，而非纯挑刺

## Templates

### PRD 模板

V1 的核心模板为 `PRD`。它不只是一个提示词，而是一份固定 contract，至少包含：

- 目标文档类型
- 默认 Specialist 角色
- 调研策略
- 输出结构
- 假设和未决问题记录方式

### 模板扩展原则

- 模板可以逐步增加
- 每个模板仍复用固定三 Agent 工作流
- 变化的主要是 Specialist 角色、调研重点和输出结构
- V1 不开放用户自定义编排

## Capability Decisions

### 模型接入

- V1 优先使用聚合模型 API，例如 OpenRouter，统一接入多模型
- 产品层不依赖某个 provider 的原生 agent 产品形态
- 模型层负责推理、结构化输出和工具调用建议
- 产品层自己掌握工作流与权限边界

### Agent 运行时

- 不采用可编排式图工作流作为首版核心形态
- V1 优先使用轻量固定编排 runtime，而不是重框架
- 核心流程固定为 `Conductor -> parallel(Researcher, Specialist) -> Conductor`

### 本地上下文

- 采用工作区只读模式
- 可读取用户指定工作区中的文件与文本内容
- 可基于工作区材料辅助生成 PRD
- 不修改工作区中已有文档
- 允许创建新的输出文档

### Web 能力

- Web 是 V1 必选能力
- 仅用于轻量调研，不用于生成深度研究报告
- 重点支持概念补足、事实补足和少量竞品样本

## User Stories

1. 作为一个想法还不够清晰的用户，我希望不用先填写完整表单，也能快速拿到第一版 PRD，这样我可以先看方向再修正。
2. 作为一个产品发起者，我希望系统先帮我形成正式文档，而不是不停追问细节，这样推进更快。
3. 作为一个经常写 PRD 的用户，我希望系统自动补一些必要事实和竞品参考，这样首稿更扎实。
4. 作为一个不擅长结构化表达的用户，我希望主 Agent 帮我把零散想法收束成正式文档，这样我能更快进入下一步。
5. 作为一个需要专业判断的用户，我希望除了调研外，还有一个专业角色帮我审视范围和结构，这样首稿不至于太空。
6. 作为一个重视结果的用户，我希望最终交付的是 PRD 正文和独立参考资料，而不是一长串聊天记录。
7. 作为一个注重隐私和边界的用户，我希望系统只读我的工作区，不直接改已有文件，这样我更放心使用。
8. 作为一个高频用户，我希望第一版结果尽快出来，即使它还带着部分假设，这样我能边看边修。
9. 作为一个桌面端用户，我希望系统原生支持工作区上下文和文档输出，而不是只会网页聊天。
10. 作为一个后续要扩模板的用户，我希望未来能逐步增加不同专业角色，但仍保持固定三 Agent 的简单工作流。

## Implementation Decisions

### 产品边界

- V1 不是通用开发 Agent，也不是深度研究平台
- 它首先是一个面向 PRD 首稿交付的桌面文档工具
- 核心衡量标准是“是否更快产出方向正确的正式首稿”

### 运行架构

- 桌面端容器优先采用 Tauri
- 前端可优先考虑 React，但最终框架选择不应改变固定工作流与输出 contract
- Agent runtime 保持轻量，核心逻辑由产品侧掌控

### 文档交付

- 最终 PRD 单独成稿
- 参考资料与审查意见独立成文
- 首版产物必须支持后续人工修改与二次生成

### 结果状态

- 首稿允许以“方向版”状态交付
- 系统需要显式记录假设与未决问题
- 不应把信息不足的首稿伪装成完整定稿

## Testing Decisions

### 什么是好的测试

- 优先验证用户能否快速获得一个结构完整、方向合理的 PRD 首稿
- 优先验证工作流行为与文档交付结果，而不是内部 prompt 细节
- 优先验证轻确认不会把用户卡在前置收集环节

### 初期优先测试的模块

- PRD 任务识别是否稳定
- Quick Clarify 是否能在少量问题内启动执行
- Researcher 是否只做轻量调研而不过度发散
- Specialist 是否按模板提供稳定的专业视角
- Conductor 是否能稳定输出四份交付文档
- 工作区只读与新文档写入边界是否正确

### 建议的验证层次

1. 流程层：验证固定三 Agent 编排和最终交付包生成。
2. 工具层：验证工作区读取、Web 调研调用和新文档输出。
3. 端到端层：验证用户从模糊输入到获得 PRD 首稿的完整桌面体验。
4. 样例集层：用一批模糊需求样本验证“快首稿”是否真的成立。

## Out of Scope

- 用户自定义 Agent 拓扑或 LangGraph 式可编排工作流
- Git 读取、diff、提交分析和代码审查能力
- 修改现有本地文件
- 团队协作、共享空间、评论流和多人同步
- 多行业一次性覆盖
- 深度研究报告和完整咨询交付
- 插件市场和复杂第三方生态

## Further Notes

### 当前产品判断

- yTriple 的首个差异化不在“多模型”，而在“模糊需求 -> 正式首稿”的固定闭环
- 如果首版做成泛聊天工具，这个产品会失去焦点
- V1 最应该证明的是：它能否比普通聊天工具更快地产出可继续修改的正式 PRD 首稿

4. 首稿状态命名是否采用 `Draft Directional` 等分级

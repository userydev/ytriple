# 产品实现偏差复盘

2026-09-13。依据当前产品正文、开发计划、三个关键历史版本与当前项目状态/过程代码进行根因审查。本次不开发、不运行模型，不把代码阅读当作全产品实测或市场验证。本文记录工程责任与证据，不另建产品定义或开发路线。

## 结论

此前读过文档、检查过实现、做过界面评价，但审查不合格：大量检查回答了“有没有接入、能否运行”，没有据此判断目标用户是否已经能完成产品承诺的工作，也没有让方向性失败阻止继续投入。

主要原因是产品要求在工程拆解中被降低，已有任务/事件/文件模型反过来限制了产品功能，工程验证又没有发现或阻止这种替换。“反复修补”是这条决策链的结果，不是根因。当前开发计划不足以指导并证明完整产品目标实现。上一轮立即判断“只需重做界面层”也过早，项目持续状态和复盘等问题涉及功能行为与数据表达。

## 产品原本要实现什么

目标用户是并列的个人开发者、个人自媒体创作者。共同定位为个人 AI 工作台：团队先理解获准资料和目标，帮助用户判断、形成可交给人和工具使用的成果，在实际使用后吸收反馈，减少下次工作的重复解释和返工。

雷达负责有依据的信息理解；项目承接持续目标、工作进展和交付；资产保存可复用知识、方法与能力。多 Agent、Skill、多窗口服务这三类工作的理解、干预与接续。例行、待处理、交付检查和服务端支撑它们。共同价值应体现在理解、交接、接续和改进上，而非文件、对话、成员或页面的数量。

这一方向在[产品定义](讨论总结.md)第 1–3、11、13 节已有清楚陈述。文档能够说明立项意图，不能单独证明市场需求和商业成立；当前资料也不足以判定立项本身错误。不能用我们的实现失败替代立项判断。

## 哪一层出了什么问题

| 层次 | 判断 | 责任与影响 |
| --- | --- | --- |
| 立项与定位 | 双用户及共同价值明确，实际价值仍需使用证据；没有证据要求全部推倒 | 不能把 UI 失败说成产品方向必错，也不能说市场已经验证 |
| 产品正文 | 不是整体错误；核心要求早已存在，但持续状态、修正生效、相似工作改进仍缺完整行为定义 | Codex 应主动明确这些行为，不应让用户重讲需求；未规定表结构不是产品文档的过错 |
| 工程计划 | 出现过降低要求的设计决定；当前主要是模块接入与检查台账，缺完整结果的覆盖和缺口判断 | 功能名称列全不等于完整计划；没有承担产品要求到可执行设计的转换责任 |
| 实现 | 部分核心能力被近似数据替代 | 用任务目标代表项目理解、运行状态代表进展、记录摘录代表复盘，会使界面无论怎样排仍缺有价值内容 |
| 交互 | 以现有组件和面板重新拼装，主工作路径没有先成立 | 减层级时删掉并行能力，恢复能力时又塞回面板，导致来回摆动 |
| 验收与继续开发的决策 | 工程检查和小样本成功被当成继续扩建的充分理由 | 产品正文已有“不算完成”，却没执行；反复否定后仍让用户承担发现根本问题的成本 |

正文也有需纠正的前提：开头“已经完成的团队、工作台”及历史版本“已经打磨的同窗口关系”不能视为用户认可了当时实现。可复用的工程能力与已通过的产品体验需要分开，不能继承一句“完成”就跳过复核。

## 已能追溯的具体错误

1. **项目理解被降成目录与任务观察。**历史 `62b4f4f` 的产品正文第 171、174 行要求读取项目资料，理解目标、阶段、风险、状态新鲜度，并明确不能缩成 Git 状态或会话列表。我们维护的 `4f18313` 开发计划第 27 行却限定“发送讨论只带扫描概况，预览正文需明确添加”。这把本应由团队完成的理解准备退回给用户。当前虽补了正式资料读取，`src/shared/project-status.ts` 第 269 行起仍从优先任务或交付记录取目标，第 299 行起按运行/交付状态决定主要状态；尚不能完整表达项目持续理解及其修正、失效与更新。状态表只是展示方式，不能补齐这种能力。

2. **公开分析被当成偶尔出现的汇报。**`4f18313` 开发计划第 25 行已经要求问题理解、方法、详细分析和判断，第 33 行有一次合成调用的成功记录。这证明不是最近才提出需求，但不证明真实工作稳定产生可读分析。本轮补了公开答复保留，仍需区分“保存内容”和“解释判断怎样改变”。当前 `src/shared/process-story.ts` 第 660 行起主要按修订类型及关键词提取问题/有效做法；`src/core/process-document.ts` 第 141 行起按固定组摘录。它能提供可追溯回看，却不能据此声称已充分实现对做法得失和整改效果的归纳评价。

3. **多窗口要求被错误理解为面板数量。**`62b4f4f` 产品正文第 101–107 行已经规定同一工作的主窗口与辅助窗口关系，以及团队理解当前对象、用户无需重复转述。`1a4c1c0` 第 113 行要求沿用该关系。它允许设计具体组织，不支持把项目协作降为临时弹窗。后来恢复三面、聚焦和拖动，也只能证明空间能力恢复，不能证明内容主次及工作路径成立。

4. **纠正没有成为后续设计必须遵守的条件。**`4f18313` 开发计划第 24 行已经纠正过机械截短报告，要求完整可读的结论、依据与取舍；之后仍以压缩内容和层级实现“简单”。我们保存了改动记录，却没有在后续简化时检查此前解决的问题是否复发。这正是“总结了但没有长记性”的具体表现。

## 开发计划是否覆盖全部功能

当前计划有软件/媒体、团队、Skills、雷达、资产、交付、反馈、例行及服务的接入记录，但不足以证明完整覆盖，更不能继续作为“按它做完就满足产品目标”的依据。

| 产品承诺 | 现有证据能支持什么 | 仍然缺什么 |
| --- | --- | --- |
| 持续理解项目和用户当前状态 | 读取正式资料，显示任务、交付和目录证据 | 哪份理解当前有效、怎样由用户修正、变化后何时失效和重核；运行状态与目标进展分开 |
| 可理解的协作与复盘 | 实际委派、公开答复和来源版本可保存回看 | 稳定说明分歧、判断变化及原因、整改是否有效；不能靠事后摘录自动宣布具备 |
| 反馈促进成长 | 反馈记录、方法草案、资产召回等已有工程路径 | 一项已采纳修正如何在正确范围改变后续相似工作，并能核对实际结果 |
| 两类用户都能完成工作 | 软件初始化/文件操作检查；媒体合成材料到脚本/交接检查 | 同等证明开发者背景遗漏减少、创作者制作交接有效，以及各自的接续与反馈闭环 |
| 一套工作台贯穿各入口 | 各模块已接入，共享部分任务与成果能力 | 用户能否辨认当前对象、重点、状态和下一步；最新体验已经被否定 |

以上是已发现的主要缺口，不是未逐项实测的功能一律不存在。官方运营服务、支付和广泛平台接入还需遵守原产品边界，不能将文档允许渐进的项目全部算作 bug，也不能借此隐藏核心能力缺口。

## 后续决策必须改变什么

后续判断从“用户结果 → 必要行为与信息 → 实现 → 对应证据”逐项对照。对于项目理解、复盘、反馈复用等核心能力，必须能指出当前内容从何而来、何时变化、怎样纠错，以及用户下一步能够完成什么；仅有列表、标签、保存或按钮则明确是局部能力。

对现有底座按职责评估：存储、版本、调用和权限边界的有效证据保留；项目状态、复盘语义、上下文关系与界面结构重新审视，不预设全部保留或全部废弃。不因用户说“全功能可用”就把范围拆成并行页面扩张，仍需在完整产品范围内先形成可核查的完整工作。

当前继续停止扩建。此记录不能代替实际改正，也不要求用户重新讨论全部已有目标。下一步若恢复开发，依据应是已明确的核心行为与可操作工作路径；不能再把测试通过、换 Skill 或新写一份文档当成方向已经成立。

# ytriple 产品定义

本文定义产品目标、功能行为、主要使用流程和验收场景。技术方案由 [ARCHITECTURE.md](ARCHITECTURE.md) 承接，当前发布版本的范围、待决事项与进度由 [PLAN.md](PLAN.md) 承接。产品范围不等于一个版本必须同时实现的清单，也不表示相关能力已经实现。

## 1. 产品定位与目标用户

> ytriple 是面向个人开发者和个人自媒体创作者的 AI 工作台。用户与 AI 团队共同吸收信息、知识和方法，积累本地资产，形成给人、工具和 Agent 使用的有效说明书，再从真实使用中改进判断与做事能力。

Y 是用户本人；Triple 是能力放大，不是固定三个 Agent 或三倍效率承诺。**多 Agent 团队是默认工作方式，协作流程与思维可视化构成产品核心。** 团队以不同视角分工、交流和修正，角色与能力可以持续调整；用户通过公开分析理解工作方法，在多轮交流中发现哪一步未达到要求，逐步形成可复用的工作流程。主窗口、思维窗口、结果窗口共同承接这一体验。简单任务可以由团队中的一个成员完成，仍保留团队身份与工作连续性。

| 目标用户 | 需要解决的问题 | 产品应提供的价值 |
| --- | --- | --- |
| 个人开发者 | 新项目的产品目标与取舍没有聊透，开发工具接手时背景和规则不完整，已有项目状态难以持续理解 | 通过团队讨论形成清楚的产品定义，初始化标准项目底座供 Codex 等接手；全面理解已有项目、管理状态并提出建议 |
| 个人自媒体创作者 | 收藏积压，选题和表达缺少支持，制作材料与工具分散，作品反馈难以变成经验 | 理解频道与受众，消化资料，形成原创内容和制作说明，持续复盘并积累方法 |

两类用户并列，不把其中一类作为附属场景。“个人”指由本人主导目标、判断和交付，不按粉丝数、收入或是否偶尔外包划分。

产品不要求用户先配置一群 Agent、迁移全部资料或建立完整个人画像。创作者不需要理解 Git、MCP 和工程目录才能开始；开发者不必经过频道设定。临时研究、写作和问答可以直接开展，不强制创建项目。

## 2. 产品主线与基本思想

**共同吸收 → 消化与本地积累 → 协作产出说明书 → 人与工具实际使用 → 反馈与共同成长。**

这是一条贯穿产品的价值链，不是每次使用必须完成的固定步骤。普通阅读、单次问答和一次文档处理都可以独立成立。

| 核心思想 | 在产品中的含义 |
| --- | --- |
| Personal State：理解当前工作 | 根据获准资料理解目标、阶段和已确认判断；系统先准备，用户修正，不反复要求填写已有信息 |
| Intelligence：理解信息 | 筛选、关联、核查、解释与比较，不把收藏数量、摘要长度当作知识增长 |
| Capabilities：组织能力 | 根据目标组织成员、Skills、工具、MCP 和工作流，而不是让某个工具决定产品形态 |
| Continuity：保持连续 | 跨会话、时间、成员、模型和专业工具保留有效背景、成果及决定的原因 |
| Learning：从结果改进 | 让已采纳的修正和真实验证结果影响后续相关工作，不仅保存聊天或增加标签 |

用户成长是长期产品目标：通过参与团队工作，学会不同工作的处理方法、识别未达要求的步骤，并在后续更快找到思路。团队能力随方法、Skills、工具用法和实践反馈持续改进；Agent 如何进一步学习和进化保留探索空间，不预设完整算法，也不要求一次开发完成。成长不默认等于训练模型、全天记录电脑或无限保存资料。

**本地优先**意味着用户掌握资料、资产和成果，不等于所有推理都离线运行。AI 默认承担理解与协作，而不是仅附着在列表旁边。模型和 Agent 可以替换，已有知识与成果不应随提供商更换而失去用途。

## 3. 产品组成与服务边界

### 3.1 客户端：围绕工作组织入口

客户端提供首页、雷达、项目、资产和可直接到达的定时任务入口，账户与设置位于辅助位置。入口可以按任务性质分组，不据此要求每页具有同样的布局、相同数量的区块或相同的信息密度。不同项目类型共用客户端，区别在工作对象、默认能力和判断标准。

| 入口 | 用户来到这里的目的 | 默认重点 |
| --- | --- | --- |
| 首页 | 开始一件事、继续已有工作、处理真正需要本人介入的事项 | 当前工作与可执行事项，而不是所有模块的小型副本 |
| 雷达 | 阅读和消化外部信息 | 已整理的认识、证据与变化，不要求先创建任务 |
| 项目 | 围绕持续目标推进和检查交付 | 项目目标、实际进展、作品或版本、相关工作与依据 |
| 资产 / Lib | 找到并使用已有积累 | 有用途和适用条件的知识、材料、说明书与能力 |
| 定时任务 | 管理已经委托给团队的例行工作 | 委托是否有效、何时执行、在哪里执行、结果如何 |
| 设置 | 管理服务、能力及本机使用条件 | 连接、权限、账户和偏好，不承载日常任务入口 |

雷达、项目和资产是三个核心业务领域；首页是工作入口，定时任务是执行管理入口。它们共用同一套工作、材料、成果和反馈关系，不各自建立聊天记录、待办或成果的竞争副本。

#### 工作、项目与运行记录的区别

**一项工作**围绕一个可识别的目标，关联必要材料、团队分析、成果和用户决定。一次问答、一个执行轮次、一条通知或一个文件，都不自动成为另一项工作。

工作可以属于项目、作品或雷达议题，也可以暂时独立存在。独立研究与临时文档处理应能命名、找回、继续和归档；后来归入项目时保留过程与成果，不复制一套会话。只浏览或保存资料不自动创建工作，也不启动模型。

**一次运行**是围绕这项工作进行的一次实际处理，记录当次目标、所用材料、成员活动和结果。一项工作可以经历多次运行；运行结束不代表工作目标完成。**定时任务**保存持续委托及其触发条件，每次实际执行产生运行记录，相关结果仍归回原工作及其项目、议题或资产。通知和首页事项引用这些对象，不另建工作副本。

跨入口使用引用关系：从首页打开结果、从雷达发起研究、从定时任务回看某次执行，都应定位对应的工作和准确成果。具有不同目标的新工作可以复用已有资产，但不能直接继承其他项目的私有资料或规则。

#### 首页 / Dashboard：开始、继续、处置

首页的主要价值是缩短“打开应用”到“理解并推进一件事”的距离，不是展示功能数量。以下为默认组织方案；必须保留的是用户能力与信息关系，不是固定的卡片数、区域顺序或视觉模板。

| 用户意图 | 首页如何支持 | 不采用的做法 |
| --- | --- | --- |
| 开始工作 | 一个可输入目标、粘贴链接或添加材料的轻入口；系统形成可修改的目标和归属，简单工作可以直接开始 | 同时摆满新聊天、新研究、新文档、新项目等按钮；从链接或一句话擅自执行安装、发布或上传 |
| 继续工作 | 显示少量用户固定或确有进展的工作，说明上次做到哪里、离开后什么变了、当前可以继续什么；其余通过已有工作查找入口访问 | 只按最新消息排序；只能在项目内找到临时研究；要求重新读完聊天历史 |
| 处理需本人介入的事项 | 将待决、重要异常、需要审阅的结果按原工作归并，说明影响、依据与可执行操作 | 待办、通知、异常、新成果各占一个重复列表；同一失败在多处制造待办 |
| 发现值得读的变化 | 有相关内容时呈现少量雷达短解读，支持独立阅读及进入原议题；不与自己的受阻工作争夺同等注意力 | 复制全部信息流；只有标题或计数；没有新增理解也凑栏目 |

首页不另设完整项目看板；项目状态摘要用于帮助继续和判断，详细目标与依据回项目查看。完整通知记录通过轻量入口访问，不作为首页独立内容墙。模型、来源和服务器的健康情况平时在设置或所属对象查看；**只有影响当前工作、需要用户行动的异常才进入处理区**。纯运行日志不进入首页。

优先级由实际影响、用户固定事项和真实期限支持。团队可以解释排序原因，但不编造紧急程度，也不因为消息最新就永远排第一。正在阅读时不因新事件反复重排；用户已处理或暂缓的事项不会因同一事件重放而反复出现，有实质新变化时再显示变化。

同一件事只有一个主要行动入口。例如定时任务因模型授权失效而未生成报告，首页显示“本次报告未生成，相关任务受影响”，从此处理权限或查看任务；不同时创建一个红点、一个失败待办和一个“新报告”通知。“标记已读”只改变提醒状态，不表示授权恢复或报告完成。

正常启动进入首页，不自动打开最近聊天或启动手动工作；已获授权的定时任务由自己的触发规则执行。离开期间的变化基于可核查记录整理，注明观察时间；本机未运行时不能编造离线期间的持续观察。

首次使用优先提供真实目标或材料的开始入口，并保留浏览雷达、导入项目等路径；不先让用户配置首页、不展示空统计墙。没有可用模型时明确哪些工作需连接能力，已有资产与可用阅读仍可访问。进入稳定工作期后，继续工作与需处理事项自然成为主要内容，没有数据的区域不为凑布局保留大块占位。

首页、已有工作查找和项目入口中的选择只是导航与展示范围，不构成资料上传或跨项目访问授权。每个摘要应回到原对象并保留其操作上下文，不能在首页卡片里再嵌入一套团队对话。

### 3.2 服务器

| 服务方向 | 负责什么 | 用户获得什么 |
| --- | --- | --- |
| 信息服务 | 来源管理、内容取得、筛选与解读、议题更新、订阅投递 | 已经整理的信息供给；可以作为独立服务使用，不依赖客户端一直打开 |
| AI 能力服务 | 模型与专项能力、可用状态、用量和权益，以及适合远端运行的委托 | 不自行配置各厂商 API 也能使用 AI；适用的长任务与例行任务可以托管 |
| 用户服务 | 账号、设备、订阅、权限、用量及数据控制 | 登录、查看权益、管理授权和设备、导出或清理自己的服务数据 |

用户可以使用官方服务、自部署相关服务或自带 API。基础接入支持 OpenAI 兼容格式，并保留 Google/Gemini 的原生能力，尤其专项研究；不把兼容格式理解为所有模型功能等价。

服务器提供推理不等于接管本地团队。远端委托只获得该项工作实际需要且获准的资料，不自动读取整个 Lib、本地项目或浏览器登录状态。外部研究服务是团队可调用的能力，不替代团队对用户目标和交付结果的责任。

本地基础使用不以官方账号或订阅为前提；缺少可用模型时说明 AI 功能限制。订阅到期不锁住本地资料与成果。公共信息和个人资料分开，私人内容不默认进入公共内容池或供其他用户使用。开源、自部署和可选订阅方向保留，具体套餐与价格不在本文确定。

## 4. 核心产出：说明书

“说明书”是对可用成果的统称，不是狭义操作手册，也不限定一种文件格式。

| 接收方 | 典型成果 |
| --- | --- |
| 用户 | 研究结论、取舍依据、指导方案、学习材料、脚本、发布文案及整理后的文档 |
| 工具、Agent 或专业执行者 | 目标与约束、输入条件、工具用法、制作要求、Skill、工作流、架构思路及交接材料 |

两类成果服务同一个目标，不强制生成两套重复文档。能够直接给出结果时，不额外制造说明文档。

### 4.1 阅读、修订与交接

用户能查看所属工作、接收对象、当前版本、依据、适用条件、尚缺输入和完成标准。可以直接编辑，也可以选择段落或问题交给团队修订；修改同一成果时保留版本和改动关系，不不断新建同主题文件。

主要文字成果使用 Markdown。产品保留常规文字与文档导入、信息图和演示成果的方向；输入解析深度、原格式编辑、预览与真实导出分别说明，不能互相冒充。具体支持格式由发布版本明确。

复杂交付提供“检查是否准备好”：核对缺失材料、要求冲突、证据不足和接收方可能产生的歧义。可让未参与此前讨论的成员只依据交接材料复述目标与条件，暴露缺口，但不能把这种检查当作真实执行或效果验证。

交接通过可读取文件、导出材料或实际接入的工具完成，保留交接版本和接收对象。草案、已确认、可交接、已交接、已使用、已验证和待修订分别表达，不要求机械经过全部状态。

这些表述说明不同事实，不是一条自动升级的完成进度：内容是否被采纳、材料是否齐备、是否发生交接、是否有使用或验证证据分别判断。每项判断对应具体版本和依据；旧版被使用或验证的记录，不能直接证明新版已经使用或验证。成果可以已经交接，同时仍有待修订部分。

**生成不等于使用，交接不等于执行，执行成功不等于项目目标已经达到。**没有接收或使用证据时保留未知，不能以打开工具或发送链接推定完成。

## 5. 多 Agent 可视化、三窗口协作与 Skill

### 5.1 默认团队

用户默认向一个可调整的团队开展工作，不必先开启“多 Agent 模式”。团队围绕问题组织多视角分析、分工、核查与汇合，实际流程可随工作变化；不要求每次所有成员发言或走相同的固定步骤。协作方法可以持续升级，已有工作、成果和公开过程仍可理解和继续使用。

| 场景 | 默认责任组合 | 主要任务 |
| --- | --- | --- |
| 软件项目 | 统筹、CTO、研究员 | 需求与方案判断、研究、项目准备、状态理解、交接与反馈 |
| 媒体项目 | 主编／统筹、研究员、内容编辑 | 频道与选题、事实核查、原创表达、制作说明与复盘 |

默认组合可以调整，底层不分成两套产品。用户可以随工作需要改变角色、责任和能力组合，团队也可以提出调整建议；角色与能力变化显示生效范围，历史贡献保留当时的成员身份和能力依据。媒体工作遇到工具和技术问题时可以调用 CTO。成员稳定存在不表示持续运行或消耗模型费用。

用户可以向团队提出目标，也可以直接找一个成员。成员能委派、追问、利用彼此成果、处理证据冲突并改变判断；不是分别回答同一个问题后拼接。常驻成员可以调用专项子 Agent，结果交回负责成员，用户不需要充当传话人。

### 5.2 主窗口、思维窗口、结果窗口

**三窗口是产品的主要工作方式，是多 Agent 底座的一部分，不是三个角色分别占据的聊天框。**“窗口”指可独立阅读与操作的工作面，不要求启动三个操作系统窗口。主要桌面工作空间支持三者同时对照；各窗口可调整空间、聚焦和还原，窄空间可在同级入口间切换，不能用弹窗替代完整协作。

| 窗口 | 回答的问题 | 默认呈现的内容 | 主要操作 |
| --- | --- | --- | --- |
| 主窗口 | 目标是什么，团队当前判断是什么，用户需要决定什么 | 用户与团队／成员的交流；当前目标与交流对象；完整可读的基本结论、关键依据与取舍；受阻和待决事项；相关分析和成果入口 | 发起目标、选择成员、添加资料、指定 Skill、提问、纠正、确认、停止或继续；引用另两窗的选定对象开展讨论 |
| 思维窗口 | 团队怎样调查和协作，依据是什么，判断为什么改变 | 成员职责与状态、真实委派关系；成员主动提供的公开分析、方法、关键发现、证据对照、分歧和修正；实际调用的 Skill／工具／子 Agent 与返回结果 | 按议题、成员或处理轮次查看；展开子任务与来源；针对一项判断追问；回看过程、总结或复盘指定范围 |
| 结果窗口 | 实际交付了什么，这个版本是否可以使用 | 说明书、脚本、报告、图表或其他真实成果的正文与预览；当前版本、来源关系、未完成条件、交接与使用状态 | 阅读、编辑、局部修订、比较版本、就绪检查、导出、交接、收藏和查看使用反馈；打开复盘报告 |

主窗口不能机械截成一句摘要、把基本判断全部藏入附件；思维窗口不能变成工具日志；结果窗口不能只是文件名或“生成成功”的提示。相同长文不在三个窗口重复铺开：主窗口负责交流与决定，思维窗口说明分析与协作，结果窗口承载可用成果，三者通过准确引用联动。成员需要基于资料作出实质分析和相互核查；减少重复展示不能被实现为删掉公开分析或压缩成一句状态。

简单问答可以直接在主窗口结束，不强制生成说明书、全员协作或复盘报告。没有结果或过程记录时明确相应状态，不用示例文件和预设发言冒充已有工作。

#### 三窗口的主次由工作阶段决定

三个工作面始终可直接到达，桌面空间允许时可同时对照；不要求每次打开都固定等宽或同时填满。默认呈现服务当前工作，用户的主动布局选择优先：开始任务时突出目标与材料；团队处理时便于同时看公开分析和交流；形成成果后便于对照正文、依据与修改意见。新的处理阶段只提供提示，不自动抢走阅读焦点或改变用户正在使用的布局。

三窗口不是三个互不关联的信息源。共同显示当前工作身份，并能辨认查看的是当前轮、历史分析还是某一成果版本；结果可有多个，但用户应能区分主成果、支持材料和历史版本。旧版查看不悄悄替换正在编辑的正文。

运行进度与成果质量分开表达。成员结束只说明其本轮处理结束；只有真实成果或必要说明已经可读，才能表示已产生结果；仍待核查的结论不能因为流程结束就改成确定结论。缺少过程或成果时说明原因，不用空模板假装三个窗口都有内容。

### 5.3 思维窗口：过程本身要可理解、可干预

产品中的“思维过程”指**成员主动提供的公开分析、可说明的研究方法、证据比较、协作问答和判断修订**；不承诺取得模型未公开的内部推理。提供方实际提供公开摘要时可以标注来源展示，没有提供的内容不能伪造为实时思考，也不能事后补写成当时发生的事实。

思维窗口把工作组织为可阅读的分析轨迹，而不是逐条复制日志。一次议题下可以看到问题理解、调查方法、关键依据、候选方案与取舍、尚有分歧、当前判断和修正原因；按真实工作需要出现，不要求每位成员每次都填齐固定栏目。

**过程可视化同时服务学习。** 用户应能看懂当前步骤解决什么、采用什么方法、需要达到什么要求，以及它怎样影响后续工作。多轮交流后，可以从一个结果问题追溯到相关步骤、当时依据与用户修正，分清已发现的不足和仍待核查的解释。实际流程按任务展开，不把全部工作硬套成同一张步骤清单。

| 过程元素 | 展示与操作要求 |
| --- | --- |
| 团队概览 | 显示当前参与的成员、具体负责的问题及运行／等待／受阻等真实状态。选择成员后可定位其贡献，不只显示头像和“思考中” |
| 协作关系 | 以当前问题为线索，明确显示负责成员、委派对象、提出的异议和返回内容；选择即可读相关分析与依据。关系图、连线或分组可作为表达手段，不要求默认铺开整张运行图；可视化必须体现实际协作和判断变化，不靠增加节点制造复杂感 |
| 分析记录 | 以带成员归属和发生顺序的内容块呈现可读分析、方法、发现和判断；关键依据就地可展开。完整公开内容可读取，不只剩状态标签和机械截断句 |
| Skill 与工具使用 | 在相关分析旁显示实际采用的能力、版本及其用途；可以查看输入覆盖和真实结果。区分“准备调用、已加载、执行有结果、效果待验证”，不以徽标替代能力证据 |
| 子 Agent | 默认折叠在负责成员或委派问题下，展开后看到限定目标、来源范围、发现、失败或回信，以及负责成员如何使用它；不要求用户逐一管理独立窗口 |
| 分歧与修正 | 重要分歧在正常阅读中可见，关联各方依据；判断变化说明原判断、新判断、触发证据或用户意见，并指向受影响的成果版本；未解决的保持未解决 |
| 步骤与要求差距 | 显示实际处理步骤所针对的问题、方法和要求；关联未达要求的具体表现、证据、修正及后续结果。可针对该处讨论并比较多轮变化，不能把事后猜测标成已证实原因 |
| 过程回看 | 支持查看当前有效工作、特定轮次或历史记录，保留范围与时间。旧目标结果可追溯但有旧版本标记，不混入当前有效结论 |

默认按正在解决的问题和重要判断变化组织公开分析，成员筛选、关系展开和时间回看用于深入。能够从“结论为什么变了”进入有关成员的实质分析，而不是先研究一张 Agent 关系图。详细工具记录放在可展开的排障层；原始日志能证明动作发生，不能单独证明理解或判断正确。

用户可在思维窗口选中一项分析或证据，选择“追问此处”或“提出修正”，带着成员、议题、来源和版本进入主窗口讨论；这不自动改变全局目标。明确改变方向后，受影响成员、子任务和成果才按新的有效目标继续。

新内容到达时，用户在底部跟随阅读可以继续跟随；已向上阅读或正在选择文字时保持位置，使用新内容提示，不抢滚动和输入焦点。过程只显示实际收到的汇报；缺少分析、资料未读或任务仍在等待时明确表示，不生成百分比假进度。

### 5.4 过程总结与复盘

思维窗口提供可直接操作的**“总结过程”与“复盘工作”**，二者作用不同，可以放在同一操作组内，但不能混用结果名称。

| 操作 | 实际处理的内容 | 应交付什么 |
| --- | --- | --- |
| 总结过程 | 所选工作或轮次中实际记录的公开分析、成员问答、证据与决定 | 可学习的处理流程、关键步骤与方法、各成员的贡献、分歧与决定、仍未完成部分，以及可返回的原始记录 |
| 复盘工作 | 上述过程，加上用户修正、准确成果版本、已获得的执行或使用反馈 | 原目标与实际结果的差距；哪些步骤未达要求、相关依据和修正是否生效、哪些解释仍是假设，以及可供用户采纳的方法改进 |

用户可以选择当前工作、某一轮或已选记录的范围；系统明确本次用了哪些过程与结果，避免把所有历史混为一谈。工作尚未结束也可阶段复盘，但必须标明未完成状态；没有实际使用反馈时，只能评价过程、说明书和可核查结果，不能宣称用户效果已经改善。

总结和复盘通过团队及合适的 Skill 处理：识别分析与结果的联系、检查前后判断和修正是否对应，而不是只按关键词摘录发言、统计工具次数或列出“做得好／做得不好”。结论要指回具体成员记录、证据、用户意见和成果版本；不能用事后推断补造当时未记录的想法。

生成的总结／复盘作为真实成果在结果窗口打开，主窗口呈现基本结论和需要用户决定的改进。用户可以继续修订、保存、关联项目或收藏到 Lib；“保存复盘”不等于修改长期方法。需要影响后续工作时，用户明确采纳的改进才进入对应项目、频道或 Skill 范围，并可追查后续使用情况。

经过多轮修正形成的有效方法，可以通过“沉淀为可复用方法”整理为带适用条件、步骤要求和实例的流程草案，再在实际工作中检验与完善。保留探索和修改的依据，帮助用户掌握方法，也为团队改进提供材料；不能仅因一次运行结束就宣布工作流已经稳定。

### 5.5 三窗口联动与工作连续性

三个窗口始终属于同一项工作，保留当前项目／议题、有效目标、所选材料和成果版本。选择另一个成员改变交流对象，不创建新的上下文孤岛；浏览其他资料不默认为把该资料发送给所有成员或远端服务。

从思维记录打开依据或关联成果时，定位准确来源和版本；查看旧成果可以与当前版本对照，不静默切换正在编辑的正文。结果窗口选中段落要求修改时，主窗口携带段落与版本，思维窗口记录相关分析和修正，结果窗口形成对应修订，不另外生成一份无关同名文件。

跨窗口追问明确显示针对的对象与作用范围，例如“解释此依据”“修改所选段落”或“调整本项工作的目标”。系统结合上下文准备范围，用户可纠正；解释问题不会直接覆盖正文，普通局部修改也不扩成全项目规则。不要求每次发言都弹出确认表单；含义存在实质冲突或超出授权时，才集中确认。

成果修改前存在新的外部版本时，保留差异并处理冲突，不用旧上下文覆盖新正文。来源出现变化时，只对相关判断和成果提示需要复核，说明受影响的依据；不能由一次来源刷新强行重写全部说明书或触发整个团队重跑。

停止、切换或重开时，保留草稿、阅读位置、选择、布局偏好、有效过程和成果。停止不抹去已完成贡献，远端取消未确认要说明；迟到的旧结果不覆盖新目标或抢走用户后来打开的页面。折叠、聚焦、调整空间不影响实际任务执行。

这一交互同时适用于软件项目、媒体作品、雷达深度研究和资产处理。首页和普通阅读不必常驻三个大窗口，但进入实质协作不能退化成临时对话弹窗。具体视觉排布可以设计和验证，三窗口的责任、并行对照与过程复盘能力不能因简化界面而删掉。

### 5.6 Skill 的操作与结果

Agent 身份定义责任；Skill 提供可复用知识、方法和必要资源；工具或 MCP 提供实际访问与动作通路；工作流组织这些能力。

| 入口 | 操作 | 结果 |
| --- | --- | --- |
| 资产中的 Skills | 使用内置能力，导入可信包或链接，查看、启用、停用及编辑副本 | 用途、来源、版本、依赖和验证记录清楚 |
| 成员能力设置 | 选择默认可用范围和能力组合 | 不必把所有 Skill 全文永久写入角色提示词 |
| 当前工作 | 从主窗口指定 Skill，或团队在可用范围内自动选择 | 思维窗口能查到实际加载的版本、处理对象、相关分析和工具结果；成果进入结果窗口并保留引用 |
| 工作成果 | 选择“沉淀为可复用方法” | 形成带适用条件、样例和修正依据的 Skill 或工作流草案，经使用后再确认 |

默认提供少量实际有用的场景能力，如资料消化、选题评估、脚本核查、需求澄清和交接检查；不要求用户先逛插件市场才能使用。

已发现、可加载、缺依赖、待验证、已验证和停用分别表达。方法型 Skill 可以辅助分析而不执行脚本；需要软件、脚本或账号时，缺少依赖就说明缺什么，不假装运行。安装或导入 Skill 不自动获得联网、付费、写文件或安装权限。

## 6. 雷达：阅读与信息消化

雷达采用有编辑判断的栏目式体验，围绕问题和持续议题整合、解释、跟进，不只是转发新闻或加长摘要。用户无需提问，就能在雷达主页获得有用理解；详情连贯说明背景、证据、分歧和限制。首页 Dashboard 只摘取其中少量重点，点击后进入同一解读，不另造一份新闻内容；需要团队深入时，再带着当前议题进入三窗口协作。

### 6.1 三类来源，共用一套消化体验

**订阅服务**接收服务器提供的内容；**我的来源**接收用户添加的网址、RSS 和资料；**平台与收藏**接收实际获得授权的平台内容或导出材料。不同来源不形成三套阅读器。

添加地址时，帮助识别单篇内容、持续来源、账号、目录或工具。明确它是单次导入还是可持续更新。来源暂不可达、需要登录或只取得部分内容时如实显示。

### 6.2 从积压收藏到主题理解

用户选择一批资料或一个关注范围，团队完成筛选、去重、主题归纳及与已有 Lib 的对照，交付关键认识、新增条件、分歧、能力线索和必要的深入阅读入口。

不是每篇收藏分别生成一篇摘要，再让用户重新归并。过滤可解释、可纠正，默认不删除原平台收藏。标题、描述、全文、字幕和画面分别标明读取范围，读不到不等于没价值。

同一议题出现新材料时更新已有理解，说明本次改变；保留重要反例和不同观点，不把转载当独立证据。没有新增理解时不凑推送。原文用于核查与深入，消化后的内容是主要阅读对象。

用户可以继续追问、关联项目、创建选题或吸收资产，不强迫普通阅读进入任务流程。工具资料先形成用途、适用条件和候选状态，实际验证后才能成为可靠能力。

### 6.3 相关性与供给

预置来源降低冷启动成本，个人来源不依赖购买官方信息服务。根据用户明确目标、项目和获准资产判断相关性，保留自主浏览和不同观点，不假装知道用户已掌握什么。

科技、AI、金融、股票等可作为初始主题候选，不是所有用户的默认兴趣。来源覆盖、内容深度和个性化可以逐步增加，不能用复杂推荐算法的缺失推迟基本的整理与解读质量。

## 7. 项目：软件与媒体

### 7.1 共同状态与连续工作

项目承接持续目标、正式资料、具体工作、说明书和反馈。用户应能知道当前解决什么、已有何种结果、真正阻塞在哪里、还有什么未完成及判断依据。进入项目可以继续已有工作，而不是重新交代背景。

项目状态来自有效项目资料、实际结果和用户确认，附带范围、时间和依据。团队运行状态与项目进展分开；最近任务的目标、文件改动数或一份文档生成不能替代项目目标和完成状态。

在获准范围内实际读取相关正式资料后形成理解。资料缺失时明确未知；重要依据改变后，原理解需要复核。用户修正及其范围要在后续相关工作和重开接续中生效，不只是增加一条聊天记录。

### 7.2 软件项目

**软件方向的核心路径是：用户与多 Agent 团队把产品聊透，初始化为标准开发项目，再由 Codex 等专业工具接手。** 团队帮助澄清目标、使用方式、边界、重要取舍和验收场景，把讨论结论落实为可接续的项目材料；用户不需要自己重抄聊天或先填写模板。

标准开发模板承接已确认的产品内容、适用目录与管理规则、必要文档、开发接续说明和未决事项。模板可以按项目类型调整，应填入真实讨论结果；仍待专业开发工具设计或验证的部分明确标注，不以空文件齐全或擅自补全技术决定表示“初始化完成”。

| 工作 | 用户操作 | 交付结果与边界 |
| --- | --- | --- |
| 产品讨论 | 提供想法、目标或已有讨论，与团队多轮澄清和修正 | 形成能落实到初始化材料的产品定义、取舍依据、验收场景和真实未决事项 |
| 初始化与交接 | 选择项目位置和适用模板，采用讨论结论 | 按本机 Policy 建立标准项目底座；身份、登记、规则、必要文档和适用 Git/worktree 可核查；Codex 等可从明确接续点开展工程设计与开发 |
| 导入与整体理解 | 提供已有项目并授权读取其内容 | 全面读取和理解项目，包括源码、配置、测试、文档和已有结果等实际内容，说明覆盖范围、关联与缺口，不只复述目录或少数文档 |
| 状态管理 | 查看项目进展和后续变化，讨论目标、问题与建议 | 根据实际项目证据整理状态、风险和待处理事项，区分已实现、待验证与未知，不自行执行整改 |
| 开发建议 | 对具体资料或变化提出意见 | 对既有项目的日常建议统一写入一个固定的项目建议文档，保留依据与已有内容；不自行修改代码、配置或正式开发方案 |
| 结果回验 | 导入或授权读取版本、问题反馈及执行结果 | 对照原目标和说明书，形成可采纳的修正；没有证据就不宣称已执行 |

本机已有管理规则应识别并保留；缺少体系时帮助建立对应目录与规则，再初始化项目。残缺或冲突不当作空目录覆盖，不硬编码项目作者机器的路径。

全面理解可以通过分批读取建立，必须能辨认实际已读、尚未读及不可读取的项目内容；不能只建索引便宣称已理解全部项目。后续依据变化更新理解，不要求每轮对话重读全部未变内容。读取整个项目不等于取得整改权限，也不自动将整个项目发送给远端服务。

固定建议文档沿用项目已有约定；没有时在接入时确定一个写入位置，后续持续更新同一文档，保留已有建议及其依据。已有项目的正式文件、工作草案和建议文档应可区分。新项目初始化有其明确写入范围；交接后的持续管理只向固定建议文档回写建议，不把讨论、草案修订或就绪检查显示为正式方案已被修改或开发工具已采纳。这不限制 ytriple 保存自己的工作过程、状态与成果。

ytriple 可以研究方案和架构思路，但不替代专业开发工具的工程设计、代码实现与测试。开发反馈被记录、被采纳、被执行是不同结果。

### 7.3 媒体项目

媒体项目代表频道或栏目，作品承接具体内容。作品的资料、脚本、制作说明、平台／语言版本、发布链接和反馈保持关联，不变成互不相干的会话。

| 工作 | 用户操作 | 交付结果 |
| --- | --- | --- |
| 频道与栏目 | 添加账号、代表作品、受众和制作条件，修正团队理解 | 可持续使用的频道方向与表达标准 |
| 选题 | 从雷达、收藏、观众问题或想法创建选题 | 受众价值、原创角度、证据缺口、制作条件与取舍 |
| 研究与脚本 | 关联资料、补充调查、撰写和修订内容 | 有依据的原创文章或脚本，编辑与研究员相互核查 |
| 制作说明 | 选择内容形式、已有工具与素材 | 适用的镜头、录制、素材、生成要求和工作流，不机械生成全套附件 |
| 发布准备 | 选择平台和语言，检查内容与标题承诺 | 标题、封面方案、简介、字幕等必要材料 |
| 发布与复盘 | 登记真实发布，提供或授权取得成品、数据和评论 | 与原创作判断对照的结果、待核查解释和方法修正 |

短文案可以跳过不需要的环节，不要求所有作品走完整生产线。实际设计、剪辑和发布继续使用专业工具。

账号区分自有与对标，公开更新可进入雷达，经营数据用于作品复盘。保留 YouTube、TikTok、X、抖音等接入方向，但实际数据覆盖分别确认；手动提供真实报告也能开展复盘。没有对标后台权限就不生成其私有指标，未知素材授权不标成已获许可。

## 8. 资产与反馈：让用过的东西真正留下来

Lib 是统一查找、理解和使用资产的入口，不等于强制把全部文件搬到一个目录。

| 资产类别 | 包含内容 | 使用方式 |
| --- | --- | --- |
| 知识与参考 | 原始材料、研究结论、判断依据、方法和反例 | 查找、引用、核查、补充或修订 |
| 能力 | Skills、工具资料、MCP 使用方法、工作流及适用条件 | 按目标调用、试用、验证、停用 |
| 成果与经验 | 说明书、实际结果、用户修正和失败条件 | 跨任务复用，检验并改进后续工作 |

资产体现解决什么问题、来源、版本、适用条件和使用证据。新资料与已有资产区分重复、新增、补充和冲突；新任务中团队应主动找出获准且有关的资产，不让用户逐个找文件。

项目的权威正文留在项目内，跨项目知识和资源按本机规则组织。引用、资料快照和可复用副本分清，不制造两份竞争的正式文档。修订保留差异，不覆盖未知外部修改。

### 8.1 反馈怎样影响后续工作

用户通过观察、讨论、定位过程中的不足和复用方法逐步成长；Agent 的学习与进化是持续改进方向，具体机制尚未确定。下面的反馈采纳与复用是可逐步实现的能力，不代表完整的自主进化方案，也不以先实现此类方案为其他能力的使用前提。

用户可以把真实问题、评论、报告或执行结果交给团队整理，保留原话、来源和覆盖范围，区分缺陷、需求、误解和个别意见。结果关联原项目、作品或说明书。

反馈被采纳后，明确修改的是当前成果、项目／频道标准还是跨项目方法，并在后续适用工作中实际使用。一次作品的改法不自动变成全局风格，一次失败也不直接否定全部工作流。

复盘区分目标判断、说明书表达、执行和外部条件；证据不足保留假设。**保存反馈不等于学习，提出修改不等于修改有效。**应能追溯后续工作用了哪些已采纳修正，以及结果是否支持它们。

### 8.2 可携带与恢复

用户可以导出、备份和恢复资料、资产、说明书及必要关联；恢复不能静默覆盖同名内容。保留版本与用途关系，不打包密钥和平台登录凭据，不以购买服务或启用云同步为前提。

## 9. 定时任务与个人工作支持

### 9.1 定时任务：独立入口，关联原工作

左侧菜单提供独立的“定时任务”按钮，直接进入任务管理页面，不藏在设置、首页卡片或单次对话的更多菜单中。这里统一管理按时间、可观察变化或实际节点触发的自动化委托；“例行工作”是这类委托的业务含义，不再作为另一个重复入口。

用户可以在任务页面选择“新建任务”，也可以从一次有效工作选择“设为定时任务”，两种方式进入同一个任务管理体系。继承或选择目标、资料范围、负责人、Skill 和成果归属，主要确认触发条件、执行位置、授权、用量限制及通知方式，不要求编写定时表达式或搭建流程图。允许按具体时间或周期安排；事件和发布后触发只在相应来源实际可观察时生效。

默认创建流程只要求用户看清“做什么、何时做、结果到哪里”，系统沿用既有工作中实际可用的成员、方法和资料范围。运行位置、用量及授权摘要直接可见，详细参数按需展开；条件缺失时显示具体阻塞，不把全部配置变成开始的前提。导入或运行一次有效工作不自动建立长期任务。

| 例行工作 | 触发示例 | 结果 |
| --- | --- | --- |
| 消化新增收藏 | 定期或出现新材料 | 与旧材料和 Lib 对照后的增量理解 |
| 项目变化简报 | 定期或重要变化 | 有依据的进展、反馈与阻塞说明 |
| 栏目准备 | 定期或创作前 | 结合频道与已有作品的选题和资料准备 |
| 发布后复盘 | 实际发布一段时间后 | 对应版本／作品的真实结果与修正 |
| 资产有效性检查 | 定期或相关条件变化 | 待复核资产和修订依据，不直接覆盖稳定版本 |

任务列表清楚显示名称、关联项目／主题、触发方式、启用与运行状态、执行位置、上次结果和下次触发；可以按状态或所属项目筛选，直接新建、立即运行、暂停、编辑或停止。任务详情提供实际用量、失败原因、当前有效方法版本和运行历史，每次结果可以回到原工作及对应成果。用户从通知或首页进入时，定位同一个任务，不再创建第二份委托。

每次运行的公开分析、成员协作和真实成果都沿用三窗口表达；任务管理列表不复制完整过程。区分“暂停后续触发”和“停止本次运行”，已在远端提交的任务以实际取消结果为准。触发按用户时区呈现，时间、来源或发布节点改变时，其影响可见。

没有新输入就记录检查结果，不强行重复生成。结果回到原项目、议题或资产，不每次新建孤立聊天。中断补做、重试或多端恢复不能造成重复执行；未知结果先核对。方法版本或权限改变时，不能悄悄改变长期任务。

本机任务依赖实际运行环境和机器状态；后台执行须明确启用。服务器只处理其有权访问的资料，本地文件或登录环境不可用时明确等待。关闭窗口、程序退出、机器休眠、远端运行和取消未确认分别表达，不以有服务器推定任何任务都能全天执行。

### 9.2 处理事项、通知与交付节奏

首页的处置区按第 3.1 节组织。**事项表示需要行动，通知表示发生变化，执行记录表示系统做过什么**；三者不能用同一种“待办”替代。同一个业务事件可以有不同查看入口，但只维护一份真实状态。

例如，授权失败需要处理；在授权范围内自动完成的普通报告可能只需汇总通知；一次没有新增材料的检查只保留运行记录。新成果不默认都要求用户审批，只有确实需要选择、审阅或解除阻塞的部分进入处置区。用户处理源问题后，相关摘要随真实结果更新；暂缓、已读或静音不代表问题已经解决。

个人不需要先设立一套人工待办系统才能使用这些能力。事项从已有工作和明确委托中形成；AI 建议先作为可采纳建议，不擅自为用户排入期限或承诺交付。用户可以调整重点，不能让每天的新通知冲掉长期重要工作。

项目提供轻量交付列表或日历：软件看版本和交接，媒体看作品。目标日期、当前说明书、缺失输入及外部执行状态关联；计划发布时间不能当作已经发布。列表与日历是同一组交付的不同视图，不另造任务状态。

通知支持汇总、静音与重要程度控制，完整记录可查。普通进度与无变化检查不轰炸用户，重要失败仍在所属工作中可见；不因没有发通知就表示任务没执行，也不因发了通知就表示结果已被采用。

### 9.3 轻量资料入口

支持从文件、正文、链接和实际可用的浏览器保存／分享入口带入材料，保留来源与用户附言。用户可以只保存材料，也可以带着目标交给团队；保存不自动启动深度研究或上传远端。材料可以归入已有项目，尚未决定用途的保留为可找回材料，不要求先起项目名或填写分类。

全局查找应能按工作、项目、资产和成果找到原对象与版本，不只搜索聊天标题。它是跨入口导航能力，不代表模型已经取得全部检索结果的正文权限；可以用简单检索逐步实现，不预设大型语义检索系统。移动分享和平台覆盖可以逐步扩展，不以完整移动端工作台为前提。

## 10. 产品边界与长期演进

不以企业、MCN、客户审批、工时管理或代运营作为当前产品中心；不重做完整 IDE、剪辑、设计与发布平台。不默认自动发布互动、删除源端资料、安装工具或无人值守改代码。

外部内容是材料，不是授权。事实、模型判断、用户采纳、情景假设和真实结果分别表达；多人一致、粉丝增长、播放量和 Star 都不能单独证明正确或有价值。

可选情景推演、更多平台、深层个性化和移动端保留扩展空间。推演放在具体议题内，不作为基础阅读门槛，也不把模拟言论当现实反馈；不承诺收益或确定未来。

以下七层成熟度用来描述能力深化，不是七个页面或固定开发顺序：

| 层级 | 含义 |
| --- | --- |
| L1 · Ask / Find | 找到信息并提出有效问题 |
| L2 · Act | 通过授权能力完成具体工作 |
| L3 · Persistent Context | 保留有效背景、目标和修正 |
| L4 · Structured State | 组织项目、知识、能力和成果状态 |
| L5 · Indexed Retrieval | 为当前工作找回有关积累 |
| L6 · Semantic & Relational Intelligence | 理解关系、缺口和矛盾，将方法用于新目标 |
| L7 · Composable Production + Learning | 组合可靠能力持续产出，以真实反馈改善方法 |

高度自动化来自经过验证的资产、清楚的授权和实际反馈，不来自无限 Agent 循环，也不是“自动赚钱”的保证。

## 11. 代表性验收场景

以下用具体示例表达上述行为的验收标准，不是新增功能或已实测结果，也不自动决定当前发布版本。版本计划选定的功能，应对应有关场景与明确结果。示例中的项目名、角色、媒体形式和操作顺序用于暴露问题，不要求硬编码这些样本；同类材料和等价操作也应满足相同的用户结果。

| 标识 | 场景与操作 | 应观察到的结果 |
| --- | --- | --- |
| AC-01 低门槛开始 | 提供少量资料和一个明确目标，开始研究或文档工作 | 不先配置全套团队和知识目录；得到可读取成果，缺少能力或授权时能看清具体缺项 |
| AC-02 项目状态 | 软件项目目标是接通真实收藏，最新完成任务只是整理 README；随后相关正式资料更新 | 不因 README 任务完成而认定收藏已经接通；目标判断有依据，受资料变化影响的理解标明待复核或得到更新 |
| AC-03 协作与修正 | 脚本原先面向开发者，用户改为面向普通创作者，并切换到另一成员继续修订 | 后续交流和同一脚本采用新受众条件，不只回复“收到”；已有可用证据保留，不要求重讲背景 |
| AC-04 Skill 实用性 | 对同一工作指定方法，再尝试一个缺依赖的 Skill | 前者能查看实际方法与结果，后者明确缺项而不冒充执行；加载不自动产生新的权限 |
| AC-05 收藏消化 | 处理含重复、新知识、分歧和读取不完整内容的一批材料，再补充同议题新证据 | 交付主题理解而非等量摘要；过滤可纠正；保留证据范围，说明相对原理解的变化 |
| AC-06 说明书与交接 | 修改一份成果，做就绪检查并交给实际接收方 | 修订和交接对应准确版本；缺失条件可见；没有使用证据时不标为已验证 |
| AC-07 媒体连续工作 | 从频道资料和选题形成脚本与制作说明，登记发布并导入反馈 | 各环节属于同一作品；实际数据与原假设对照，不凭指标编造因果或保证效果 |
| AC-08 复用与成长 | 用户确认仅栏目 A 采用“先呈现结果再解释方法”的开场方式；重开后分别开始栏目 A、B 的新脚本 | 栏目 A 的新工作能读取并采用该标准，依据可查；栏目 B 不因这次局部确认被自动改写规则 |
| AC-09 例行可靠性 | 设置例行任务，出现无新输入、离线、停止或重复触发 | 状态、时间、用量和结果可查；不重复生成或执行，不冒充能够访问不可用的本地资源 |
| AC-10 数据与体验 | 编辑中切换工作、出现迟到结果，随后导出或恢复资产 | 草稿、位置和对象归属不丢失；旧结果不覆盖新内容；恢复不破坏原资产，服务变化不锁住本地文件 |
| AC-11 三窗口对照 | 开始真实协作，同时查看交流、公开分析和当前成果；调整窗口、聚焦再还原，对结果中的段落提出修改 | 三者属于同一目标和准确版本；主窗口保留讨论、思维窗口解释相关分析、结果窗口呈现实际修订；草稿与位置保留，不因操作另起孤立任务 |
| AC-12 团队可视化 | 研究员委派专项核查，另一成员提出证据异议，并调用一个实际可用 Skill 处理 | 可以看清委派与回信、谁提出什么异议、所用能力及结果、哪项判断因此改变；子 Agent 按负责关系展开，不以预设对话、头像或日志数量证明协作 |
| AC-13 过程总结与复盘 | 一次工作经历错误判断、用户纠正和成果修改；先总结过程，再加入真实使用反馈进行复盘 | 总结记录工作如何展开，复盘对照目标、过程与结果；能返回准确记录与版本，区分已证实原因和推测；仅保存报告不自动修改长期 Skill |
| AC-14 首页与注意力 | 一个定时报告因授权失效未生成，另有已完成的普通资料整理；重开首页并查看首次使用状态 | 同一失败归并为一个需处理事项，说明实际影响并回原任务，不再重复列为通知、异常和待办；普通结果可查看但不强制审批。首次使用可从目标或材料开始，无数据不造假 |
| AC-15 定时任务入口 | 从左侧新建任务，再从一次工作设定另一项任务；在首页收到运行结果，进入任务查看并暂停 | 两种创建方式进入统一列表；能查看触发条件、执行位置、上次与下次运行及结果；首页与原项目指向同一任务；暂停后续与停止当前含义清楚 |
| AC-16 过程证据不足 | 某成员只有工具完成事件，没有主动输出公开分析；回看并尝试复盘该轮 | 可以展示实际动作与其结果，并明确缺少公开分析；不编造内部思维或事后回填实时思考；复盘说明证据限制，不据此宣称理解或效果已验证 |
| AC-17 临时工作与找回 | 不建项目先研究一份材料，切去雷达再返回；随后将该工作归入一个项目 | 能从继续工作或查找恢复原目标、过程与成果；归入项目不复制会话或丢失版本，不要求重讲背景 |
| AC-18 默认主次与主动控制 | 新工作开始、成员处理、出现成果时，分别观察三窗口；用户正阅读历史分析时有新内容返回 | 默认内容适合该阶段，三面随时可达且桌面可并行；新内容不抢焦点、不强行切布局；旧记录与当前成果范围清楚 |
| AC-19 跨入口状态一致 | 从首页处理一个失败任务，在项目查看同一工作，再从任务历史打开上一次结果 | 原因、处置与运行状态同源，解决后首页不残留重复待办；历史成果仍指向当时版本，不把已读当解决 |
| AC-20 轻量捕获与范围 | 仅保存一条链接，稍后再以该材料发起目标；对成果的一条依据提解释问题 | 保存不自动创建运行或上传；后续工作引用原材料；解释不擅自修改正文或全局目标，所用对象可辨认 |
| AC-21 过程学习与方法沉淀 | 团队经过多轮讨论修正一份成果，用户追问未达要求的步骤，并选择沉淀方法 | 可以读懂实际步骤、方法和要求，回到问题及修正依据；形成有适用条件的流程草案供后续试用，不把保存草案当作方法已稳定或 Agent 已学会 |
| AC-22 默认团队与能力变化 | 不开启额外模式直接开始工作，随后调整成员角色或更新能力并继续相关工作 | 默认进入团队工作方式，实际分工与互相利用成果可见；变更的责任、能力与生效范围清楚，历史保留原身份和版本，既有工作可以继续 |
| AC-23 新项目初始化与接手 | 用户与团队讨论一个新产品，修正重要取舍后，采用模板初始化并交给 Codex 等工具 | 真实目标、约束、使用流程、验收与未决事项进入相应项目材料；目录和规则可核查，接收方可以从明确位置继续，不要求用户重抄讨论；未完成工程设计不冒充已完成 |
| AC-24 项目全面理解与建议边界 | 接入包含源码、配置、测试和文档的项目；建立整体理解后有源码变化，再写入两次建议 | 阅读覆盖与缺口可查，理解结合实际内容，变化影响相应状态判断；建议进入同一个固定文档并保留已有内容，其他项目代码、配置与正式方案不被改写 |

## 12. 版本选择与待明确事项

本文保留产品的完整方向，不规定当前版本必须同时交付所有功能。[PLAN.md](PLAN.md) 应明确本版纳入的用户路径、必要能力、平台和格式覆盖、交付环境以及暂不包含的部分，不以功能名称齐全代替路径完整。当前讨论建议集中记录在那里；经 USER 确认的产品行为变化再更新本文，避免候选方案被当成既定要求。

当前发布范围、首发运行环境、必须接通的具体来源与平台、订阅套餐和额度、移动端形态等，不能从这份产品定义自行推定为已经确认。现有产品行为一旦纳入某版，其质量与权限边界不能因为分批实现而被降低。

多 Agent 可视化、独立的思维窗口与过程总结／复盘，是团队协作版本的核心交互要求，不能只交付聊天和运行日志。首页和左侧直接可达的定时任务入口保留，但不把其举例内容逐项变成永久独立板块；能够开始、继续、处置和理解变化才是判断首页的依据。

第 3.1 节的首页归并、三窗口的默认主次及轻量查找属于产品设计取舍，不代表已经通过真实用户试用。具体布局和触发细节可以替代，只要保留核心能力、减少用户协调并有可操作证据。新增一项功能前应判断能否由已有工作对象、引用与操作承担；没有独立用户结果就不新增模块。复杂度首先由系统承担，不通过删掉实质分析来换取表面简单。

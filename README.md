# ytriple

**Y is the user. Triple is the amplifier.**

ytriple 是以用户为中心的 Local-first Personal AI Workbench。Y 与真正协作的常驻 AI 团队共同吸收，沉淀本地 Lib 资产，产出给人和工具的有效说明书，再通过实际使用、项目反馈和经验复用共同成长。

**吸收 → 本地资产 → 两类说明书 → 人与工具使用 → 真实反馈与成长。**团队协作和交互贯穿全程，雷达、研究、文档、工具和项目是服务这条主线的能力与入口，不是互相独立的产品。

## 第一版范围

第一版同时包含以下四部分，以 AI 与多 Agent 底座为核心：

- **AI 与多 Agent 底座**：真实模型与工具调用、成员委派与追问、必要上下文共享、成果交接，以及工作中断后的接续。
- **AI 工作台基本功能**：团队交流与成员直聊、工作和项目组织、资料与成果查看、历史接续、模型及工具配置。
- **项目初始化**：从产品雏形、需求讨论到 Codex 可以接手开发的环境，遵循本机 `/Users/Admin/AI` 下的文档与项目管理规则，建立项目登记、规则、必要文档和适用的 Git/worktree。缺少本机 AI 目录与规则体系时，先实际创建完整体系，再初始化项目；已有体系读取并保留。这两种环境都属于首版必验收范围。其他机器默认使用当前用户的 `~/AI`，具体根路径可配置；文档随实际工作持续改进。
- **文档与成果处理**：主要通过多 Agent 交互完成读取、分析、撰写、修订和保存。以 MD 输出为主，输入覆盖 PDF、TXT、MD、JSON、DOC/DOCX 等常规文档，产出也包含信息图和 PPT。

底座与项目初始化、信息消化、文档产出等真实流程同步建设和验证，工作台承载完整体验。工程选型、实施增量和验收见 [开发计划](docs/开发计划.md)，由 Codex 维护；基础雷达与收藏消化按当前产品重心设计，入口覆盖、Radar 深度、账号监控、浏览器辅助和服务器能力逐步扩展。

当前场景整合为项目孵化、信息吸收与学习、研究与创意产出三条相连的工作流。首批资料入口关注知乎收藏、抖音收藏或视频链接、GitHub，以及 X 信息；同时提供通用信息源，经团队消化后形成符合产品主线的推荐。具体接入工具及验证状态见产品调研。

团队平时保留入口，明确交给 ytriple 的任务完整展示。主窗口以简短、易懂的总结支持决策，两个辅助窗口按需展示详细报告、证据与成果。模糊问题主要由团队判断推进，Y 的明确否定与修正优先。首版只做前台运行，保存工作便于下次接续；暂不设置任务总时长和费用预算，保留可配置限制与资料外发控制的扩展方式。

## 产品边界

核心团队为统筹 / 工作伙伴、CTO / 产品技术伙伴、Deep Research / 研究员。用户可以面对团队，也可以直接与一个成员工作；常驻成员可按需调用子 Agent，固定身份不等于每次全员运行或只能三个 Agent。

雷达既消化积压收藏，也处理预置与手动信息源，用户主要阅读团队整理后的主题知识与能力线索，必要时回到原文。工具与工作流吸收进入本地资产，候选和已验证状态区分。信息源与个性化消化可成为独立工具或订阅服务方向，不只是新闻推送。

项目能力以初始化、监控和指定文档反馈为主；项目代码与正式开发方案的修改继续交给 Codex。研究、文档和资料组织是工作台自身的重要能力。说明书既包括直接成果和指导方案，也包括给执行者的目标、方法与条件；不强制生成两套重复文档。

基础模型接入以 OpenAI 兼容格式为主，同时允许 Google/Gemini 原生能力，包括 Deep Research。首版支持 Gemini、DeepSeek 与本机 Ark 的多套连接配置，可按成员选择并在任务中覆盖；具体模型能力与连接状态分别验证。账号监控先关注 TikTok、YouTube、X、抖音，必要时研究浏览器插件等辅助方式，在本机自用雏形上逐步加入。不要求全部吸收入口或平台一次开发完成。

长期方向是开源本地工作台，以及可自部署、可选订阅托管的服务器能力；具体收费服务尚未确定，当前不执行仓库公开或发布。成长由说明书的实际用途、Y 与团队的能力改善和真实项目反馈检验；高度自动化依靠验证过的资产与明确授权逐步形成。

## 研发协作

用户决定目标、取舍与授权。网页 ChatGPT 维护讨论总结、产品与能力调研及参考；Codex 负责具体设计、选型、开发拆解、实现与验证。研究不自动成为需求，不由网页 AI 另建工程规格或实施路线。
